08 — Job Schedulers: Slurm, PBS, and LSF

A cluster full of provisioned, networked, storage-attached nodes is just expensive furniture until something decides who gets to run what, where, and when. That "something" is the workload manager — the piece of software every user actually touches. This section covers why HPC clusters need one, does a deep dive on Slurm (the dominant choice for modern GPU/AI clusters), and gives practical overviews of PBS and LSF as alternatives.

Why HPC clusters need a workload manager

Picture a 200-node GPU cluster shared by 40 researchers and a dozen production training pipelines. Without a scheduler, "running a job" means SSH-ing into a node and hoping nobody else had the same idea. That breaks down almost immediately:

  • Resource allocation. Someone has to track which GPUs, CPU cores, and memory are free right now, and hand out exclusive or shared slices of them so two jobs don't collide on the same GPU.
  • Queuing. When demand exceeds supply (it always does), jobs need to wait in an orderly line rather than fail outright or silently oversubscribe hardware.
  • Fairness. One team submitting 10,000 jobs shouldn't be able to starve every other team for a month. Fair-share accounting balances historical usage against current demand.
  • Multi-tenant scheduling. Different teams, priorities, and budgets ("this account gets 30% of the H100s") need to coexist on the same physical hardware with policy enforcement, not gentlemen's agreements.
  • Accounting & auditing. Someone will eventually ask "who used the cluster last month and for how many GPU-hours" — for chargeback, for capacity planning, or for a grant report.
Slurm / PBS / LSF vs. Kubernetes

Kubernetes solves a related but different problem: long-running, self-healing, loosely-coupled microservices with declarative desired state and rolling updates. HPC/AI workload managers solve tightly-coupled, finite-duration, batch jobs — an MPI job or a multi-node training run where all ranks must start together, communicate over low-latency fabrics (InfiniBand/RoCE), and where the job simply finishes rather than being kept "alive" forever. Slurm has first-class notions of job steps, exclusive node allocation, topology-aware placement, and backfill — things Kubernetes' scheduler doesn't natively do well. That said, the lines are blurring: many AI shops run Slurm on bare metal underneath and Kubernetes for inference/serving on top, or use projects like Slurm's PMIx/pyxis plugins and Kubernetes operators (e.g. the Slurm-on-Kubernetes and MPI Operator projects) to bridge the two. For batch HPC/AI training at scale, Slurm (or PBS/LSF) remains the default choice.

Deep dive: Slurm

Slurm (Simple Linux Utility for Resource Management), maintained by SchedMD, is the most widely deployed workload manager in modern GPU and AI training clusters — it runs on a majority of TOP500 systems and is the scheduler underneath most large NVIDIA DGX SuperPOD and cloud GPU cluster reference architectures.

Core architecture

Slurm's design is deliberately simple: a central brain, an agent on every node, and a shared trust mechanism between them.

slurmctld — the controller

slurmctld is Slurm's central management daemon: it monitors resources and nodes, accepts submitted jobs, and decides which jobs get which resources and when. It typically runs on one or two dedicated "controller" nodes (a backup slurmctld can take over on failure) and is the single source of truth for cluster state.

slurmd — the node agent

slurmd runs on every compute node. Per SchedMD's documentation, it behaves like a remote shell: it waits for work, executes it, returns status, and waits for more — while participating in Slurm's fault-tolerant hierarchical communication tree so a single controller can manage thousands of nodes without a communication bottleneck.

munge — authentication

MUNGE (MUNGE Uid 'N' Gid Emporium) is Slurm's default authentication mechanism. Every host in the cluster shares a cryptographic key (/etc/munge/munge.key); the munged daemon signs and verifies RPC messages between slurmctld, slurmd, and client commands so a node can't forge a job submission or impersonate another user. If munge's clocks drift or the key is out of sync across nodes, authentication fails cluster-wide — it's usually the first thing to check when squeue hangs after a new node join.

slurmdbd — accounting

The optional Slurm Database Daemon stores historical job accounting, fair-share usage, and association (user/account/QOS) data in MySQL or MariaDB. It's what sacct and fair-share priority calculations read from, and it's required for multi-cluster federation and detailed chargeback reporting.

Partitions and QOS

A partition (Slurm's word for a queue) is a named subset of nodes with its own limits — e.g. a gpu partition for GPU-equipped nodes and a cpu partition for everything else, or debug vs. batch with different max walltimes. A QOS (Quality of Service) is an orthogonal policy object — it can raise or lower job priority, cap the number of GPUs a group of users can hold at once, or grant preemption rights — and can be layered on top of any partition. A common pattern: a high-priority QOS for production training jobs that preempts a best-effort QOS used for exploratory notebooks.

Submitting work

Slurm gives you three main entry points:

  • sbatch — submit a batch script that runs asynchronously; Slurm queues it and returns immediately with a job ID.
  • srun — run a job step, either standalone (blocking, interactive-feeling) or inside an sbatch script to launch parallel tasks across allocated nodes.
  • salloc — obtain a resource allocation interactively (e.g. for debugging), then run commands or drop into a shell on the allocated nodes.

Scheduling policies

Slurm's default scheduler is the multifactor priority plugin. Each pending job gets a priority score that blends several weighted factors — age (how long it's waited), fair-share (how much the submitting account/user has already consumed relative to its allocated share), job size, partition, and QOS. On top of ordering, the backfill scheduler is what keeps utilization high: it looks past the head of the queue and starts smaller, lower-priority jobs early — as long as doing so won't delay the expected start time of the higher-priority job at the front of the queue. This is why a big 512-GPU job can be "next in line" for hours while short single-GPU jobs keep slipping in around it without ever pushing the big job back.

GPU resource tracking with GRES

Slurm tracks GPUs (and other non-CPU resources like MPS shards) through the Generic Resource (GRES) plugin framework. Nothing is tracked by default — an admin must declare GresTypes=gpu in slurm.conf and list per-node GPU counts/types in gres.conf. Users then request GPUs at submission time, e.g. sbatch --gres=gpu:a100:2, and Slurm binds the job to specific GPU device files via cgroups so a job can never see or touch a GPU it wasn't allocated.

Isolation with cgroups

Slurm's cgroup plugin (via cgroup.conf) uses Linux control groups to enforce what a job actually gets: it constrains a job's tasks to their allocated CPU cores, caps memory so one job's OOM doesn't take down a neighbor, and restricts device access so GPU allocations from GRES are actually enforced at the kernel level rather than just "agreed on by convention." This is the mechanism that makes multi-tenant GPU sharing on a single node safe.

Worked example: a multi-node GPU training job

Here's a realistic end-to-end flow for training a model across 4 nodes × 8 GPUs each, using PyTorch's distributed launcher.

#!/bin/bash
#SBATCH --job-name=llm-pretrain
#SBATCH --partition=gpu
#SBATCH --qos=high-priority
#SBATCH --account=research-team-a
#SBATCH --nodes=4
#SBATCH --ntasks-per-node=8
#SBATCH --gres=gpu:h100:8
#SBATCH --cpus-per-task=16
#SBATCH --mem=0                     # request all available memory on the node
#SBATCH --time=08:00:00
#SBATCH --exclusive
#SBATCH --output=logs/%x-%j.out
#SBATCH --error=logs/%x-%j.err

set -euo pipefail

echo "Job $SLURM_JOB_ID starting on $SLURM_JOB_NUM_NODES nodes"
scontrol show hostnames "$SLURM_JOB_NODELIST" > logs/hostfile-$SLURM_JOB_ID.txt

export MASTER_ADDR=$(scontrol show hostnames "$SLURM_JOB_NODELIST" | head -n1)
export MASTER_PORT=29500
export NCCL_DEBUG=WARN
export NCCL_SOCKET_IFNAME=ib0

srun --gres=gpu:h100:8 --ntasks-per-node=8 --cpus-per-task=16 \
  torchrun \
    --nnodes="$SLURM_JOB_NUM_NODES" \
    --nproc_per_node=8 \
    --rdzv_id="$SLURM_JOB_ID" \
    --rdzv_backend=c10d \
    --rdzv_endpoint="${MASTER_ADDR}:${MASTER_PORT}" \
    train.py --config configs/llm_pretrain.yaml

A minimal admin-side slurm.conf and gres.conf pair for a small GPU partition looks like:

# /etc/slurm/slurm.conf (excerpt)
ClusterName=demo-cluster
SlurmctldHost=ctrl01
AuthType=auth/munge
SchedulerType=sched/backfill
SelectType=select/cons_tres
SelectTypeParameters=CR_Core_Memory
ProctrackType=proctrack/cgroup
TaskPlugin=task/cgroup
GresTypes=gpu

PriorityType=priority/multifactor
PriorityWeightAge=1000
PriorityWeightFairshare=10000
PriorityWeightJobSize=1000
PriorityWeightPartition=1000
PriorityWeightQOS=2000

NodeName=gpu-node[012-015] CPUs=128 Sockets=2 CoresPerSocket=64 \
  ThreadsPerCore=1 RealMemory=1024000 Gres=gpu:h100:8 State=UNKNOWN

PartitionName=gpu Nodes=gpu-node[012-015] Default=NO MaxTime=24:00:00 State=UP

# /etc/slurm/gres.conf (excerpt, on each GPU node)
AutoDetect=nvml
Name=gpu Type=h100 File=/dev/nvidia[0-7]
Troubleshooting: deadlocks and starvation
  • Job stuck PENDING with reason Resources: usually correct — it's waiting for enough free nodes/GPUs; check squeue --start for an estimated start time and confirm backfill can see it (small jobs shouldn't wait behind it forever).
  • Job stuck with reason Priority: other jobs simply outrank it. Check sprio -j <jobid> to see the fair-share/age/QOS breakdown and confirm the account's fair-share usage isn't saturated.
  • Classic circular-wait starvation: a large job (e.g. needing all 4 nodes) can wait indefinitely if a stream of smaller jobs keeps backfilling ahead of it and resetting the "idle gap." Mitigate with SchedulerParameters=bf_max_job_test tuning, a dedicated reservation, or raising the big job's priority/QOS so backfill respects its expected start time.
  • Nodes stuck in DRAIN or DOWN: check sinfo -R for the drain reason, then scontrol update NodeName=gpu-node012 State=RESUME once the underlying issue (bad GPU, failed health check, full disk) is fixed.
  • Munge auth failures after adding a node: verify munge.key matches across all nodes and that clocks are in sync (NTP/chrony) — munge rejects messages with too much clock skew.
  • Job appears RUNNING but produces no output: check the epilog/prolog scripts and cgroup limits — an OOM-killed rank inside an MPI job can leave the job "running" while other ranks hang waiting on a collective.

Alternatives: PBS and LSF

Slurm dominates new GPU/AI cluster builds, but PBS and LSF remain common — especially in sites with long institutional history, specific ISV software certifications, or existing licensing relationships.

PBS Professional / OpenPBS

Originally developed at NASA, OpenPBS is the open-source core of Altair's commercial PBS Professional. Jobs are submitted with qsub, using #PBS directives inside the script (analogous to Slurm's #SBATCH) for resource requests like -l select=4:ncpus=32:ngpus=8. It's popular in traditional national-lab and manufacturing/CFD HPC centers, and is well regarded for fine-grained job arrays (qsub -J 1-100) and mature commercial support (Altair) alongside the OpenPBS community edition.

IBM Spectrum LSF

IBM Spectrum LSF (originally Platform LSF) submits jobs with bsub. It's strong in heterogeneous, cross-platform enterprise environments (Unix and Windows hosts together), has deep roots in EDA/chip-design and financial-services compute farms, and offers sophisticated load-index-based dispatch (choosing hosts by real-time CPU/memory/IO load rather than static slot counts). Sites already standardized on LSF for CPU workloads sometimes extend it to GPU/AI queues rather than run two schedulers.

Field note

If you're standing up a new GPU/AI cluster today with no strong existing vendor relationship, Slurm is the default choice for most reference architectures (including NVIDIA's own DGX SuperPOD and Base Command deployment guides) — it has the deepest GPU-aware scheduling ecosystem (GRES, topology plugins, pyxis/enroot container integration, NCCL-aware placement) and the largest community of people who already know how to operate it.
