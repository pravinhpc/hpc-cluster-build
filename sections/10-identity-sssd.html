10 — Identity & Access: Integrating SSSD with Your Cluster

Your LDAP directory (or Active Directory / FreeIPA) is the source of truth for who your users are. But you don't want every one of your 2,000 compute nodes talking directly to that directory every time someone runs ls -l or ssh. SSSD is the local buffer that makes identity lookups fast, resilient, and directory-friendly at cluster scale.

WHAT — What Is SSSD?

SSSD (System Security Services Daemon) is a local system daemon that sits between the Linux operating system and one or more remote identity/authentication backends — LDAP, Active Directory, FreeIPA, or Kerberos. It is not itself a directory service; it is a broker and cache. Applications never talk to LDAP directly. Instead, the standard OS lookup paths — NSS (Name Service Switch, used by getent, id, ls -l to resolve names and groups) and PAM (Pluggable Authentication Modules, used by login, sshd, sudo to authenticate) — talk to SSSD over a local Unix socket, and SSSD talks to the directory on their behalf.

This is a deliberate architectural change from the older approach of pam_ldap and nss_ldap (or nss-pam-ldapd), which wired PAM and NSS directly into the LDAP protocol with no caching layer in between. Every lookup and every login was a live network round trip to the directory server. If the LDAP server was slow, unreachable, or overloaded, every single login attempt on every node failed immediately — there was no fallback.

WHY — Why HPC Clusters Use SSSD Instead of Direct LDAP Clients

  • Offline caching keeps nodes usable during a directory blip. If your LDAP/AD server has a network hiccup, a restart, or a maintenance window, nodes running SSSD can still authenticate already-known users and resolve UID/GID mappings from local cache. With direct pam_ldap, that same blip means every login on every node fails instantly — on a cluster with thousands of compute nodes and hundreds of concurrently starting jobs, that is not a hypothetical, it is a recurring operational reality.
  • Reduced load on the directory server. A large cluster job launch can spawn identity lookups (getpwnam, group resolution) from thousands of node daemons and shell sessions nearly simultaneously. Without a cache, this becomes a thundering-herd problem against your LDAP server. SSSD absorbs the vast majority of these lookups locally and only refreshes on a TTL, converting a burst of thousands of directory queries into a trickle.
  • Built-in Kerberos ticket management. HPC environments frequently pair identity (LDAP/AD) with Kerberos for SSO and for secure NFS (sec=krb5) or Slurm authentication. SSSD natively renews and manages Kerberos tickets as part of the login flow, instead of requiring a hand-stitched pam_krb5 plus pam_ldap combination.
  • Consistent behavior across mixed OS images. Large clusters are rarely 100% homogeneous — you may have RHEL/Rocky login nodes, Ubuntu compute nodes, and a different distro for storage or management nodes. SSSD ships as a standard, well-maintained package on all of them, giving you one identity-resolution behavior and one config file format to reason about instead of distro-specific LDAP client quirks.
Common Misstep
Teams that skip SSSD and hand-roll /etc/ldap.conf + pam_ldap on a golden image usually regret it the first time the directory server needs a maintenance restart during business hours — every node in the cluster loses the ability to start new sessions at once, including the admins trying to SSH in to fix it.

WHERE — Where SSSD Sits in the Cluster

SSSD runs as a local daemon on every single node — login nodes, compute nodes, storage/NFS gateway nodes, and (if they authenticate interactive users) management nodes. It is not a centralized service; there is no "SSSD server" for the cluster to depend on beyond the identity backend itself. Each node caches identity data independently, in its own local /var/lib/sss/db/ database.

Logically, SSSD sits directly beneath /etc/nsswitch.conf and the PAM stack, and directly above the network connection to your directory. This is the same LDAP/AD/FreeIPA backend described in Section 09 — LDAP Integration — SSSD does not replace that backend, it is the client-side layer that makes consuming it safe at scale.

WHEN — When to Configure SSSD in the Build Sequence

SSSD configuration belongs in the base/golden node image build — the same stage where you set up NTP, DNS resolution, and the NFS/LDAP client packages. It should be baked in and validated before nodes are registered with the provisioning system (BCM, xCAT, Warewulf) and long before they are added to the scheduler's node pool (Slurm/PBS). The reasoning is simple: the scheduler will try to resolve job-submitting users' UIDs/GIDs on every node the moment it's in the pool, and epilog/prolog scripts often depend on working id and getent passwd calls. If SSSD isn't configured and validated first, node registration and job dispatch will fail with confusing, hard-to-trace permission and UID errors.

Recommended order: base OS image → network/DNS/NTP → SSSD + LDAP/Kerberos client config (this section) → validate with id/getent → join provisioning system → join scheduler pool.

Cache Invalidation Tradeoff
There is a real tension between offboarding urgency (a terminated employee's access should disappear fast) and cache TTL (long TTLs mean fewer directory hits but slower revocation). A common compromise on HPC clusters: keep entry_cache_timeout in the 1–4 hour range for routine operation, and maintain a documented, scripted sss_cache -E + restart procedure (pushed via your config management tool, e.g. Ansible, across all nodes) for emergency offboarding, rather than dropping TTLs cluster-wide just to cover the rare urgent case.

HOW — Step-by-Step Configuration

1. Install the packages

# RHEL / Rocky / AlmaLinux
sudo dnf install -y sssd sssd-ldap sssd-krb5 sssd-tools authselect

# Ubuntu / Debian
sudo apt-get install -y sssd sssd-ldap sssd-krb5 sssd-tools libnss-sss libpam-sss

2. Configure /etc/sssd/sssd.conf

This file must be owned by root with permissions 0600 — SSSD will refuse to start otherwise. Below is a realistic configuration for an HPC cluster node pointed at an LDAP directory, with offline caching and TLS enabled:

[sssd]
# Services this instance provides to the OS
services = nss, pam
domains = hpccluster.example.org
config_file_version = 2

[domain/hpccluster.example.org]
id_provider = ldap
auth_provider = ldap
chpass_provider = ldap

ldap_uri = ldap://ldap01.hpccluster.example.org,ldap://ldap02.hpccluster.example.org
ldap_search_base = dc=hpccluster,dc=example,dc=org
ldap_id_use_start_tls = true
ldap_tls_cacert = /etc/pki/tls/certs/hpc-ca-bundle.pem

# --- Offline / caching behavior: the whole point for a large cluster ---
cache_credentials = true
entry_cache_timeout = 5400
entry_cache_user_timeout = 5400
entry_cache_group_timeout = 14400
offline_credentials_expiration = 7

# Do NOT enumerate the full directory on a large cluster: it is expensive
# and unnecessary — resolve users/groups on demand instead.
enumerate = false

# UID/GID mapping (skip if the directory already publishes POSIX attrs
# via RFC2307 / RFC2307bis schema, as covered in Section 09)
ldap_id_mapping = false

min_id = 10000
max_id = 2000000

# Make home directories consistent across every node
override_homedir = /home/%u
default_shell = /bin/bash

[nss]
filter_groups = root
filter_users = root
entry_negative_timeout = 15

[pam]
offline_credentials_expiration = 7
pam_verbosity = 2

3. Point NSS and PAM at SSSD

On RHEL-family systems this is best done through authselect, which writes consistent, supported NSS and PAM configuration in one step:

sudo authselect select sssd with-mkhomedir --force
sudo systemctl enable --now sssd

Manually, this is equivalent to ensuring /etc/nsswitch.conf includes sss in the passwd/group/shadow lines, and the PAM stack (/etc/pam.d/system-auth or /etc/pam.d/common-auth on Debian/Ubuntu) includes pam_sss.so:

passwd:     files sss
group:      files sss
shadow:     files sss
netgroup:   files sss

4. Bake it into the golden/node image

Once validated on a single test node, fold the package install, sssd.conf, TLS CA bundle, and authselect/PAM changes into your provisioning system's golden image build (BCM software image, xCAT osimage, or Warewulf container). Every node provisioned from that image then boots with identity resolution already working — this must happen before the node is registered with the scheduler.

5. Tune cache timeouts for cluster scale

ParameterPurposeTypical HPC value
entry_cache_timeoutGeneral TTL for all cached entries3600–5400s
entry_cache_user_timeoutTTL specifically for user entries5400s
entry_cache_group_timeoutTTL for group entries (change less often)14400s
offline_credentials_expirationDays a cached password remains valid while offline7 days
enumerateWhether to pre-fetch the entire directoryfalse (always, on large clusters)
Do Not Enable Enumeration
enumerate = true tells SSSD to download and cache the entire user/group directory up front. On a directory with tens of thousands of accounts this is slow to complete, adds real load to the LDAP server on every SSSD restart across every node, and is almost never necessary — SSSD resolves individual users/groups on demand just fine.

6. Troubleshooting

# Check SSSD service state and recent errors
sudo systemctl status sssd
sudo journalctl -u sssd -n 100 --no-pager

# Increase log verbosity for the LDAP backend, then check the domain log
sudo sed -i 's/^debug_level.*/debug_level = 7/' /etc/sssd/sssd.conf
sudo systemctl restart sssd
sudo tail -f /var/log/sssd/sssd_hpccluster.example.org.log

# Confirm a specific user resolves via SSSD (bypasses local /etc/passwd)
getent passwd jdoe
id jdoe

# Force SSSD to go back to the directory instead of serving stale cache
sudo sss_cache -E
sudo systemctl restart sssd

# Clear the cache for one user only, without a full restart
sudo sss_cache -u jdoe

# Simulate an offline node to test cached-credential login
sudo systemctl stop network sssd   # in a lab node, NOT production
sudo systemctl start sssd
id jdoe   # should still resolve from cache if previously logged in
Field Note
The single most common "SSSD is broken" ticket on a new cluster build is actually a permissions problem: /etc/sssd/sssd.conf not being exactly 0600 root:root. SSSD silently refuses to start (or starts with a stale config) if the permissions are wrong — check this first before diving into LDAP connectivity.
