06 — Cluster Provisioning with Warewulf + OpenHPC

If BCM is the polished commercial product and xCAT is the venerable 20-year-old toolbox, Warewulf + OpenHPC is the "modern open-source native" path: a lightweight, container-image-based provisioning tool paired with a curated, pre-tested stack of HPC software. Together they're the closest thing the open-source HPC world has to a documented, reproducible recipe for going from bare metal to a working Slurm cluster — for the cost of your own time.

What are Warewulf and OpenHPC, really?

Warewulf is a cluster provisioning system, currently on major version 4 (a ground-up rewrite from the Warewulf 3 era). Its whole philosophy is stateless-first: instead of installing an OS to each compute node's disk, Warewulf builds a single container image — a normal OCI/Docker-style root filesystem — and PXE-boots every compute node straight into that image over the network. There's no per-node install step, no drift between nodes, and no need for local disks at all on the compute fleet. Warewulf 4 replaced the old Warewulf 3 toolchain (wwsh, wwbootstrap, wwmkchroot, wwvnfs) with a single unified CLI: wwctl.

OpenHPC, on the other hand, isn't a provisioning tool at all — it's a curated software distribution: a large, pre-built, pre-tested set of RPM packages covering everything a cluster needs above bare Linux — Slurm, compilers (GNU, and optionally Intel/LLVM toolchains), MPI libraries (OpenMPI, MPICH, MVAPICH), performance tools, and provisioning "recipes" that glue a base OS + Warewulf (or xCAT) + Slurm together into a documented build. OpenHPC is a community project hosted by the Linux Foundation, with contributions from Intel, Dell, Lenovo, and various national labs and universities.

The two are not the same layer, and that's the point: Warewulf answers "how do bits get onto a bare-metal node," OpenHPC answers "which HPC software, at which tested versions, goes into that image." OpenHPC's official install guides (the "Cluster Building Recipes" PDFs) are written specifically against Warewulf as the reference provisioning backend, which is why the two are almost always discussed together.

Why this pairing is popular
Warewulf + OpenHPC is entirely free and open source, has no vendor lock-in, and is directly documented by the OpenHPC project itself with version-pinned "recipe" PDFs for specific OS + Warewulf + Slurm combinations. It's the path of choice for university clusters, national labs, and anyone who wants to understand — and own — every layer of their stack rather than depend on a commercial platform.

Core concepts

Container images (the node's root filesystem)

In Warewulf 4, what used to be called a "VNFS image" in Warewulf 3 is now simply a container. You build it by importing a base OS container from any OCI registry (Docker Hub, GitHub Container Registry, a private registry) and then customizing it — installing packages inside it with wwctl container exec, much like building a Dockerfile interactively. The finished container becomes the exact root filesystem every compute node boots from. Warewulf publishes ready-made base containers (e.g. ghcr.io/warewulf/warewulf-rockylinux:9) so you rarely start truly from scratch.

Overlays (system vs. runtime)

A container image is the same for every node in a profile — but real nodes need per-node differences: hostname, IP address, SSH host keys, /etc/hosts, Slurm's slurm.conf. Warewulf solves this with overlays — small, templated sets of files layered on top of the container at boot time (and periodically refreshed):

  • System overlay: applied early in boot, before the node is fully up — things the node needs to actually boot and get network config (network interfaces, hostname, /etc/passwd).
  • Runtime overlay: applied after boot and can be re-pushed live to running nodes without a reboot — things like updated Slurm config, SSH keys, or monitoring agent config.

Overlay files are Go templates rendered per-node from Warewulf's node database, so one template (e.g. /etc/hosts.ww) generates a correct, unique file for every single node automatically.

Node profiles

Rather than specifying every setting (container, kernel args, network config) on every single node, you define a profile — a template of defaults — and nodes inherit from it. A typical setup has a default profile plus maybe a gpu-compute profile with different kernel arguments or a different container. Adding a new node is then often just one line assigning it to a profile and giving it a MAC/IP.

PXE / iPXE boot flow

Mechanically it's the same DHCP → TFTP/PXE → boot pattern every provisioning tool uses under the hood (see the xCAT section for the general pattern), but Warewulf owns the whole chain itself via wwctl configure: it can run its own DHCP/TFTP services, or hand off to iPXE for a more capable, scriptable boot loader that fetches the kernel, initramfs, and container image over HTTP instead of the much slower legacy TFTP-only path.

Step-by-step: building a cluster with Warewulf + OpenHPC

This walkthrough follows the shape of OpenHPC's own "Cluster Building Recipes" (published per OS release, e.g. Rocky Linux 9 + Warewulf + Slurm) and real wwctl syntax from the Warewulf 4 documentation. Adjust package/version numbers to whatever OpenHPC release you're targeting — the OpenHPC recipe PDFs pin exact versions per OS.

Step 1 — Install OpenHPC base + Warewulf on the head node

Start from a clean Rocky Linux/RHEL install on the head (management) node, add the OpenHPC repo, then pull in the OpenHPC base meta-package and the Warewulf integration package:

# Enable the OpenHPC repo for your OS release (example: EL9)
dnf -y install http://repos.openhpc.community/OpenHPC/3/EL_9/x86_64/ohpc-release-3-1.el9.x86_64.rpm

# Base OpenHPC tools + Warewulf provisioning integration
dnf -y install ohpc-base warewulf-ohpc hwloc-ohpc

# Enable and start the Warewulf daemon
systemctl enable --now warewulfd

Step 2 — Build a Warewulf container image with OpenHPC packages

Import a base OS container from an OCI registry, then exec into it to install OpenHPC packages, exactly like customizing a Dockerfile interactively:

# Import an official Warewulf base container (Rocky 9)
wwctl container import docker://ghcr.io/warewulf/warewulf-rockylinux:9 rocky-9 --syncuser

# Exec into the container to add the OpenHPC repo + base packages
wwctl container exec rocky-9 /bin/bash <<'EOF'
dnf -y install http://repos.openhpc.community/OpenHPC/3/EL_9/x86_64/ohpc-release-3-1.el9.x86_64.rpm
dnf -y install ohpc-base-compute chrony ohpc-slurm-client
dnf -y update
EOF

# Rebuild the bootable image artifacts from the modified container
wwctl container build rocky-9
Tip
wwctl container exec drops you into the container's chroot with its own package manager working normally — you're literally building the compute-node root filesystem by installing packages into it, no separate "image build" DSL to learn.

Step 3 — Define node profiles and nodes

# Create/adjust a profile compute nodes will inherit from
wwctl profile add compute
wwctl profile set compute --container=rocky-9 --netdev=eth0

# Add individual nodes, referencing the profile and container
wwctl node add n0001 --profile=compute --ipaddr=10.1.1.101 --hwaddr=3c:ec:ef:...:01
wwctl node add n0002 --profile=compute --ipaddr=10.1.1.102 --hwaddr=3c:ec:ef:...:02

# Confirm what was registered
wwctl node list

Step 4 — Configure network boot (DHCP / TFTP / iPXE)

# Generate and apply DHCP, TFTP, and iPXE configuration in one shot
wwctl configure --all

# Or configure services individually
wwctl configure dhcp
wwctl configure tftp

# Push overlays so nodes have current per-node config baked in
wwctl overlay build

wwctl configure --all writes out DHCP reservations for every defined node's MAC, sets up the TFTP/iPXE boot chain, and restarts the relevant services — the Warewulf equivalent of xCAT's makedhcp/makedns step.

Step 5 — Boot the compute nodes

Power on (or PXE-reboot) the compute nodes. With network boot as the first boot device in firmware/BIOS, each node will DHCP, fetch the iPXE chain, then pull the kernel, initramfs, and container image over HTTP and boot straight into it — no install step, no waiting on disk partitioning:

# Watch nodes come up
wwctl node status

# Tail the head node's provisioning logs while nodes boot
journalctl -u warewulfd -f

Step 6 — Install Slurm + OpenHPC dev toolchain

Slurm's controller runs on the head node; Slurm's client daemon is already baked into the compute container from Step 2. Add the controller-side packages and a compiler/MPI toolchain for users:

# On the head node — Slurm controller + Munge auth
dnf -y install ohpc-slurm-server
systemctl enable --now munge
systemctl enable --now slurmctld

# Compiler + MPI stack (goes into the compute container, then rebuild it)
wwctl container exec rocky-9 dnf -y install gnu14-compilers-ohpc
wwctl container exec rocky-9 dnf -y install openmpi5-pmix-gnu14-ohpc
wwctl container build rocky-9

# Push the updated container + config out and restart compute-side services
wwctl overlay build

Step 7 — Validate with a test MPI job

# As a regular (non-root) user, load the OpenHPC-provided module environment
module load gnu14 openmpi5

# Compile a simple MPI hello-world (OpenHPC ships one under /opt/ohpc/pub/examples)
mpicc -O3 -o mpi_hello /opt/ohpc/pub/examples/mpi/hello.c

# Submit it through Slurm across two nodes
sbatch -N 2 --ntasks-per-node=4 --wrap="mpirun ./mpi_hello"

# Check it landed and ran correctly
squeue
sacct -j <jobid> --format=JobID,NodeList,State,ExitCode

A clean run — job completes, exit code 0, output shows one greeting line per rank from both nodes — confirms Warewulf's provisioning, the network fabric, Munge authentication, and Slurm's scheduler are all correctly wired end to end.

OpenHPC component stack — how the layers fit

Pros / cons vs. BCM and xCAT

ToolModelStrengthsTrade-offs
Warewulf + OpenHPCFree, open-source, OCI-container image basedSimple mental model (containers + overlays), modern workflow, OpenHPC gives version-tested package recipes, zero license cost, active upstream (hpcng/Warewulf, openhpc.community)Smaller ecosystem than xCAT for exotic hardware/console management at extreme scale; you own all integration and support yourself
xCATFree, open-source, CLI/DB-drivenExtremely mature, flexible, scales to very large/hierarchical clustersSteeper learning curve, less modern image workflow, community support only
BCM (Bright)Commercial, GUI + CLITurnkey experience, vendor support, integrated monitoring out of the boxLicense cost, less transparent internals, vendor lock-in
Watch out
Warewulf's stateless-by-default model means anything written outside the container/overlay system (e.g. an admin manually installing a package on a running node with dnf install) vanishes on next reboot. This is a feature for consistency, but it catches newcomers who expect a normal persistent Linux box — always make changes in the container and rebuild.
Why this matters
This is the most "open-source native" and cost-free path in this entire guide: no license, no vendor account, and the exact commands here are traceable back to public Warewulf and OpenHPC documentation. It's an excellent choice for labs, universities, and any team that wants to fully own and understand their provisioning stack.
