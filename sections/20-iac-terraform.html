20 — Infrastructure as Code: Provisioning Cluster Infrastructure with Terraform

Section 07 covered Ansible and bare-metal provisioning — turning already-existing servers into a working cluster. This section is one layer below that: how the cloud resources those servers (or node pools) live on get created in the first place. Terraform is the most widely used tool for that "day 0" job — declaring a VPC, subnets, IAM roles, storage, and GPU node pools as code, before any configuration-management tool ever touches a node.

Where Terraform sits in the stack

It's easy to conflate Terraform and Ansible because both are "infrastructure automation," but they solve different problems and operate at different layers:

Terraform — infrastructure provisioning

  • Creates the cloud resources themselves: VPC/VNet, subnets, route tables, security groups, IAM roles/policies, compute instances or managed node pools, block/object storage, load balancers
  • Declarative — you describe the desired end state, Terraform computes a diff and a plan to get there
  • Tracks a state file mapping your config to real-world resource IDs
  • Answers: "does this VPC, subnet, and GPU node pool exist, with these exact settings?"

Ansible — configuration management

  • Configures the operating system inside resources that already exist: packages, users, drivers, Slurm, munge
  • Procedural-declarative hybrid — runs tasks against live hosts over SSH
  • Mostly stateless between runs — re-derives current state by inspecting the host each time
  • Answers: "is this VM/node running the right kernel, drivers, and Slurm config?"

In a typical GPU cluster build, Terraform runs first to stand up the VPC, subnets, IAM roles, storage buckets, and the compute instances or node pool that will become login/compute/controller nodes. Once those instances exist and are reachable, Ansible (or a cluster-management tool like Bright/Warewulf) takes over and brings the OS on each node to a known-good state — the same split of responsibility as bare-metal PXE/kickstart handing off to Ansible in section 07, just with cloud API calls standing in for a physical power-on.

Provisioning layer stack

Core Terraform concepts

ConceptWhat it is
ProviderA plugin that talks to a specific API — aws, google, azurerm — translating HCL resource blocks into cloud API calls
ResourceA single managed object: one VPC, one subnet, one node pool, one IAM role
ModuleA reusable, parameterized bundle of resources — e.g. a "GPU node pool" module callable once per cloud with different variables
StateA file (terraform.tfstate) mapping your config to real resource IDs — Terraform diffs desired vs. actual state on every plan
BackendWhere state lives — local disk by default, or a remote backend (S3, GCS, Azure Blob, Terraform Cloud) for team use
State lockingA mutex on the state file so two concurrent apply runs can't corrupt it — implemented via DynamoDB, GCS native locking, or the backend's built-in lock API
Rule of thumb
Never run Terraform against local state for anything beyond a solo experiment. The moment more than one person (or a CI pipeline) touches a cluster's infrastructure, a remote backend with locking is mandatory — local state has no way to prevent two concurrent applies from clobbering each other.

A reusable GPU node pool module

The pattern that scales across clouds is a small, parameterized module — one Terraform module per logical resource (a GPU node pool, a VPC, a storage bucket) — called once per provider with provider-specific variables. This keeps the calling code (the "root module" for a given cluster) short and readable, and lets you reason about a GPU node pool the same way regardless of which cloud it's on.

# modules/gpu-node-pool/variables.tf
variable "cluster_name"     { type = string }
variable "node_count"       { type = number }
variable "gpu_instance_type" { type = string }   # e.g. p5.48xlarge / a3-highgpu-8g / Standard_ND96isr_H100_v5
variable "subnet_id"        { type = string }
variable "labels"           { type = map(string), default = {} }

# modules/gpu-node-pool/main.tf (AWS example — EKS managed node group)
resource "aws_eks_node_group" "gpu" {
  cluster_name    = var.cluster_name
  node_group_name = "${var.cluster_name}-gpu"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = [var.subnet_id]

  scaling_config {
    desired_size = var.node_count
    max_size     = var.node_count
    min_size     = var.node_count
  }

  instance_types = [var.gpu_instance_type]
  labels         = merge(var.labels, { "nvidia.com/gpu" = "true" })

  taint {
    key    = "nvidia.com/gpu"
    value  = "true"
    effect = "NO_SCHEDULE"
  }
}

Calling this same module shape against GCP swaps aws_eks_node_group for google_container_node_pool, and against Azure for azurerm_kubernetes_cluster_node_pool — the variables (cluster_name, node_count, gpu_instance_type) stay conceptually the same even though the underlying resource type is provider-specific. Teams building multi-cloud GPU capacity typically keep one module per provider behind a common variable interface, rather than trying to force a single resource block to be truly cloud-agnostic.

Terraform + cluster-build-tool integration

Terraform rarely stands alone in an HPC build — it's often the engine underneath a higher-level cluster tool, or the surrounding-infrastructure layer next to one:

  • Google Cloud Cluster Toolkit (formerly Cloud HPC Toolkit) is Terraform-based under the hood: you author a YAML "blueprint," the gcluster CLI compiles it into a deployment folder containing generated Terraform (and Packer) configuration, which you then apply directly.
  • AWS ParallelCluster has an official Terraform provider and module (from ParallelCluster 3.8.0+) — Terraform manages the surrounding VPC, subnets, and networking, while the ParallelCluster provider manages the cluster resource itself, so the whole stack — network plus cluster — is defined in one HCL codebase.
  • Azure CycleCloud / AKS and most managed Kubernetes-based GPU platforms expose Terraform providers (azurerm, google, aws) for the surrounding VNet/VPC and node pool resources, even when the scheduler layer on top is configured by a separate tool.

The practical pattern: Terraform owns the network, IAM, storage, and node pool/instance layer everywhere; whatever sits above it (Slurm via Ansible, Kubernetes via a cluster tool, a vendor's own installer) consumes the IDs Terraform outputs — VPC ID, subnet IDs, node pool name — as inputs.

State management at scale

State is the single most operationally sensitive artifact in a Terraform workflow — lose it or corrupt it and Terraform no longer knows what it manages. At team scale, three practices matter:

  • Remote backends — store state in S3 (with an S3-native lock or a DynamoDB lock table), Google Cloud Storage, Azure Blob, or Terraform Cloud/Enterprise, never on a laptop disk.
  • Workspaces — Terraform workspaces (or, more robustly, separate state files per environment via directory/backend-key separation) keep dev/staging/production or per-cluster state fully isolated, so an apply against one workspace can never touch another's resources.
  • State locking — the backend takes a lock before any plan/apply that could write state, and releases it after. This is what prevents two engineers (or a human and a CI job) from applying concurrently and corrupting the state file.

CI/CD for Terraform

Because Terraform changes can create, modify, or destroy real cloud infrastructure, the review discipline around it is typically stricter than application code CI:

# .gitlab-ci.yml (excerpt)
stages: [validate, plan, apply]

validate:
  script:
    - terraform fmt -check
    - terraform validate

plan:
  script:
    - terraform plan -out=tfplan
  artifacts:
    paths: [tfplan]

apply:
  script:
    - terraform apply tfplan
  when: manual        # human approval gate before anything touches real infra
  only: [main]

The core pattern is plan/apply gating: every merge request runs terraform plan and posts the diff for human review; apply only runs against the exact plan that was reviewed (not a fresh plan at apply time, which could drift from what was approved), and production applies are gated behind manual approval. A separate scheduled job running terraform plan with no apply step doubles as a drift detector — if it reports changes against infrastructure nobody touched via Terraform, something was modified out-of-band (a console change, a manual fix during an incident) and needs reconciling.
