00 — Introduction & The HPC Stack Overview

A High-Performance Computing (HPC) cluster is not "a bunch of powerful servers." It's dozens, hundreds, or tens of thousands of computers wired together with a purpose-built network so they behave, for the duration of a job, like a single enormous machine. This section gives you the mental model you need before touching any hardware: what a cluster actually is, how its layers stack on top of each other, who builds and runs it, and how the rest of this guide is organized.

What Makes a Cluster Different From "Just a Bunch of Servers"

If you've used cloud virtual machines, you already understand renting compute. Spin up a VM, SSH in, run your code, shut it down. An HPC cluster shares some DNA with that world but solves a fundamentally different problem: tightly-coupled, large-scale parallel work where hundreds of processors need to exchange data with each other in microseconds, not milliseconds.

Cloud VM / Single Server

One machine (or a loosely related fleet) does independent work. Network between VMs is "good enough" Ethernet through a virtualized layer. Storage is usually a remote block or object volume attached over the same general-purpose network. Scheduling is "start this VM when I ask" — there's no queue of competing jobs fighting over the same physical fabric.

HPC Cluster

Hundreds of physical nodes run one logical job split across all of them simultaneously (e.g., training one large model, or one weather simulation). They need a low-latency, high-bandwidth fabric (InfiniBand or RDMA-capable Ethernet) so GPUs on different physical machines can talk almost as fast as GPUs inside the same machine. A scheduler (Slurm, PBS, LSF) decides whose job runs where and enforces fair sharing of a fixed, expensive pool of hardware.

Why this matters
Every design decision downstream in this guide — the fabric you pick, the storage you choose, how you provision nodes, how you schedule jobs — flows from this one fact: a cluster's job is to make many physical computers act like one very large computer for the length of a single computation.

The Layered Mental Model

The cleanest way to understand an HPC cluster is as a stack of layers, each one built on top of the one below it. This is the same order this guide follows, section by section.

Read the stack bottom-up as "what's built on what," and top-down as "what a user actually touches." A researcher submitting a job never thinks about InfiniBand cabling — but if the fabric layer is misconfigured, their job silently runs 10x slower or fails to scale, and the symptom shows up all the way at the top, in the scheduler and the user's log file.

Anatomy of a Cluster

Zoom into the hardware/network picture and every HPC cluster — from a 16-node university lab rig to a multi-thousand-GPU NVIDIA DGX SuperPOD — is built from the same recognizable parts.

The Building Blocks, Explained

ComponentRole
Login node(s) The only machine(s) users SSH into directly. Used to edit code, compile, manage data, and submit jobs to the scheduler. Deliberately not where heavy computation happens — a runaway process here would degrade the experience for every user on the cluster.
Head / management node Runs the cluster management software (e.g., NVIDIA Base Command Manager, xCAT, or Warewulf), DHCP/PXE/DNS services for provisioning, and often the scheduler's control daemon. In NVIDIA's DGX SuperPOD reference architecture this role is typically handled by a redundant pair of head nodes for high availability.
Compute nodes Where the actual work happens — CPUs, GPUs (often 8 per node in DGX-class systems), local NVMe scratch, and high-speed network adapters. These are provisioned, not hand-configured, so hundreds of them stay identical.
Management network A standard Ethernet network (often 1GbE–25GbE) carrying provisioning traffic (PXE boot), configuration management, monitoring metrics, and interactive SSH. Kept logically and often physically separate from the high-speed fabric.
High-speed fabric InfiniBand or RDMA-capable Ethernet (RoCE) connecting GPUs across nodes with microsecond-scale latency. This is what lets a training job spread across 500 GPUs behave like they're in one box. NVIDIA's DGX SuperPOD architectures separate this into distinct compute and storage InfiniBand fabrics precisely so training traffic never contends with storage I/O.
Storage nodes Servers running a parallel filesystem (Lustre, GPFS/Spectrum Scale) or NFS, exporting a shared namespace so any compute node can read/write the same files a job needs, regardless of which physical node it lands on.
Field note
NVIDIA's DGX SuperPOD reference architectures typically dedicate five dual-socket x86 servers to system management: two run as a redundant pair of Base Command Manager head nodes, and three more host supporting services. The full design uses four distinct networks — a compute (InfiniBand) fabric, a storage fabric, an in-band management/Ethernet network, and an out-of-band (BMC/IPMI) management network — so that no single traffic type can starve another.

Who Does What

Cluster Admin

Owns the physical and platform layers: racking, cabling, provisioning images, keeping nodes healthy, patching the OS, managing the fabric and storage, and operating the scheduler. Lives in layers 1–4 (and touches 5, 6, 8) of the stack.

HPC Engineer

Bridges infrastructure and users: tunes the scheduler's fair-share policy, builds module environments and container images, optimizes MPI/NCCL performance across the fabric, and diagnoses why a job scales well on 8 nodes but falls apart on 80. Lives in layers 5–8.

User (Researcher/Engineer)

Never touches provisioning or the fabric directly. Logs into the login node, loads a module or container, writes a batch script, and submits it to the scheduler. Their entire experience of "the cluster" is layers 6–8 of the stack.

A Day in the Life: Submitting a Job

To make the stack concrete, here's what actually happens when a researcher — call her Priya — runs a multi-GPU training job.

  1. SSH in. Priya connects to login01. Her identity is checked against LDAP/SSSD (layer 6) — the cluster doesn't have a local Unix account for her; it trusts the central directory.
  2. Load the environment. She runs module load pytorch/2.4 or pulls a container image — the user environment layer (7) hands her a known-good, reproducible software stack instead of "whatever happens to be installed."
  3. Write and submit a batch script. Something like sbatch --nodes=4 --gpus-per-node=8 train.sh. This hands control to Slurm (layer 5), which queues the request.
  4. The scheduler places the job. Slurm's control daemon (slurmctld) checks which of the compute nodes are free, healthy, and topologically close together on the fabric, then dispatches the job to per-node slurmd daemons that actually launch it.
  5. The job runs across the fabric. PyTorch's distributed backend uses NCCL over InfiniBand/RDMA (layer 2) so the 32 GPUs across 4 nodes synchronize gradients almost as fast as if they were in one box. Checkpoints are written to the shared parallel filesystem (layer 3), visible identically from every node.
  6. Priya watches it happen. Grafana dashboards fed by DCGM and Prometheus (layer 8) show GPU utilization, temperature, and fabric throughput in near-real time, so both Priya and the cluster admin can tell instantly if a GPU is idle, a node has fallen off the fabric, or the job is I/O-bound.
  7. The job finishes; resources are freed. Slurm marks the nodes idle again, ready for the next queued job — the whole cluster is a shared, time-multiplexed resource, not dedicated hardware per user.
Common newcomer mistake
Running compute directly on the login node ("it's just a quick test!"). Login nodes are shared by every user on the cluster and are not sized for GPU or heavy CPU workloads — always submit even small test jobs through the scheduler, ideally to an interactive/debug queue.
