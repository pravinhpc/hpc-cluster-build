07 — Roll-Your-Own: Bare-Metal Provisioning with Ansible + Slurm (No Vendor CM Tool)

Every HPC cluster manager we've covered so far — Bright Cluster Manager, xCAT, Warewulf — bundles provisioning, image management, and monitoring into one opinionated product. Plenty of teams skip all of them and build the same outcome from plain, boring, well-documented pieces: a kickstart file, an Ansible inventory, and a pile of roles. This section walks through why teams do that, what the toolchain looks like, and a realistic step-by-step build.

Why skip the vendor cluster-management tool?

Bright Cluster Manager (BCM), xCAT, and Warewulf all solve a real problem — turning a rack of bare-metal servers into a coherent, provisioned, monitored cluster — but they come with trade-offs that push some teams toward a hand-rolled stack instead:

Reasons to go vendor/CM-tool

  • Turnkey image management, node groups, health checks, GUI/CLI out of the box
  • Vendor support contract (BCM) — someone to call at 2am
  • Built-in monitoring/alerting integration
  • Faster to stand up a first cluster if the team has never done this before

Reasons to roll your own

  • Small clusters (a handful to a few dozen nodes) where a full CM platform is overkill
  • Full control — no black-box image format, no proprietary CLI wrapping systemd/Slurm underneath
  • Avoiding vendor lock-in — BCM licensing cost scales with node count; Ansible/Foreman are free and portable
  • Cloud/bare-metal hybrid — the same Ansible roles that configure a bare-metal compute node can configure a cloud VM or a bare-metal-as-a-service instance (Oracle Cloud, CoreWeave, Equinix Metal), so one config-management codebase spans both
  • Existing Ansible investment — many infra teams already run Ansible for everything else (networking, storage, web fleets); adding Slurm nodes to the same tool avoids a second stack to learn
  • Auditability — plain YAML in git is easier to diff, review, and reason about than a CM tool's internal database
The honest trade-off
Full control and zero license cost, but you own every integration and edge case: driver version skew, kernel/OFED mismatches, image drift, and the glue between provisioning and the scheduler are now your team's job, not a vendor's. Roll-your-own works best when you have (or want to build) real Ansible/Linux systems expertise on the team.

The toolchain

There's no single "roll-your-own" product — it's a stack of small, independently maintained tools, each doing one job well:

LayerTool optionsJob
Bare-metal OS installForeman + Cobbler, or Canonical MAAS, or plain PXE + kickstart/preseedPXE-boot a bare node, partition disks, install a minimal base OS unattended
Golden image (optional)HashiCorp PackerPre-bake an OS image with drivers/agents already installed, so first boot is fast and consistent
Configuration managementAnsible (playbooks + roles)Bring every node to a known-good state: users, NTP, DNS, drivers, packages, services
Cluster softwareAnsible roles for Slurm, munge, OpenMPI, MLNX_OFED / GPU driversTurn a configured Linux box into a working scheduler node
Testing / CIansible-lint, Molecule, git + GitLab CI/GitHub ActionsCatch broken roles before they hit production nodes

A common, pragmatic pattern for teams under ~200 nodes: skip Foreman/Cobbler entirely, use a plain PXE server (dnsmasq + a kickstart file per node role) to get a minimal OS on the disk, then hand everything else — from that point forward — to Ansible. Foreman or MAAS earn their keep once you're managing enough hardware diversity or churn that a UI-driven inventory of machines, discovery, and re-provisioning workflows pays for itself.

Step-by-step: building the pipeline

Step 1 — PXE / kickstart base OS install

Every node PXE-boots off the management network, hits a DHCP/TFTP server (dnsmasq is the common lightweight choice; Foreman/Cobbler if you want a managed front-end), and loads a kickstart (RHEL/Rocky/AlmaLinux) or preseed/cloud-init (Debian/Ubuntu) file that does the minimum: partition disks, set the hostname from MAC/IP mapping, install a minimal package set, drop an SSH key, and register the node so Ansible can reach it. Nothing cluster-specific happens here — no drivers, no Slurm. That's Ansible's job, starting the moment the node reboots into its installed OS.

# /var/lib/tftpboot/kickstart/compute.ks  (RHEL/Rocky-family)
lang en_US.UTF-8
keyboard us
timezone UTC --utc
rootpw --lock
sshkey --username=root "ssh-ed25519 AAAA...clusteradmin"

# Minimal, deterministic partitioning — no LVM surprises
zerombr
clearpart --all --initlabel
part /boot --fstype=xfs --size=1024
part swap --size=8192
part / --fstype=xfs --size=1 --grow

# Register in Cobbler/Foreman or just enroll into Ansible inventory
%post --log=/root/ks-post.log
useradd -m -G wheel clusteradmin
echo "clusteradmin ALL=(ALL) NOPASSWD:ALL" > /etc/sudoers.d/clusteradmin
curl -fsSL http://mgmt01/bootstrap/enroll.sh | bash -s -- "$(hostname)"
%end

reboot

If you want faster, more consistent installs at scale, use Packer to build a golden image (disk image or container-style rootfs) with the base packages, agents, and even MLNX_OFED pre-baked, so kickstart just lays the image down instead of running a full package install every time. This is the closest roll-your-own gets to Warewulf's stateless-image model, but entirely optional — most small clusters skip it and just run kickstart + Ansible fresh each time.

Step 2 — Inventory design (group nodes by role)

Ansible's inventory is the map of the cluster: which hosts exist, and which groups (login/compute/storage/controller) they belong to. Group-based variables are how you say "all compute nodes get GPU drivers" or "only the controller gets slurmctld" without repeating yourself per host.

# inventory/production/hosts.yml
all:
  children:
    slurm_controller:
      hosts:
        ctrl01.cluster.local:
    slurm_login:
      hosts:
        login01.cluster.local:
        login02.cluster.local:
    slurm_compute:
      hosts:
        gpu[001:032].cluster.local:
      vars:
        has_gpu: true
        ib_hca: mlx5_0
    storage:
      hosts:
        nfs01.cluster.local:
        nfs02.cluster.local:
    cluster:
      children:
        slurm_controller:
        slurm_login:
        slurm_compute:
        storage:
      vars:
        munge_key_path: /etc/munge/munge.key
        slurm_cluster_name: rndcluster
        ntp_servers: [ntp01.cluster.local]
        domain: cluster.local

Keep host ranges (gpu[001:032]) rather than 32 individual lines — it's the difference between an inventory you can review in a code review and one nobody reads. Split into inventory/production and inventory/staging directories so a small test rack can validate role changes before they touch the real fleet.

Step 3 — Common roles: NTP, DNS, users, drivers

Every node, regardless of role, needs the same baseline: time sync (Slurm and munge are both sensitive to clock skew), consistent DNS/hosts resolution, the same admin users and SSH keys, and — for GPU/IB nodes — the NVIDIA driver and MLNX_OFED (or DOCA-OFED, its successor) InfiniBand/RoCE stack. This is where a roll-your-own stack does the work BCM/Warewulf would otherwise do for you via their image/driver management.

# roles/common/tasks/main.yml
- name: Install baseline packages
  ansible.builtin.package:
    name: [chrony, tuned, vim, tmux, python3]
    state: present

- name: Configure chrony NTP servers
  ansible.builtin.template:
    src: chrony.conf.j2
    dest: /etc/chrony.conf
  notify: restart chronyd

- name: Create cluster admin users
  ansible.builtin.user:
    name: "{{ item.name }}"
    groups: wheel
    shell: /bin/bash
  loop: "{{ cluster_admins }}"

# roles/mlnx_ofed/tasks/main.yml  (compute + login + storage nodes with IB/RoCE)
- name: Download MLNX_OFED ISO
  ansible.builtin.get_url:
    url: "{{ mlnx_ofed_iso_url }}"
    dest: "/tmp/MLNX_OFED-{{ mlnx_ofed_version }}.iso"
    checksum: "sha256:{{ mlnx_ofed_sha256 }}"

- name: Mount ISO and run mlnxofedinstall
  ansible.builtin.shell: |
    mount -o loop /tmp/MLNX_OFED-{{ mlnx_ofed_version }}.iso /mnt/ofed
    /mnt/ofed/mlnxofedinstall --add-kernel-support --without-fw-update -q
  args:
    creates: /usr/bin/ibstat
  notify: reboot node

- name: Install NVIDIA GPU driver (compute nodes only)
  ansible.builtin.include_role:
    name: nvidia_driver
  when: has_gpu | default(false)
Watch for
MLNX_OFED (and its successor DOCA-OFED) must match the running kernel exactly — a kernel update via yum update without rebuilding OFED kernel modules is the single most common way roll-your-own IB clusters silently break. Pin kernel versions in the common role and rebuild/reinstall OFED whenever the kernel bumps, ideally via a CI job rather than manually.

Step 4 — Slurm controller, slurmd, and munge key distribution

Munge provides the shared-secret authentication between the Slurm controller and every compute node — every host needs the exact same munge.key, generated once and distributed securely (Ansible Vault, not plaintext in git). Slurm itself splits into slurmctld (controller), slurmd (compute), and optionally slurmdbd (accounting database) — each gets installed and started by role, driven by the inventory groups from Step 2.

# playbooks/site.yml
- hosts: cluster
  become: true
  roles:
    - common
    - mlnx_ofed
    - munge

- hosts: slurm_compute
  become: true
  roles:
    - nvidia_driver
    - slurm_compute

- hosts: slurm_controller
  become: true
  roles:
    - slurm_controller

---
# roles/munge/tasks/main.yml
- name: Install munge
  ansible.builtin.package:
    name: munge
    state: present

- name: Distribute munge key (generated once, stored in Ansible Vault)
  ansible.builtin.copy:
    content: "{{ vault_munge_key }}"
    dest: /etc/munge/munge.key
    owner: munge
    group: munge
    mode: "0400"
  notify: restart munge

---
# roles/slurm_controller/tasks/main.yml
- name: Install slurm-slurmctld
  ansible.builtin.package:
    name: [slurm-slurmctld, slurm-slurmdbd]
    state: present

- name: Deploy slurm.conf from inventory-driven template
  ansible.builtin.template:
    src: slurm.conf.j2
    dest: /etc/slurm/slurm.conf
  notify: restart slurmctld

# slurm.conf.j2 excerpt — node/partition lines built from inventory
{% for host in groups['slurm_compute'] %}
NodeName={{ host }} CPUs=64 Gres=gpu:8 State=UNKNOWN
{% endfor %}
PartitionName=gpu Nodes={{ groups['slurm_compute'] | join(',') }} Default=YES MaxTime=INFINITE State=UP

Notice the last block: slurm.conf is templated directly from the Ansible inventory, so adding a new compute node is a one-line inventory change plus a re-run of the playbook — the same mechanism BCM or Warewulf give you through their node-group abstraction, just built from primitives you own.

Step 5 — Idempotency and drift management

The entire value proposition of Ansible collapses if playbooks aren't idempotent — running ansible-playbook site.yml twice in a row should report zero changes the second time. Drift (a node manually patched at 2am during an incident, and never reconciled back into the playbook) is the single biggest operational risk of roll-your-own: there's no CM-tool dashboard flagging "this node doesn't match the golden image."

  • Run the full playbook against the fleet on a schedule (nightly or weekly), not just on provisioning day — this is your drift detector. A run with non-zero "changed" tasks against a node nobody touched deliberately is a signal worth investigating.
  • Use --check --diff mode in CI or a cron job to report drift without applying it, then alert if diff count exceeds a threshold.
  • Treat manual SSH changes on production nodes as an incident-only escape hatch, and follow up by codifying the fix into the role within the same week — otherwise the playbook and reality permanently diverge.
  • Pin package versions (Slurm, munge, OFED, GPU driver) explicitly in role variables rather than "latest," so a re-run doesn't silently upgrade something mid-semester.

Step 6 — CI/CD for cluster configuration

Because the whole cluster definition is just YAML in git, it gets the same review discipline as application code: pull requests, linting, and automated testing before anything touches real hardware.

# .gitlab-ci.yml
stages: [lint, test, deploy]

lint:
  stage: lint
  script:
    - ansible-lint playbooks/ roles/
    - yamllint inventory/

molecule-test:
  stage: test
  script:
    - cd roles/slurm_compute
    - molecule test   # spins up a Docker/Podman instance, converges the role, verifies idempotence

deploy-staging:
  stage: deploy
  script:
    - ansible-playbook -i inventory/staging playbooks/site.yml --diff
  environment: staging
  only: [main]

deploy-production:
  stage: deploy
  script:
    - ansible-playbook -i inventory/production playbooks/site.yml --diff
  when: manual
  only: [main]

Molecule tests a role in isolation (spin up a throwaway container, converge, assert idempotence, tear down) — it catches broken roles before they ever run against a real compute node. ansible-lint catches style and correctness issues (deprecated modules, missing handlers, unpinned versions) at PR time. Gate production deploys behind a manual approval step; staging can auto-deploy on merge to catch problems on a small test rack first.

Roll-your-own vs. BCM / xCAT / Warewulf

DimensionAnsible + kickstart (roll-your-own)BCM / xCAT / Warewulf
CostFree (open-source tooling only)BCM: paid license per node; xCAT/Warewulf: free but still a full platform to run
Time to first clusterSlower — you assemble the pieces yourselfFaster — provisioning + image management pre-integrated
FlexibilityTotal — every piece is a normal Linux tool you already knowBounded by the tool's abstractions and supported OS/driver matrix
Vendor lock-inNoneSome (BCM proprietary config format; xCAT/Warewulf communities are smaller)
Drift managementManual discipline (scheduled playbook runs, --check mode)Built-in via stateless/golden images (Warewulf) or image sync (BCM)
SupportCommunity / your own teamBCM: vendor support contract; xCAT/Warewulf: community
Best fitSmall-to-mid clusters, cloud/bare-metal hybrid, teams with existing Ansible skillLarger clusters, teams wanting a supported turnkey platform
Rule of thumb
If your team already runs Ansible for everything else and the cluster is under a few hundred nodes, roll-your-own is usually the lower total-cost path — you're reusing skills and tooling you already maintain. Past a few hundred nodes, or if the team has no dedicated Linux/Ansible ops capacity, the integrated CM tools start paying for themselves in reduced day-2 toil.
