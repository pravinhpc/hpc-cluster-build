15 — CSP Build: AWS

Everything in this guide so far has assumed you own the racks. If you're building your GPU cluster on AWS instead, the physical layer disappears and is replaced by three things you configure through APIs: the right GPU instance type, a low-latency RDMA-capable network fabric called EFA, and an orchestration tool — AWS ParallelCluster — that plays the same role BCM, xCAT, or Warewulf played in the on-prem guides. This page walks through all three, plus the storage and networking building blocks a real build needs.

GPU instance types

AWS's GPU compute lineup for large-scale training and HPC centers on the P-series, with Trn-series as a non-NVIDIA alternative for specific workloads:

  • P5 — 8× NVIDIA H100 GPUs (80GB HBM3 each, 640GB total), NVSwitch-connected for 900GB/s GPU-to-GPU bandwidth, 3rd Gen AMD EPYC CPUs, 2TB system memory, up to 3200Gbps EFA networking. This is the default choice for large H100 training clusters on AWS.
  • P5e / P5en — the H200 refresh: 8× H200 GPUs with 1.7x the memory and 1.4x the memory bandwidth of H100, paired with 4th Gen Intel Xeon CPUs (P5en) for Gen5 PCIe CPU↔GPU bandwidth and a newer EFA/Nitro generation with lower latency.
  • P4d / P4de — the previous generation: 8× NVIDIA A100 GPUs (40GB on P4d, 80GB on P4de), still widely used for cost-sensitive training and inference workloads that don't need H100/H200-class throughput.
  • Trn1 / Trn2 — AWS's own Trainium accelerators, relevant if your workload targets AWS's Neuron SDK rather than CUDA. Mentioned here for completeness; this guide's tooling (Slurm, EFA, ParallelCluster) applies to Trainium instances too, but the software stack above the network layer is different from an NVIDIA GPU cluster and is out of scope for this page.

EFA — AWS's RDMA fabric

Elastic Fabric Adapter (EFA) is AWS's answer to InfiniBand: a network interface that supports OS-bypass, low-latency communication using the Scalable Reliable Datagram (SRD) protocol, layered under standard MPI/NCCL libraries via libfabric. On P4d and later GPU instances, EFA also supports NVIDIA GPUDirect RDMA, letting the NIC read and write GPU memory directly without staging through host memory — the same fundamental optimization that InfiniBand-with-GPUDirect provides on-prem. For multi-node NCCL collective communication (all-reduce during distributed training), EFA is what makes AWS GPU instances usable at scale instead of falling back to slow TCP/IP over the standard ENA network interface.

Two things matter operationally: EFA is only available on specific instance types and sizes (the full P5/P4d family qualifies), and it only reaches full performance when instances are launched into a cluster placement group — a placement strategy that packs instances close together on the physical network to minimize inter-node latency. ParallelCluster handles both automatically when EFA is enabled in the config.

AWS ParallelCluster

AWS ParallelCluster is AWS's open-source, AWS-supported cluster deployment tool — the direct AWS-native equivalent of BCM or Warewulf from earlier in this guide. Instead of provisioning bare metal, it provisions AWS resources: it reads a YAML config file describing your desired cluster, then uses AWS CloudFormation under the hood to stand up a VPC-attached head node, an auto-scaling compute fleet, a Slurm controller and workload manager configuration, and optional shared storage — all from one pcluster create-cluster command.

At a high level, a ParallelCluster cluster has:

  • A head node — runs Slurm's controller (slurmctld), the ParallelCluster agent, and typically serves as the login/submission node.
  • One or more compute fleets (queues) — Slurm partitions backed by EC2 Auto Scaling groups, each mapped to a specific instance type (e.g. a gpu queue on P5, a cpu queue on general-purpose instances). Nodes scale from zero and terminate when idle, so you only pay for GPU time actually used.
  • Shared storage — typically FSx for Lustre for scratch/training data, mounted on every node.
  • Networking — a VPC, subnets, and (for the GPU queue) EFA + cluster placement group configuration.

FSx for Lustre — parallel storage

Amazon FSx for Lustre is AWS's managed parallel file system — the cloud equivalent of the Lustre or GPFS storage covered in guide 03. It's built for exactly the profile a GPU training job needs: high aggregate throughput (terabytes per second at scale), high IOPS, and the ability to mount the same namespace across thousands of compute nodes concurrently. It can also link directly to an S3 bucket, transparently presenting S3 objects as files and syncing writes back, which makes it convenient for training jobs that read datasets staged in S3. ParallelCluster can create a new FSx for Lustre file system as part of cluster creation, or attach an existing one.

VPC and networking design

A minimal but realistic AWS cluster VPC has: one VPC, a private subnet for compute and head nodes (GPU instances generally shouldn't have public IPs), a public subnet with a NAT gateway for outbound package/container pulls, and security groups scoped so cluster-internal traffic (Slurm, NFS/Lustre, EFA) is allowed between cluster nodes but nothing is open to the internet inbound. The GPU compute subnet should be placed in a single Availability Zone — cluster placement groups and EFA both require this, since spreading GPU nodes across AZs breaks the low-latency guarantee the fabric depends on.

IAM roles

ParallelCluster needs IAM permissions at two levels: the identity running pcluster commands needs broad permissions to create the CloudFormation stack, VPC resources, EC2 instances, and IAM roles themselves; and the cluster's EC2 instances need an instance role (attached automatically by ParallelCluster) granting the head and compute nodes permission to call EC2 (for Slurm's dynamic scaling), CloudWatch (for logging), and S3/FSx as needed for storage access. Production deployments typically scope both down from the AWS-managed policy ParallelCluster ships with to a tighter, reviewed policy.

Step-by-step: building a cluster with ParallelCluster

Step 1 — Install and configure the CLI

pip install aws-parallelcluster, then run pcluster configure for an interactive wizard, or hand-write the config YAML directly (shown below). You'll need an existing VPC and subnets, or let the wizard create them.

Step 2 — Write the cluster config

A realistic minimal GPU training cluster config looks like this:

Region: us-east-1
Image:
  Os: alinux2

HeadNode:
  InstanceType: c5.2xlarge
  Networking:
    SubnetId: subnet-0a1b2c3d4e5f6g7h8
  Ssh:
    KeyName: my-cluster-keypair

Scheduling:
  Scheduler: slurm
  SlurmQueues:
    - Name: gpu
      ComputeResources:
        - Name: p5-48xlarge
          InstanceType: p5.48xlarge
          MinCount: 0
          MaxCount: 32
          Efa:
            Enabled: true
      Networking:
        SubnetIds:
          - subnet-0a1b2c3d4e5f6g7h8
        PlacementGroup:
          Enabled: true

SharedStorage:
  - MountDir: /fsx
    Name: fsx-scratch
    StorageType: FsxLustre
    FsxLustreSettings:
      StorageCapacity: 4800
      DeploymentType: SCRATCH_2

Step 3 — Create the cluster

pcluster create-cluster --cluster-name gpu-train-01 --cluster-configuration cluster-config.yaml. ParallelCluster translates the config into a CloudFormation template and deploys it — this creates the head node, Slurm configuration, FSx file system, and Auto Scaling group for the gpu queue, typically in 10-15 minutes.

Step 4 — Connect and submit jobs

pcluster ssh --cluster-name gpu-train-01 -i my-key.pem logs into the head node, where a standard Slurm environment is waiting: sinfo shows the gpu partition, and sbatch/srun work exactly as they do on an on-prem Slurm cluster. Requesting nodes triggers the Auto Scaling group to launch P5 instances, which join the fleet and pick up the job once EFA and NCCL are confirmed healthy.
