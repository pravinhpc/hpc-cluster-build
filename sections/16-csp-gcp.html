16 — CSP Build: Google Cloud (GCP)

Everything earlier in this guide assumed you own the racks. Google Cloud gives you a different path to the same end state — a Slurm-scheduled fleet of GPU nodes with a fast interconnect and shared storage — where the "racking and cabling" step is replaced by API calls and a YAML file. This section covers the GPU instance families GCP offers, the GPUDirect-TCPX/TCPXO networking stack that stands in for InfiniBand, and Cluster Toolkit, Google's purpose-built tool for standing up an HPC/AI cluster on top of it.

GPU instance families

GCP's accelerator-optimized machine family maps roughly onto three generations of NVIDIA GPU:

  • A2 — NVIDIA A100 GPUs (40GB or 80GB variants), the oldest of the three families still in active use for training and inference workloads that don't need the newer interconnect.
  • A3 family — NVIDIA H100 GPUs, split into several machine types with different networking capability: a3-highgpu-8g and a3-edgegpu-8g (8× H100, GPUDirect-TCPX), and a3-megagpu-8g (8× H100, higher-bandwidth NICs, GPUDirect-TCPXO). There is also an A3 Ultra tier built around H200 GPUs with RDMA-capable networking.
  • A4 — NVIDIA B200 GPUs, GCP's current-generation Blackwell offering, using GPUDirect-RDMA rather than the TCPX variants. A GB200 NVL72-based tier (A4X / A4X Max) also exists for the largest training jobs.

The practical decision usually comes down to what your framework and interconnect requirements are: A2 is the cheapest entry point if you're on A100-class workloads already, A3 Mega is the common choice for large-scale H100 training where NCCL bandwidth actually matters, and A4 is where you land if you need B200/Blackwell-class compute and are willing to work within GCP's current regional capacity constraints.

GPUDirect-TCPX / TCPXO: GCP's RDMA-like fabric

Bare-metal HPC clusters use InfiniBand or RoCE with true RDMA to let GPUs on different nodes exchange data without involving the host CPU. GCP's A3 VMs are virtualized and don't expose raw RDMA hardware to the guest, so Google built GPUDirect-TCPX (and its successor GPUDirect-TCPXO) as a software-offloaded networking stack that gets most of the same benefit over standard Ethernet NICs:

  • GPUDirect-TCPX — used on a3-highgpu-8g and a3-edgegpu-8g. An optimized TCP path that reduces CPU involvement and latency compared to vanilla TCP, using a userspace networking layer alongside the standard NIC driver.
  • GPUDirect-TCPXO — used on a3-megagpu-8g, GCP's newer, more fully offloaded evolution of the same idea, paired with higher-bandwidth NICs, and generally what you want for large multi-node NCCL collectives.
  • GPUDirect RDMA — the A4 (B200) generation moves to genuine RDMA-based GPUDirect rather than a TCP-offload variant, closer in spirit to on-prem RoCE.

In practice this stack is not something you hand-roll: both GKE and Cluster Toolkit ship pre-built modules, NCCL plugins, and receive-side-scaling configuration that wire GPUDirect-TCPX/TCPXO up correctly for you, because the setup — extra NICs, specific driver versions, NCCL plugin versions that must match — is fiddly enough that getting it wrong silently degrades your collective bandwidth rather than failing outright.

GCP Cluster Toolkit

Cluster Toolkit (formerly Cloud HPC Toolkit) is Google's open-source tool for building GCP HPC/AI clusters from a declarative blueprint, analogous to how this guide uses BCM, xCAT, or Warewulf on bare metal. It's built on top of Terraform and Packer: you write a YAML "blueprint" describing the network, storage, and compute you want, and the toolkit's gcluster CLI expands that blueprint into Terraform modules and deploys them.

A blueprint is organized around a small set of concepts:

  • Deployment groups — ordered stages of the deployment (e.g. network first, then storage, then the Slurm cluster itself), each backed by its own Terraform state.
  • Modules — reusable building blocks (a VPC, a Filestore instance, a Slurm login node, a Slurm nodeset/partition) that Google maintains in the Cluster Toolkit repository and that you reference and configure with variables.
  • Variables and outputs — modules pass values to each other (a network module's output feeds into the compute module's input), so the blueprint reads like a wiring diagram rather than a flat parameter list.

Under the hood, Cluster Toolkit's Slurm modules deploy the Slurm on Google Cloud scheduler integration, which uses a controller VM plus dynamically-provisioned (or statically-reserved) compute nodesets — so GPU nodes can either stay running for a reservation-backed cluster or spin up and down per job via GCP's autoscaling APIs.

Storage: Filestore and Parallelstore

GCP offers two managed file storage options that show up constantly in Cluster Toolkit blueprints:

  • Filestore — managed NFS, the default choice for home directories, shared scripts, and general-purpose shared storage. Simple to provision and mount, but its throughput ceiling is well below what large multi-node GPU training jobs need for dataset I/O.
  • Parallelstore — a managed parallel file system (built on DAOS) purpose-built for HPC/AI throughput, striping data across multiple storage servers so aggregate bandwidth scales with capacity — hundreds of GB/s is achievable, versus the much lower ceiling on Filestore or Cloud Storage FUSE.

The common pattern: Filestore for /home and configuration, Parallelstore (or Cloud Storage with FUSE/hierarchical namespace, for read-heavy checkpoint/dataset access) for the actual training data path.

Networking and IAM basics

A Cluster Toolkit deployment needs a VPC with subnets for the control plane and — on A3/A4 machine types — additional subnets dedicated to the GPUDirect-TCPX/TCPXO NICs (these machine types attach multiple NICs per VM specifically for the offloaded networking path). Firewall rules need to permit intra-cluster traffic on the compute subnet(s) and the outbound access your nodes need for package installs, container pulls, and license servers. On the identity side, the deployment uses a dedicated service account with the IAM roles Cluster Toolkit's modules require (Compute Admin-equivalent permissions, Filestore/Parallelstore admin, and Cloud Storage access for images/state) — scoped to a project rather than granted broadly, same as any production cloud deployment.

Step-by-step: building a Slurm cluster with Cluster Toolkit

Step 1 — Install Cluster Toolkit and set up the project

Clone the cluster-toolkit repository, build the gcluster binary (Go-based), and authenticate to your GCP project with gcloud auth application-default login. Enable the required APIs (Compute Engine, Filestore, Parallelstore if used, IAM) on the target project.

Step 2 — Write or adapt a blueprint

Google publishes ready-made example blueprints for common shapes (A3 Mega, A3 Ultra, A3 High Slurm clusters) that you copy and adjust rather than writing from scratch. A minimal GPU-cluster blueprint looks like this:

blueprint_name: gcp-a3mega-slurm

vars:
  project_id: my-gcp-project
  deployment_name: a3mega-cluster
  region: us-central1
  zone: us-central1-a

deployment_groups:
- group: primary
  modules:
  - id: network
    source: modules/network/vpc

  - id: gpunets
    source: modules/network/multivpc
    settings:
      network_count: 8

  - id: homefs
    source: modules/file-system/filestore-instance
    use: [network]
    settings:
      local_mount: /home

  - id: a3mega_nodeset
    source: community/modules/compute/schedmd-slurm-gcp-v6-nodeset
    use: [network, gpunets]
    settings:
      machine_type: a3-megagpu-8g
      node_count_static: 8
      bandwidth_tier: gvnic_enabled

  - id: a3mega_partition
    source: community/modules/compute/schedmd-slurm-gcp-v6-partition
    use: [a3mega_nodeset]
    settings:
      partition_name: a3mega

  - id: slurm_controller
    source: community/modules/scheduler/schedmd-slurm-gcp-v6-controller
    use: [network, a3mega_partition, homefs]

Step 3 — Deploy

Create a deployment variable file, then run gcluster deploy pointing at both files:

gcluster deploy -d a3mega-deployment.yaml gcp-a3mega-slurm.yaml --auto-approve

Cluster Toolkit expands the blueprint into Terraform, applies each deployment group in order, and reports progress; a Slurm cluster of this shape typically takes on the order of 30-40 minutes end to end, most of it in image and node provisioning.

Step 4 — Verify and submit a job

SSH to the login/controller node, confirm nodes are visible with sinfo, and submit a small GPU job with srun/sbatch to confirm scheduling and GPUDirect-TCPXO are working before scaling up dataset size or job count.
