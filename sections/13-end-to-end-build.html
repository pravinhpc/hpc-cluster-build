13 — Full End-to-End Build Walkthrough: Day 0 to Day N

Every section so far has looked at one layer of the stack in isolation — compute, fabric, storage, provisioning, identity, scheduling, monitoring. This capstone section puts it all back together as one continuous story: an empty rack on Day 0, a room full of idle GPUs by Day 3, and a production cluster with real researchers running real jobs by Day 12. Think of it as the "project plan" version of everything you've read — the order things happen in, why that order matters, and the checkpoints that tell you it's safe to move to the next phase.

How to use this section
Each phase below links back to the deep-dive section that covers it in full technical detail. This page is deliberately the "zoomed out" view — read it first to understand the shape of a build, then dive into the linked sections for the how.

The Whole Build in One Picture

Before the phase-by-phase walkthrough, here's the timeline end to end. Real builds compress or stretch these numbers depending on cluster size (dozens of nodes vs. thousands) and how much of the hardware supply chain is already sitting in the datacenter, but the order of phases is remarkably constant across every HPC/AI cluster build, from a 32-GPU department cluster to a multi-thousand-GPU supercomputer.

Day -30 to 0: Planning

Goal: turn "we need to train/run inference on model X at scale Y" into a purchase order, a rack elevation, and a network topology diagram.

  1. Workload requirements. What's the primary job type — dense LLM pre-training, fine-tuning, batch inference, mixed HPC simulation? This decides GPU generation, interconnect requirements, and memory footprint. See 01 — Compute Hardware.
  2. Hardware sizing. Translate workload into GPU count, node count, CPU/host memory ratio, and local NVMe scratch per node.
  3. Topology design. Pick rail-optimized vs. non-blocking fat-tree, decide leaf/spine counts, and settle InfiniBand vs. RoCE for both the compute fabric and the storage/management fabric. See 02 — Networking & Fabric.
  4. Storage sizing. Capacity (raw dataset + checkpoints + scratch) and required aggregate throughput, sized against the largest expected checkpoint-write burst. See 03 — Storage.
  5. Vendor procurement. Lead times for GPU nodes, switches, optics/DAC cables, and PDUs are frequently the longest pole in the schedule — order 8-16 weeks out depending on GPU generation availability.
  6. Site readiness. Confirm rack space, power (kW/rack budget — modern 8-GPU nodes can pull 10-12kW each), and cooling (air vs. liquid/direct-to-chip) are provisioned before hardware arrives. A rack of GPU nodes sitting on a loading dock waiting for power commissioning is the single most common schedule slip in real builds.

Day 0-1: Physical Install & Cabling

  • Rack the nodes. Follow the vendor rack elevation exactly — GPU trays, weight distribution, and airflow direction are not arbitrary.
  • Cable the compute fabric. Wire every GPU's NIC to its designated leaf switch port per the rail design — rail-aligned cabling (all "rail 0" NICs across every node go to the same leaf) is what makes the fat-tree non-blocking. Mistakes here are the hardest class of bug to find later, because the fabric "mostly works" but has silently degraded bisection bandwidth. See 02 — Networking & Fabric.
  • Cable the management/storage network. Separate physical (or at minimum, separate VLAN) network for provisioning, BMC, and storage traffic so a compute-fabric problem can never take down your ability to reach a node's console.
  • BMC / out-of-band setup. Assign static IPs (or DHCP reservations keyed to MAC) to every node's BMC, verify IPMI/Redfish reachability, and record serials against rack-unit position — this inventory becomes the seed data for your provisioning tool's node definitions in the very next phase.
Field note
Do a full continuity/link-up sweep before powering on compute — walk the switch port list and confirm every expected link comes up at full speed before you start racing to install software. A single bad transceiver found on Day 5 during fabric diagnostics costs you a re-cabling detour mid-schedule; found on Day 1 it costs you five minutes.

Day 1-3: Head Node + Provisioning Tool Bring-Up

This is the first real software decision of the build, and it shapes almost everything downstream — how nodes get their OS, how config drifts get corrected, how a failed node gets reimaged at 2am. Four credible paths were covered in depth earlier in this guide:

Base Command Manager (BCM)

reference:
Commercial, NVIDIA-supported, deeply integrated with DGX/GPU stacks. Fastest path to a working cluster if budget allows.

xCAT

Mature, open-source, extremely flexible, IBM/HPC lineage. Steeper learning curve, large install base in national labs.

Warewulf + OpenHPC

Lightweight stateless-node provisioning paired with a curated open-source HPC software stack. Good middle ground for smaller teams.

Bare-metal Ansible

No dedicated provisioning daemon — PXE/kickstart plus Ansible playbooks. Maximum control and transparency, maximum DIY burden.

Whichever tool wins, the Day 1-3 bring-up sequence is the same shape: install the provisioning service on the head node(s), define node profiles (OS image, kernel args, disk layout, driver/CUDA version), register every node's BMC/MAC from the Day 0-1 inventory, and get the head node itself hardened, backed up, and — ideally — deployed in an HA pair before it becomes the single point of failure for the whole fleet.

Day 3-5: Bulk Node Provisioning + Fabric Validation

  1. PXE boot the fleet. Power on all compute nodes, let them PXE into the provisioning tool, and image them in parallel (all four tools above support fleet-wide parallel imaging — this is where the tool choice starts paying off or costing you).
  2. Fabric diagnostics. Run ibdiagnet (InfiniBand) or the RoCE-equivalent link/ECN/PFC counters sweep across every port. Confirm no unreachable nodes, no port flaps, no link running below negotiated speed, and correct subnet-manager convergence.
  3. NCCL bandwidth tests. Run nccl-tests (all_reduce_perf, all_gather_perf) first within a node (NVLink), then across 2 nodes, then across a full rack, then full fleet. Compare measured busbw against the theoretical rail bandwidth from 02 — Networking & Fabric — a gap of more than ~10-15% at scale usually means a cabling, routing, or congestion-control misconfiguration, not a "that's just overhead" situation.

Day 5-7: Storage Integration

Mount the parallel filesystem (Lustre, GPFS/Spectrum Scale, WEKA, VAST, etc. — see 03 — Storage) on every compute node via the storage-side fabric, then validate before trusting it with real data:

  • Single-client and aggregate multi-client throughput tests (e.g. ior, fio) against the sizing target from the planning phase.
  • Metadata-heavy workload test (many small files) if the workload includes dataset shards or checkpoint sub-files.
  • Checkpoint-burst simulation — write a checkpoint-sized file from every node simultaneously and confirm the filesystem sustains it without falling over; this is the single most common storage failure mode in production LLM training.

Day 7-9: Identity Stack + Scheduler Bring-Up

  1. Stand up LDAP as the directory of record (09 — Identity: LDAP), and SSSD on every compute node for the LDAP-to-local-account bridge, caching, and offline resilience (10 — Identity: SSSD).
  2. Install and configure Slurm (08 — Scheduling) — controller, database, and slurmd fleet-wide, with partitions matching your rack/rail topology so job placement respects fabric locality.
  3. Validate with a full-fleet test job: submit an MPI/NCCL job that spans every node in the cluster. This is the true "is this cluster real" moment — it proves scheduler, fabric, storage, and identity are all working together, not just individually.

Day 9-10: Monitoring Stack + Alerting Live

Deploy DCGM exporters on every node, Prometheus to scrape them (plus node/switch/fabric exporters), and Grafana dashboards for GPU utilization, XID errors, thermal/power, and job-level metrics (12 — Monitoring & Observability). Wire alerting (Alertmanager or equivalent) for the handful of signals that actually predict trouble: ECC errors climbing, XID codes indicating Xid 79/94/etc., NVLink/fabric link flaps, and node-down. Alerting should be live before real users land — you want to catch a bad node from telemetry, not from a frustrated Slack message.

Day 10-12: User Onboarding Pipeline Live

Wire the onboarding chain end to end (11 — Onboarding via DLs): distribution-list membership change → identity account provisioned → Slurm association/QOS assigned → user notified with quick-start docs. Bring a small set of pilot users through the full pipeline first, and have them run a real (small) job before opening the gates. A day-1 checklist for each pilot user typically covers:

Day 12+: Steady-State Operations

The build is "done," but the cluster's life has just started. Ongoing operational cadence includes:

  • Patching cadence. Scheduled maintenance windows for OS/driver/firmware updates, staged through a canary partition before fleet-wide rollout.
  • Node health checks & draining. Automated health checks (NHC-style) gate nodes out of the scheduler on ECC/XID/thermal anomalies before they corrupt a job; drained nodes flow into a repair queue.
  • Capacity planning. Track utilization and queue wait times against growth projections to time the next hardware order — this loops back to Day -30 planning for the next expansion.
  • Incident response. On-call rotation, runbooks per failure class (fabric link down, storage degraded, scheduler controller failover), and postmortems that feed back into the health-check ruleset.

Simulation: A Worked Capacity-Planning Example

Here's a concrete, simplified example of the kind of math that drives the "hardware sizing" step back in the Day -30 planning phase — and that gets validated for real during the Day 3-5 NCCL tests.

Scenario: Train a model requiring 4 × 1021 total FLOPs on a cluster of 128 GPUs, each capable of ~989 TFLOPS dense BF16 (H100-class peak), and assume a realistic sustained model-FLOPs-utilization (MFU) of 40% once framework/communication overhead is accounted for.

Per-GPU sustained throughput = 989 TFLOPS × 0.40
                              = 395.6 TFLOPS/s effective

Cluster sustained throughput = 395.6 TFLOPS/s × 128 GPUs
                              = 50,637 TFLOPS/s  (≈ 50.6 PFLOPS/s)

Wall-clock time = Total FLOPs / Cluster sustained throughput
                = 4 × 10^21 FLOPs / 5.06 × 10^16 FLOPs/s
                = 79,051 seconds
                ≈ 21.96 hours  (~22 hours)

Now the network side: assume a data-parallel + tensor-parallel job where each all-reduce step exchanges a gradient tensor of 2 GB per GPU per step, and the training recipe runs one optimizer step roughly every 4 seconds at this scale.

Required sustained per-GPU network bandwidth
  = 2 GB / 4 s
  = 0.5 GB/s  = 4 Gb/s  minimum, per direction, sustained

Real fabrics are provisioned well above the minimum to absorb
all-reduce ring/tree overhead and keep communication from
becoming the bottleneck — a rail design offering 400 Gb/s per
GPU (e.g. NDR InfiniBand or 400G RoCE) leaves ~100x headroom
over this minimum, which is why "just barely enough" bandwidth
sizing is a common cause of GPUs sitting idle waiting on
all-reduce instead of computing.
