21 — IaC: Ansible as a Full-Stack Cluster Configuration-Management Solution

Elsewhere in this guide, section 07 uses Ansible narrowly — as the glue between a kickstart file and a working bare-metal node. This section is the broader picture: Ansible as the day-1-through-day-2 configuration-management layer across an entire HPC cluster, cloud or on-prem, sitting on top of whatever provisioned the infrastructure in the first place (usually Terraform). Same tool, much bigger job — full role structure, dynamic inventory pulled live from a cloud API instead of a static file, secrets management, and the monitoring stack, all driven by one set of playbooks.

Where Ansible sits in the stack

Terraform (or a cloud-native equivalent) answers "what infrastructure exists" — VPCs, subnets, VM/instance groups, load balancers, storage volumes, IAM roles. Ansible answers "what's running on top of it" — packages, users, drivers, services, configuration files, and their desired running state. The division of labor matters: Terraform is declarative over infrastructure resources with state tracking; Ansible is procedural over running hosts with no persistent state of its own — it re-derives what needs to change each run by comparing the target state in a playbook against whatever it finds on the host. Neither tool does the other's job well, and trying to make Terraform manage OS-level configuration (or Ansible manage cloud resource lifecycles) usually ends in something more fragile than just using both together.

Rule of thumb
If a change means creating, resizing, or destroying a cloud resource, it's Terraform's job. If a change means installing a package, editing a config file, or restarting a service on a host that already exists, it's Ansible's job. The handoff point is almost always "the instance boots and Ansible takes over from there."

A realistic role structure

A full-stack HPC cluster playbook set is organized as a handful of composable roles, each owning one concern, applied to different host groups:

RoleApplies toResponsibility
commonall nodesBase OS hardening, NTP/chrony, package repos, admin users, SSH keys
ldap-sssd-clientall nodesCentralized auth against LDAP/AD via SSSD, so login/compute nodes share one user directory
gpu-driversGPU nodesNVIDIA driver + CUDA toolkit install, pinned to a version compatible with the fleet's kernel
ib-rdma-driversGPU/high-BW nodesMLNX_OFED / DOCA-OFED InfiniBand or RoCE stack, matched to kernel version
mungecontroller + compute + loginShared-secret key distribution for Slurm authentication
slurm-controllercontroller node(s)slurmctld, slurmdbd, slurm.conf templated from inventory
slurm-computecompute nodesslurmd, gres.conf for GPU resources, cgroup config
nfs-clientcompute + loginMount shared home/scratch filesystems
monitoring-agentall nodesnode_exporter, DCGM exporter (GPU nodes), log shipper

Each role is independently testable and independently reusable — the same gpu-drivers role runs whether the node came from AWS, GCP, Azure, OCI, or bare metal, because it only cares about the running OS, not how the instance was created.

The key differentiator: dynamic inventory

Section 07's bare-metal approach uses a static inventory file — a fixed list of hostnames, hand-maintained in git. That works when nodes are physical and rarely change. It breaks down fast in a cloud-native, autoscaling, or spot-instance-heavy environment, where the set of live nodes changes hour to hour and a static file goes stale the moment anything scales.

The fix is a dynamic inventory plugin: instead of reading a file, Ansible queries the cloud provider's API at run time and builds the inventory from whatever is actually running, grouped automatically by tags.

# inventory/aws_ec2.yml — amazon.aws.aws_ec2 dynamic inventory plugin
plugin: amazon.aws.aws_ec2
regions:
  - us-east-1
filters:
  tag:Cluster: hpc-prod
  instance-state-name: running
keyed_groups:
  - key: tags.Role          # e.g. "compute", "login", "controller"
    prefix: role
  - key: tags.HasGPU
    prefix: gpu
compose:
  ansible_host: private_ip_address
cache: true
cache_plugin: jsonfile
cache_timeout: 300

Run ansible-inventory -i inventory/aws_ec2.yml --graph and Ansible groups hosts as role_compute, role_login, gpu_true, etc. — automatically, from tags, with no manual editing. Equivalent plugins exist for the other major clouds: google.cloud.gcp_compute for GCP, azure.azcollection.azure_rm for Azure, and openstack.cloud.openstack or vendor-specific plugins for OCI. Point a playbook at -i inventory/ (a directory) and Ansible merges multiple dynamic sources — useful for hybrid or multi-cloud clusters.

Watch for
Dynamic inventory results are cached by default (cache_timeout above) to avoid hammering the cloud API on every playbook run. During a rapid autoscale event, a stale cache means Ansible targets a node list that's already out of date. Set a short timeout for volatile environments, or force a refresh with --flush-cache before any run that must see live state.

Secrets: Ansible Vault

Munge keys, LDAP bind passwords, Grafana admin credentials, and API tokens for the monitoring stack all need to live in git without being readable in git. Ansible Vault encrypts variable files (or individual strings) with a shared password or a KMS-backed vault ID, and Ansible transparently decrypts them at run time.

# Encrypt a whole file of secrets
ansible-vault encrypt group_vars/all/vault.yml

# Encrypt a single string for inline use in a vars file
ansible-vault encrypt_string 'S3cr3t!' --name 'ldap_bind_password'

# Run a playbook, supplying the vault password
ansible-playbook site.yml --vault-id prod@prompt

Keep vault-encrypted files as normal git-tracked YAML (they diff and review fine as ciphertext blobs); keep the vault password itself out of git entirely — a password manager, a CI secret store, or a KMS-backed vault ID script.

A full end-to-end playbook

A realistic top-level playbook chains every role above in dependency order, targeting the dynamic-inventory groups:

# playbooks/site.yml
- hosts: all
  become: true
  roles:
    - common
    - ldap-sssd-client
    - monitoring-agent

- hosts: role_compute:role_login
  become: true
  roles:
    - ib-rdma-drivers
    - nfs-client
    - munge

- hosts: gpu_true
  become: true
  roles:
    - gpu-drivers

- hosts: role_controller
  become: true
  roles:
    - munge
    - slurm-controller

- hosts: role_compute
  become: true
  roles:
    - slurm-compute

Run it against live cloud state with:

ansible-playbook -i inventory/aws_ec2.yml playbooks/site.yml --diff

No hostnames are hardcoded anywhere — new compute nodes that appear (autoscaling, a manual Terraform apply, spot fleet churn) are picked up automatically the next time the dynamic inventory plugin queries the API, and the same playbook configures them without edits.

Monitoring as part of the same automation

The monitoring-agent role installs and configures the observability stack alongside everything else, rather than as a separate manual step:

  • node_exporter on every host — CPU, memory, disk, network metrics
  • DCGM exporter on GPU nodes — GPU utilization, memory, temperature, XID errors, ECC counts
  • Prometheus (typically on a dedicated monitoring host or controller) scraping both, service-discovering compute targets from the same dynamic inventory data
  • Grafana provisioned with dashboards-as-code (JSON dashboards checked into the same repo, applied via the Grafana provisioning API or an Ansible role)

Because the monitoring agents are installed by the same playbook run as everything else, a newly provisioned node is observable from the moment it joins the cluster — there's no separate onboarding step for monitoring to fall out of sync with compute.

Role/playbook architecture

Idempotency and Molecule testing

Same discipline as any other Ansible workload, at higher stakes because a full-stack cluster playbook touches the scheduler and the monitoring layer, not just the OS. Molecule tests each role in isolation — create a throwaway container, converge, assert zero changes on a second converge, verify, destroy — so a broken slurm-compute or monitoring-agent role is caught in CI, never against a live cluster.
