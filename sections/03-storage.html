03 — Storage: Parallel Filesystems and Data Tiers

A GPU cluster is only as fast as the data it can feed its GPUs. Once you've built a fast network fabric (see the previous section), the next bottleneck is almost always storage — specifically, how fast thousands of compute nodes can read, write, and checkpoint data at once without stepping on each other. This section explains why ordinary file servers fall over at HPC scale, how the major parallel filesystems solve that problem, and how to think about sizing storage for an AI training cluster.

Why a single file server isn't enough

Imagine a normal office file share: one server, one disk array, one network port, serving files to a few dozen laptops. That's roughly what NFS (Network File System) does, and it works fine at that scale. Now imagine 2,048 GPU nodes, each with 8 GPUs, all trying to read training data or write a multi-terabyte model checkpoint at the same moment. A single NFS server has one CPU, one set of disks, and one network link — it becomes a hard ceiling on throughput almost immediately, and every client queues up behind it.

HPC and AI clusters solve this with parallel filesystems: instead of one server owning all the data, the filesystem spreads both metadata (file names, permissions, directory structure) and file data across many independent servers and disks. A client can then talk to dozens or hundreds of servers simultaneously, so aggregate bandwidth and IOPS (I/O operations per second) scale roughly with the number of servers you add — not with the speed of any single machine.

Layman analogy
A single-server NFS share is like one checkout lane at a grocery store — everyone waits in one line no matter how many customers show up. A parallel filesystem is like opening 50 checkout lanes at once and telling each customer which lane has their items pre-sorted. The store (cluster) can now serve far more customers (nodes) per minute.

Lustre: the HPC standard

Lustre is the most widely deployed parallel filesystem in traditional HPC (and increasingly in AI training clusters). It splits its job into distinct roles:

Metadata side

  • MGS (Management Server) — holds cluster-wide configuration.
  • MDS (Metadata Server) — the node(s) that handle namespace operations: file/directory creation, permissions, "where are this file's chunks?"
  • MDT (Metadata Target) — the actual storage device (usually fast NVMe/SSD) backing an MDS, holding file names, directory trees, and layout pointers.

Data side

  • OSS (Object Storage Server) — the node(s) that actually move file data.
  • OST (Object Storage Target) — the disk array behind an OSS where file content objects physically live.
  • Client — runs on every compute node; talks to the MDS once to learn a file's layout, then talks directly and in parallel to every OSS that holds a piece of that file.

The key trick is striping: a large file isn't stored whole on one OST — it's chopped into stripes and spread across many OSTs. When a client reads that file, it pulls stripes from many OSS nodes at once, so a single file's read speed can exceed what any one server or disk could deliver alone. A Lustre filesystem typically has one (or a few) MDS but many OSS nodes — the OSS/OST layer is where you buy bandwidth by adding servers.

Field note
Lustre performance planning is mostly about counting OSTs. Need 1 TB/s of aggregate read bandwidth? Figure out what one OSS/OST pair can sustain (often 5–20 GB/s with modern NVMe JBOFs), then divide. MDS sizing matters separately — small-file-heavy workloads (millions of tiny files) stress the MDT and often push HPC sites toward all-flash MDTs or DNE (Distributed Namespace) with multiple MDS nodes.

IBM Spectrum Scale (GPFS)

IBM Spectrum Scale — still widely known by its original name, GPFS (General Parallel File System) — takes a similar "spread the work across many servers" approach but with a different internal design philosophy. Rather than Lustre's clean split of dedicated metadata vs. object servers, GPFS uses NSD (Network Shared Disk) servers that can serve both data and metadata, and it relies heavily on distributed locking so multiple nodes can safely read and write the same files concurrently — including true POSIX semantics across the whole cluster. This makes it a strong fit for mixed HPC workloads (not just streaming large files) and for sites that want a single filesystem serving both traditional simulation codes and AI pipelines. GPFS is mature, well supported commercially, and commonly deployed on IBM Storage Scale System (ESS) appliances or on customer-built NSD servers.

BeeGFS: the lightweight alternative

BeeGFS was designed to be simpler to deploy and operate than Lustre or GPFS while still delivering strong parallel throughput. It splits roles similarly — a management service (registry/watchdog, not performance-critical), one or more metadata servers (directory structure and file layout, ideally on fast flash/RAID10 since metadata access latency directly affects responsiveness), and storage servers that hold striped file data — but it's known for an easier install path, good client-side tooling, and native support for striping across multiple metadata servers to reduce namespace hotspots. Many AI-focused clusters and smaller HPC shops pick BeeGFS specifically because it needs less specialized storage-admin expertise to stand up and tune than Lustre or GPFS, at the cost of a somewhat smaller enterprise support ecosystem.

NFS still has a job

Don't rip it out
Parallel filesystems are for bulk data — training sets, checkpoints, simulation output. NFS is still the right tool for home directories, small shared configuration files, environment modules, and anything low-throughput where POSIX simplicity and broad client compatibility matter more than raw bandwidth. Most production clusters run both: NFS for /home and shared tooling, a parallel filesystem for /scratch or /data.

Object storage: the AI training workhorse for datasets and checkpoints

Alongside (or sometimes instead of) a POSIX parallel filesystem, most modern AI training pipelines lean on S3-compatible object storage — whether a cloud provider's native object store or an on-prem system presenting the same S3 API. Object storage doesn't give you a POSIX filesystem tree; it gives you a flat namespace of "buckets" and "objects" accessed over HTTP, which scales extremely well horizontally and is cheap per terabyte. It has become the standard place to keep:

  • Training datasets — large sharded files (e.g., WebDataset tar shards, TFRecord, Parquet) that are streamed sequentially, which plays to object storage's strengths.
  • Model checkpoints — periodic full snapshots of model + optimizer state, often tens to hundreds of gigabytes per checkpoint for large models, written at intervals during training.
  • Longer-term artifact and dataset archives — durable, versioned, and far cheaper per GB than an all-flash parallel filesystem.

The tradeoff: object storage typically has higher per-request latency and weaker consistency/locking semantics than a parallel filesystem, so it's less suited to the small random I/O and POSIX locking that some HPC simulation codes need. The common pattern in AI clusters is to stage data — pull datasets from object storage into local NVMe or the parallel filesystem for actual training I/O, and push checkpoints back to object storage for durability once written.

Storage tiers: matching cost to access pattern

How storage connects to the fabric

None of this works without the network fabric covered in the previous section. Parallel filesystem clients and servers exchange data over the same high-speed fabric used for GPU-to-GPU traffic — usually InfiniBand or RoCE (RDMA over Converged Ethernet) — because RDMA lets storage servers place data directly into a client's memory (or, with GPUDirect Storage, directly into GPU memory) without extra copies through the CPU. This matters enormously at scale: without RDMA, every read or write burns CPU cycles copying data between kernel buffers, which caps throughput and adds latency long before the disks or network are the bottleneck.

GPUDirect Storage (GDS) extends this idea one step further for AI workloads: it creates a direct DMA (direct memory access) path between storage (whether local NVMe or a supported parallel/object filesystem) and GPU memory, skipping the CPU "bounce buffer" entirely. For training jobs that are I/O-bound — loading huge datasets or writing large checkpoints — this can be the difference between GPUs sitting idle waiting on data and GPUs staying saturated.

Worked example: sizing storage for a GPU training cluster

Scenario: a 512-GPU training cluster (64 nodes × 8 GPUs), training a large language model, checkpointing full model + optimizer state every 30 minutes.

Step 1 — Checkpoint size. A large model's checkpoint typically includes model weights plus optimizer state (e.g., Adam keeps two extra tensors per parameter), which can be 3–4× the raw parameter footprint in mixed precision. For a model whose weights alone are, say, 400 GB in bf16, a full checkpoint (weights + optimizer state + misc.) might land around 1.2–1.6 TB.

Step 2 — Checkpoint write bandwidth needed. If the target is to write a 1.5 TB checkpoint in under 3 minutes (180 s) so training resumes quickly, that's roughly 1.5 TB / 180 s ≈ 8.5 GB/s sustained aggregate write from the parallel filesystem — comfortably within reach of a mid-sized Lustre or BeeGFS deployment with a handful of OSS/storage-server nodes, but well beyond what a single NFS server could sustain.

Step 3 — Training-data read bandwidth needed. If each GPU consumes data at roughly 1.5 GB/s (typical for image or moderate-sequence-length text pretraining once decompressed) and there are 512 GPUs, the cluster's aggregate read demand is 512 × 1.5 GB/s ≈ 768 GB/s in the worst case — though in practice local NVMe caching, data sharding, and prefetching mean much of this is absorbed at the node level rather than hitting the shared filesystem directly every step.

Step 4 — Design the tiers. Given the above: (a) put per-node NVMe as a burst buffer to cache the active dataset shard and stage outgoing checkpoints, cutting shared-FS read pressure by an order of magnitude; (b) size the parallel filesystem (Lustre/BeeGFS/GPFS) for the ~8–10 GB/s sustained checkpoint-write burst plus whatever read traffic isn't absorbed by local caching — typically a few dozen OSTs is enough at this scale; (c) keep the dataset's durable copy and older checkpoints in S3-compatible object storage, since it's rarely read at full training speed and benefits far more from cost efficiency and durability than from ultra-low latency; (d) push checkpoints older than a retention window to tape/cold archive for compliance and disaster recovery.

Common mistake
Sizing the parallel filesystem for average throughput instead of peak. Checkpoint writes are bursty — all 64 nodes hit the filesystem at nearly the same instant every N minutes. If the filesystem is only sized for average daily throughput, every checkpoint becomes a multi-minute stall where GPUs sit idle. Size for the burst, not the average.
