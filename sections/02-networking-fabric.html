Networking & Fabric: InfiniBand, RoCE, RDMA, and Topology

A rack of the fastest GPUs on earth is only as fast as the network stitching them together. This section explains why AI and HPC clusters build a dedicated, ultra-low-latency "fabric" separate from ordinary Ethernet, how RDMA and GPUDirect let GPUs talk to each other without ever bothering the CPU, the two competing fabric technologies (InfiniBand and RoCEv2/Spectrum-X), the topologies (fat-tree, dragonfly, rail-optimized) used to wire thousands of GPUs together, and a worked example sizing a network for a 128-GPU cluster.

Why a Special Network at All?

Every cluster already has a boring management network — the one used for SSH, monitoring, provisioning, and pulling container images. That network typically runs on standard 1/10/25 Gbps Ethernet and is optimized for cost and simplicity, not speed. It is completely inadequate for what happens during distributed AI training or HPC simulation.

When a large model trains across hundreds or thousands of GPUs, every GPU must periodically exchange huge tensors of gradients and activations with every other GPU — operations like all-reduce, all-to-all, and all-gather. These exchanges happen many times per second, move gigabytes at a time, and the whole cluster stalls until the slowest transfer finishes. A single congested link or a few extra microseconds of latency on the critical path can slow an entire multi-thousand-GPU job. This is why clusters build a second, purpose-built network — the fabric — dedicated entirely to GPU-to-GPU traffic, running at 200–800 Gbps per link, engineered for both huge bandwidth and microsecond-scale latency, and kept physically and logically separate from the management network.

Rule of thumb
Think of the management network as the office intranet (email, file shares, ordinary chatter) and the fabric as a dedicated bank of private phone lines wired directly desk-to-desk for the one conversation that must never lag: the GPUs talking to each other.

RDMA: Skipping the CPU and the Kernel

Traditional networking (plain TCP/IP over Ethernet) moves data through several slow hops: the application copies data into a kernel buffer, the kernel processes it through the full network stack, the NIC driver is invoked, and the CPU is interrupted repeatedly along the way. Each hop adds latency and consumes CPU cycles that could otherwise be doing useful work.

RDMA (Remote Direct Memory Access) removes nearly all of that. It lets one machine's network adapter read or write directly into another machine's memory, without involving the remote CPU and without extra data copies. The sending and receiving NICs handle the transfer using pre-registered memory regions and hardware queues; the CPU is only informed once the transfer completes (or not involved at all).

For GPU workloads, NVIDIA extends this one step further with GPUDirect RDMA: it lets a NIC (or another GPU) read and write directly to and from GPU memory over the PCIe bus, completely bypassing a copy through host (CPU) system memory. Without GPUDirect RDMA, a data transfer between two GPUs on different nodes has to go: GPU memory → system RAM → NIC → wire → remote NIC → remote system RAM → remote GPU memory. With GPUDirect RDMA, it goes straight from GPU memory to NIC to wire to remote NIC to remote GPU memory — cutting latency and freeing up the CPU and PCIe bandwidth for other work. NVIDIA's official developer documentation describes this as a direct path "between the GPU and a third-party peer device using standard features of PCI Express," originally introduced with Kepler-class GPUs and CUDA 5.0.

GPUDirect family, briefly

GPUDirect RDMA — direct GPU memory ↔ NIC transfers across nodes.
GPUDirect Storage — direct GPU memory ↔ NVMe/storage transfers, skipping a bounce buffer in system RAM.
NVLink/NVSwitch — the even-faster equivalent for GPUs inside the same node or NVLink domain (covered in the Compute & Hardware section); RDMA over InfiniBand/RoCE is what extends that same "no CPU in the middle" philosophy across nodes.

The Two Fabric Choices: InfiniBand vs RoCEv2

There are two dominant ways to build an RDMA-capable fabric for GPU clusters today. Both can deliver 200–800 Gbps per link and low-microsecond latency; they differ in how they achieve lossless, congestion-free delivery, and in cost/operational trade-offs.

InfiniBand (NDR / HDR, NVIDIA Quantum)

InfiniBand is a purpose-built networking technology (originally standardized in 1999, now largely developed and sold by NVIDIA following the Mellanox acquisition) designed from the ground up for RDMA and lossless delivery. Current generations are HDR (200 Gbps per port) and NDR (400 Gbps per port), with NVIDIA's Quantum-2 switch line (e.g., the QM9700/QM9790, 64 ports of 400 Gb/s NDR) as the flagship hardware. Key characteristics:

  • Lossless by design at the link layer — credit-based flow control means a sender never transmits a packet unless the receiver has guaranteed buffer space, so there's no need to bolt on separate congestion-avoidance mechanisms.
  • Subnet Manager (SM) — a centralized control-plane service (OpenSM as an open-source option, or NVIDIA's UFM — Unified Fabric Manager — for production/enterprise deployments) that discovers the fabric topology, assigns routing tables, and manages partitioning. Every InfiniBand fabric needs exactly one active subnet manager.
  • Adaptive Routing (AR) — the fabric can dynamically shift traffic away from congested paths in real time, and NVIDIA UFM adds features like SHARP (in-network compute/aggregation offload) and SHIELD (self-healing interconnect) on top.
  • Trade-offs — InfiniBand delivers the best raw latency and the richest in-network offload features, but it means a separate switch fabric, separate cabling, separate expertise, and effectively single-vendor sourcing (NVIDIA/Mellanox dominates the market), which some operators view as lock-in.

RoCEv2 (RDMA over Converged Ethernet) / Spectrum-X

RoCEv2 runs the RDMA protocol over standard Ethernet framing (UDP/IP), which means it can, in principle, ride on commodity Ethernet switches and reuse existing Ethernet operational knowledge. But RDMA needs a lossless transport to perform well, and Ethernet is normally "best effort" (it drops packets under congestion and lets TCP retransmit). To make RoCEv2 viable at scale, the network needs:

  • Priority Flow Control (PFC) — a link-level pause mechanism so a switch can tell an upstream sender "stop" for a specific traffic class before its buffers overflow.
  • ECN (Explicit Congestion Notification) — routers mark packets as they approach congestion, so the sender can slow down before any packet is actually dropped, combined with congestion-control algorithms like DCQCN or NVIDIA's own NVIDIA Congestion Control (NCC).
  • NVIDIA Spectrum-X — NVIDIA's productized answer: Spectrum-4 switches paired with BlueField-3 SuperNICs / ConnectX-7/8 NICs, tuned end-to-end so that PFC, ECN, and adaptive load balancing work together to deliver "zero packet drop" lossless RoCEv2 at large GPU scale, marketed at roughly 1.6x AI workload throughput versus off-the-shelf Ethernet.
  • Trade-offs — RoCEv2/Ethernet benefits from a much broader multi-vendor ecosystem (switches, optics, NICs, and operational tooling used across the whole data center industry, not just AI), and many network teams already know Ethernet operations. Getting a truly lossless, congestion-free RoCEv2 fabric right at scale is nontrivial engineering, though — PFC storms and head-of-line blocking are real failure modes if not tuned carefully, which is precisely the problem Spectrum-X packages a validated answer to.

When to choose which
There's no universally "correct" answer — it depends on scale, budget, and operations. Extremely large, dedicated training superclusters (tens of thousands of GPUs, latency-critical collectives, heavy use of in-network aggregation) often favor InfiniBand for its maturity and offload features. Cloud providers and organizations that want to reuse existing Ethernet operational tooling, avoid single-vendor lock-in, or run mixed AI/general workloads over a converged fabric increasingly choose RoCEv2 with Spectrum-X, especially since the performance gap has narrowed substantially in recent generations.

Network Topologies for HPC/AI Clusters

However fast individual links are, the way switches are wired together (the topology) determines how much bandwidth is actually available between any two GPUs, and how the network behaves as the cluster scales from dozens to tens of thousands of nodes.

Fat-Tree / Clos Topology

The dominant topology in HPC and AI data centers is the fat-tree (a practical instance of the more general Clos network from telecom switching theory). It arranges switches in tiers — commonly leaf switches (which nodes plug directly into) and spine switches (which interconnect the leaves) — such that there are many equal-cost paths between any pair of leaves. This gives the network two prized properties: it's non-blocking (in principle every node can talk to every other node at full link rate simultaneously) and it tolerates failures gracefully (traffic reroutes over a surviving equal-cost path). Larger clusters add a third tier (core/super-spine) on top of leaf-spine to keep scaling out.

Dragonfly Topology

For the very largest supercomputers, some designs use a dragonfly topology instead: nodes are organized into densely-connected local groups, and the groups themselves are connected by a smaller number of longer global links. Dragonfly can reach extreme scale with fewer total switches and cables than a pure fat-tree of the same size, trading some worst-case path diversity for lower hardware cost — a common design point in leadership-class HPC systems, less common (but not unheard of) in commercial AI training clusters.

Rail-Optimized Design for GPU Clusters

Modern GPU servers (e.g., 8-GPU nodes) typically have one dedicated high-speed NIC per GPU — this per-GPU NIC is called a rail. In a rail-optimized topology, all the "rail 0" NICs (one from every server) connect to the same leaf switch, all the "rail 1" NICs connect to a different (or the same, in smaller builds) leaf switch, and so on. This lines up perfectly with how NCCL (NVIDIA's collective communications library) schedules communication: the dominant collective operations (like all-reduce during training) are scheduled so that most traffic for a given GPU rank stays within its own rail and leaf switch, only crossing to the spine for the smaller residual cross-rail traffic. The result is dramatically better collective performance and less cross-fabric interference, and it can even reduce cost since inter-leaf/spine links can be provisioned lighter than they would need to be for fully random traffic patterns.

Key Terms Glossary

Leaf / Spine

Leaf switches connect directly to servers/nodes. Spine switches connect leaves to each other, providing the aggregation layer. Larger builds add a core or super-spine tier above the spine.

Oversubscription Ratio

The ratio of downstream (node-facing) bandwidth on a switch to its upstream (uplink) bandwidth. A 1:1 ("non-blocking") ratio means every node could theoretically use full bandwidth simultaneously; a 3:1 ratio means only a third of that is guaranteed under worst-case, all-to-all traffic — a common cost/performance trade-off outside the GPU rails themselves.

Subnet Manager

The control-plane brain of an InfiniBand fabric — discovers topology, computes routing tables, manages partitions. Runs as OpenSM (open source) or NVIDIA UFM (commercial, adds monitoring/AR/SHARP/SHIELD). Every IB fabric needs exactly one active instance.

Rail

The dedicated NIC-to-switch path assigned to one GPU position across all servers in the cluster (e.g., "rail 0" = every server's GPU-0 NIC). Rail-aligned wiring lets communication libraries like NCCL keep the heaviest traffic local to a single leaf switch.

Worked Example: Sizing a Fat-Tree for a 128-GPU Cluster

Assume a typical build: 8-GPU servers, one 400 Gbps NIC per GPU (one rail each), so 128 GPUs ÷ 8 GPUs/server = 16 servers, and 128 total 400G rail ports to connect (8 rails × 16 servers).

Step 1 — pick a leaf switch. A 64-port 400 Gbps leaf switch (like NVIDIA's Quantum-2 QM9700 class) can be split, e.g., 32 ports down to servers and 32 ports up to spines, for a 1:1 (non-blocking) leaf-to-spine ratio.

Step 2 — one leaf per rail. In a fully rail-optimized design, you'd typically dedicate one leaf switch per rail number. With 8 rails, that's 8 leaf switches, each taking one NIC from all 16 servers (16 down-links used out of the switch's capacity) — comfortably inside a 32-port leaf, leaving headroom to scale node count later.

Step 3 — spine sizing. To keep the fabric non-blocking, the total uplink bandwidth from each leaf must match its total downlink (node-facing) bandwidth. With 16 servers × 400 Gbps = 6.4 Tbps of downlink capacity per leaf/rail, you need an equivalent 6.4 Tbps of uplink capacity split across spine switches — e.g., 16 × 400 Gbps uplinks per leaf feeding into a set of spine switches sized to match.

Step 4 — result. A 128-GPU cluster this size comfortably fits in a single-tier leaf-plus-spine (2-tier) fat-tree with 8 rail-dedicated leaves and a handful of spine switches — no third (core) tier needed. Clusters typically only need a third tier once they scale into the thousands of GPUs, where a single spine layer can no longer provide enough radix (port count) to stay non-blocking.

Takeaway
Sizing a fabric is fundamentally a radix (port-count) and oversubscription-ratio exercise: count how many rail ports you have, pick a leaf switch radix, decide how much oversubscription (if any) you're willing to tolerate outside the GPU rails, and let that determine how many spine switches and tiers you need.
