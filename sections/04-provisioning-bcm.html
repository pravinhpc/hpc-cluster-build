04 — Cluster Provisioning with NVIDIA Base Command Manager (BCM)

You've racked the nodes, wired the network, and built the storage. Now you need to turn a room full of bare, blank servers into one coherent, working cluster — with the same OS, the same drivers, the same workload manager, on every node, automatically. That's the job of a provisioning system, and NVIDIA Base Command Manager (BCM) is the tool this guide uses to do it.

What BCM is

Base Command Manager is NVIDIA's commercial cluster management product. It was originally an independent company's product called Bright Cluster Manager; NVIDIA acquired Bright Computing in 2022 and rebranded the software as Base Command Manager (BCM), folding it into the broader NVIDIA Base Command / Mission Control software family used to stand up DGX SuperPOD and similar AI factory deployments. Under the new name the core architecture is unchanged, so almost everything written about "Bright Cluster Manager" online — commands, log files, directory paths — still applies to BCM.

What makes BCM useful is that it collapses several jobs that would otherwise be separate tools into one product:

  • Bare-metal provisioning — PXE-boot new nodes and install a full OS image on them with zero manual OS installs.
  • Software stack management — a "software image" (a golden root filesystem) is defined once and pushed to every node in a category, so drift between nodes disappears.
  • Configuration management — network settings, kernel modules, BIOS/BMC settings, and workload-manager roles are all assigned centrally and enforced continuously.
  • Monitoring and health checking — built-in metrics collection, alerting, and Node Health Check (NHC) style checks that can automatically drain a sick node from the scheduler.
  • User and identity management — local user database with LDAP integration for centralized authentication.

The alternative is stitching together Cobbler or MAAS for provisioning, Ansible for configuration, Ganglia or Prometheus for monitoring, and FreeIPA for identity — which works, but is a lot more moving parts to keep in sync. BCM's value proposition is "one console, one data model, one place things can go wrong (or right)."

Where this fits in the build
By this point in the guide you should already have: physical racking and power (guide 01), a working leaf-spine or fat-tree network with a dedicated provisioning/management VLAN (guide 02), and shared storage reachable from every rack (guide 03). BCM sits on top of all of that — it doesn't replace your network or storage, it configures nodes to use them correctly.

Core concepts

Head node

The head node (sometimes called the management node) is where BCM itself runs. It's the only node in the cluster you install an OS on by hand — every other node gets its OS from the head node over the network. The head node runs the BCM software stack, holds the CMDaemon database, serves DHCP/PXE/TFTP on the internal provisioning network, and is usually also where Slurm's controller (slurmctld) and the license/monitoring services live. Production clusters typically run head nodes in an active-passive high-availability pair so a single head node failure doesn't take down provisioning or job scheduling.

Node categories and software images

A software image is a complete root filesystem — kernel, drivers, libraries, GPU/CUDA stack, Slurm client binaries, monitoring agents — stored on the head node (or on shared storage) as a template. A node category is a group of nodes that share the same software image, the same kernel modules, the same disk layout, and the same roles (e.g. "gpu-compute", "cpu-compute", "login"). Instead of configuring 500 nodes individually, you configure one category and every node that belongs to it inherits the settings. Node-specific overrides (a MAC address, an IP, a specific BIOS setting) live at the individual node level and win over category defaults.

cmsh and Base View

BCM exposes two administrative interfaces over the same underlying object model:

  • cmsh — a scriptable command-line shell (think of it as a cluster-aware, hierarchical CLI similar to a network switch's config mode). This is what you use for automation, batch changes, and anything you want to keep in a script or git repo.
  • Base View (formerly Bright View) — a web GUI covering the same functionality, useful for browsing state, monitoring dashboards, and one-off changes.

Both talk to the same backend process, CMDaemon, described next — so a change made in cmsh shows up in Base View instantly and vice versa.

CMDaemon

CMDaemon is the management daemon that is the actual brain of BCM. A full CMDaemon runs on the head node holding the authoritative cluster configuration database; a lightweight CMDaemon also runs on every regular node, reporting metrics and health status back to the head node and applying configuration changes pushed down to it. cmsh, Base View, and the REST/Python API are all just clients talking to CMDaemon — there's no separate "provisioning service" and "monitoring service" to keep in sync, it's one daemon with one data model.

The node-installer and PXE boot flow

This is the mechanism that actually gets a blank server running the right OS. In short: a node powers on, PXE-boots a small Linux environment from the head node, that environment (the node-installer) figures out which category the node belongs to, downloads the matching software image, writes it to local disk (or configures diskless/NFS-root boot), and then hands off to the real kernel to boot the installed OS. Full detail is in the walkthrough below.

Step-by-step: building a cluster with BCM from scratch

Step 1 — Install the head node

BCM ships as an ISO/installer that you run on the machine that will become the head node, on top of a supported base OS (RHEL/Rocky or Ubuntu, depending on the BCM release). During installation you specify:

  • The internal cluster network range (the provisioning/management network your compute nodes will PXE-boot on).
  • The head node's own hostname and network interfaces (external/site network vs. internal cluster network).
  • Which base distribution image to install as the default software image for compute nodes (BCM includes ready-made images to start from).
  • License details and, for HA setups, the passive head node.

At the end of this step you have one fully working Linux server running CMDaemon, DHCP, TFTP, and a provisioning HTTP(S) service — but zero compute nodes yet.

Step 2 — Define node categories and software images

Next you decide how many distinct "types" of node you have — typically at least gpu-compute, maybe a separate cpu-compute, a login category, and sometimes a storage-gateway category if you're running Lustre/GPFS gateway nodes outside your dedicated storage appliance. For each category you clone or customize a software image: install the GPU driver and CUDA toolkit into the gpu-compute image, add InfiniBand/RoCE drivers (MLNX_OFED or in-box drivers) to whichever categories carry a fabric NIC, add the Slurm client packages, and enable your monitoring agent. You do this by chrooting into the image (BCM gives you a helper for this) and installing packages exactly as you would on a normal machine, then committing the image.

Step 3 — PXE-boot and provision the compute nodes

With the network switches configured to allow PXE/DHCP traffic on the provisioning VLAN (see guide 02), power on the compute nodes with PXE boot as the first boot device (usually set once in BIOS/BMC, or via a boot-order override sent through IPMI/Redfish). Each node then follows this flow:

  1. Node powers on, BMC/BIOS issues a PXE request on the provisioning NIC.
  2. Head node's DHCP service on that network answers, handing out an IP and pointing at the TFTP boot loader.
  3. Node downloads and boots a minimal Linux environment — the node-installer — over TFTP/HTTP.
  4. The node-installer identifies the node (usually by MAC address, matched against a node object already defined in cmsh, or auto-discovered on first boot) and determines which category and software image apply.
  5. It partitions local disk if needed, then pulls the full software image down from the head node over HTTPS/rsync and writes it to disk (or sets up diskless/NFS-root operation if the category is configured that way).
  6. It writes node-specific configuration (hostname, network config, fstab entries) into the freshly installed filesystem.
  7. The node reboots into the real installed OS, the local CMDaemon starts, registers with the head node, and the node transitions to an "UP" state visible in cmsh/Base View.

You can watch this whole sequence live via tail -f /var/log/node-installer on the node's console (accessible through the BMC), or from the head node with pexec/cmsh's device open/power commands. New hardware you haven't seen before shows up in cmsh as an unassigned "discovered" node — you assign it a hostname/category, commit, and reboot it to trigger provisioning.

Step 4 — Configure Slurm workload manager integration

BCM includes a Slurm "role" you assign to nodes and categories rather than hand-editing slurm.conf across the fleet. You designate one node (often the head node, or a dedicated node for larger clusters) with the slurmserver role, and assign the slurmclient role to every compute category. BCM then generates and distributes slurm.conf, gres.conf (for GPU resources), and cgroup configuration automatically, keeping them consistent across every node — including partition definitions, GPU GRES entries, and topology-aware settings for the fabric. Because BCM already knows each node's category, CPU count, and GPU inventory, it can populate most of the Slurm node definitions for you rather than you typing them by hand.

Step 5 — Configure networking (InfiniBand/RoCE) via BCM

For the high-speed fabric configured in guide 02, BCM manages the relevant kernel modules, OFED stack, and interface configuration as part of the category's software image and network settings. You define the IB/RoCE network as a BCM network object (subnet, MTU, associated interfaces), attach node interfaces to it per category, and BCM ensures the right driver stack (e.g. MLNX_OFED or the in-box driver set) is present in the image and that interface naming/IP assignment stays consistent across every node of that category — avoiding the classic problem of one node's ib0 silently becoming ib1 after a driver update.

Step 6 — Add monitoring

CMDaemon on every node already collects a baseline of metrics (CPU, memory, disk, network, and — with the GPU health/metrics package installed in the image — DCGM-based GPU metrics) and reports them back to the head node's monitoring database. From here you define health checks (disk full, GPU Xid errors, IB link down, temperature thresholds) and actions (email alert, Slack webhook, automatically drain the node from Slurm) directly in cmsh or Base View. Larger sites typically also export these metrics to Prometheus/Grafana for long-term dashboards — this guide covers that integration in a later monitoring-focused section.

User management and LDAP

Out of the box, BCM maintains its own local user/group database, replicated by CMDaemon to every node so a user account created once works cluster-wide without manual /etc/passwd syncing. For real deployments you almost always want centralized identity instead — BCM can be pointed at an external LDAP or Active Directory server so user and group lookups are authoritative there rather than in BCM's local store. We cover the full LDAP setup, including how it interacts with Slurm accounting and home-directory automount, in a later section of this guide (see "LDAP and Centralized Identity").

BCM vs. xCAT vs. Warewulf — a quick preview

BCM is one of three provisioning approaches this guide covers; the next two sections walk through xCAT and Warewulf in full. The short version, for context while you read this section:

AspectBCMxCAT / Warewulf
LicensingCommercial (NVIDIA), often bundled with DGX/SuperPOD purchasesOpen source, free
ScopeProvisioning + monitoring + Slurm config + identity in one productProvisioning-focused; you assemble monitoring/config-mgmt separately (e.g. with Ansible)
Interfacecmsh CLI + Base View GUI + REST/Python APICLI tools (xCAT: xCAT commands; Warewulf: wwctl), no bundled GUI
Support modelNVIDIA enterprise support, tightly aligned with DGX reference architecturesCommunity support, HPC-center-driven development

Deep, hands-on comparisons and migration notes come later in the guide — the point here is just that BCM trades a license fee for an integrated, vendor-supported experience that's especially common on NVIDIA DGX SuperPOD-style builds.

Realistic cmsh example

The example below shows a plausible session: checking discovered hardware, creating a GPU compute category cloned from a base image, assigning nodes into it, adding the Slurm client role, and committing the changes. Command syntax follows standard BCM/Bright Cluster Manager cmsh conventions from the official admin manual.

# Connect to the head node's management shell
[root@head1 ~]# cmsh
[head1]%

# List nodes currently known to the cluster, including newly discovered hardware
[head1]% device list
Type            Hostname     MAC                Category    Network        IP
------------ ------------ ------------------ ----------- -------------- --------------
HeadNode        head1        00:1a:2b:aa:bb:cc  -           externalnet    10.0.0.1
PhysicalNode    node001      00:1a:2b:11:22:01  gpu-compute internalnet    10.141.0.1
PhysicalNode    node002      00:1a:2b:11:22:02  gpu-compute internalnet    10.141.0.2

# Inspect available software images
[head1]% softwareimage
[head1->softwareimage]% list
Name (key)              Path                                 Kernel version
------------------------ ------------------------------------ ------------------
default-image            /cm/images/default-image            5.14.0-x86_64
gpu-compute-image        /cm/images/gpu-compute-image         5.14.0-x86_64

# Create a category for GPU compute nodes and point it at the GPU image
[head1->softwareimage]% category
[head1->category]% add gpu-compute
[head1->category*[gpu-compute*]]% set softwareimage gpu-compute-image
[head1->category*[gpu-compute*]]% commit

# Add the Slurm client role so every node in this category joins the cluster
[head1->category]% use gpu-compute
[head1->category[gpu-compute]]% roles
[head1->category[gpu-compute]->roles]% assign slurmclient
[head1->category[gpu-compute]->roles*[slurmclient*]]% set queue gpu
[head1->category[gpu-compute]->roles*[slurmclient*]]% commit

# Assign a discovered node into the category and give it a hostname
[head1->category]% device use node003
[head1->device[node003]]% set category gpu-compute
[head1->device[node003]]% set hostname gpu003
[head1->device*[gpu003*]]% commit

# Power-cycle the node to kick off PXE provisioning
[head1->device]% power reset gpu003
Successfully sent 'reset' to: gpu003

# Watch the node come up
[head1->device]% status gpu003
gpu003 ......................... [ INSTALLING ]
[head1->device]% status gpu003
gpu003 ......................... [ UP ]
Field note
Software image changes don't take effect on running nodes until you either reboot the node or push an update with imageupdate/updateprovisioners-style sync commands — editing a category's image doesn't retroactively touch nodes that are already up and running.
