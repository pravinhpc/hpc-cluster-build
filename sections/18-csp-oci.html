18 — Building an HPC/AI GPU Cluster on Oracle Cloud Infrastructure (OCI)

Oracle Cloud Infrastructure takes a distinctly bare-metal-first approach to GPU clusters. Instead of virtualizing GPU nodes, OCI hands you the physical host directly, wires it into a dedicated RDMA fabric via a construct called a cluster network, and lets you provision the whole thing with Terraform. This page is a condensed overview of what that stack looks like and how to stand up the network layer end to end; the internal edition of this guide goes much deeper on operational realities.

GPU shapes

OCI's GPU compute is offered almost entirely as bare metal ("BM") shapes — you get the whole physical server, not a hypervisor slice of one. The shapes relevant to HPC/AI cluster builds:

Every one of these shapes ships with a set of dedicated RDMA NICs separate from the host's management/VCN NIC — that RDMA fabric is what "cluster networking" actually configures.

The RDMA cluster network fabric

OCI's high-performance interconnect for bare-metal GPU and HPC shapes is built on RDMA over Converged Ethernet v2 (RoCE v2) running over NVIDIA ConnectX NICs, not classic InfiniBand. To actually get low-latency, high-bandwidth node-to-node communication (the kind NCCL/collective operations need), a GPU instance has to be launched as a member of a compute cluster or a cluster network with instance pools — a placement construct that groups instances physically close together and wires their RDMA NICs into the same non-blocking fabric segment. Instances launched independently, outside a cluster network, do not automatically get this topology-aware placement.

A cluster network with instance pools is defined by an instance configuration (the shape, image, boot volume, and network attachments a node should have) plus a placement configuration (availability domain, fault domains, and the target instance count). OCI enforces same-fabric placement for every instance in the pool, and exposes a secondary VNIC per RDMA port so the GPU driver stack (typically the appropriate NIC/OFED-equivalent driver set plus NCCL) can bind to it directly.

VCN and subnet design

A typical OCI GPU cluster VCN separates traffic into distinct subnets: a client/management subnet for SSH, provisioning, and API traffic; a storage subnet reachable by both compute and any Lustre/File Storage endpoints; and the RDMA network, which is not a normal routable VCN subnet at all — it's the dedicated backend fabric that cluster networking wires up automatically per instance. Security lists / network security groups are applied at the client and storage subnet level; the RDMA fabric is isolated by construction rather than by security-list rule.

Storage: File Storage and Lustre

For shared, POSIX-accessible storage in front of GPU training and checkpointing workloads, OCI offers two main paths: standard OCI File Storage (NFS), including high-performance mount targets that scale into the tens of Gbps per mount target and can be combined for higher aggregate throughput; and OCI File Storage with Lustre, a managed parallel filesystem purpose-built for the throughput and IOPS profile of large-scale GPU training clusters, capable of scaling to hundreds of GB/s aggregate throughput across many client nodes.

IAM policies

OCI IAM is policy-statement based rather than role-attachment based. A minimal cluster-build policy set typically grants a dynamic group (or a named group of cluster administrators) the ability to manage compute-cluster, instance-pool, instance-configuration, and virtual-network-family resources in the target compartment, plus read access to the image and boot-volume families. Isolating the GPU cluster into its own compartment, with policies scoped to that compartment rather than the tenancy root, is the standard pattern for keeping blast radius small.

Step-by-step: building the cluster network

Step 1 — Create the VCN and subnets

Stand up a VCN with a client subnet for management traffic and (optionally) a storage subnet for File Storage/Lustre mount targets. The RDMA fabric itself is not a subnet you create — it's provisioned automatically as part of the cluster network.

Step 2 — Define an instance configuration

An instance configuration captures the shape, image, boot volume size, and VNIC attachments every node in the pool should get.

Step 3 — Create the cluster network with instance pool

Point a cluster-network resource at the instance configuration, set the target size, and OCI places every instance in the pool on the same RDMA fabric segment.

Step 4 — Attach shared storage and configure the workload manager

Mount File Storage/Lustre from every node, then layer Slurm or your scheduler of choice on top exactly as you would on-prem.

# main.tf — minimal OCI cluster network with instance pool
resource "oci_core_instance_configuration" "gpu_h100" {
  compartment_id = var.compartment_ocid
  display_name   = "gpu-h100-instance-config"

  instance_details {
    instance_type = "compute"
    launch_details {
      compartment_id = var.compartment_ocid
      shape          = "BM.GPU.H100.8"
      source_details {
        source_type = "image"
        image_id    = var.gpu_image_ocid
      }
      create_vnic_details {
        subnet_id        = oci_core_subnet.client_subnet.id
        assign_public_ip = false
      }
    }
  }
}

resource "oci_core_cluster_network" "gpu_cluster" {
  compartment_id = var.compartment_ocid
  display_name   = "gpu-h100-cluster-net"

  instance_pools {
    instance_configuration_id = oci_core_instance_configuration.gpu_h100.id
    size                      = 32
    display_name              = "gpu-h100-pool"

    placement_configurations {
      availability_domain = var.availability_domain
      primary_subnet_id   = oci_core_subnet.client_subnet.id
    }
  }
}
