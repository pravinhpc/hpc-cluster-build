09 — Identity & Access: Integrating LDAP with Your Cluster

Every job on your cluster runs as somebody. Before a scheduler can enforce fair-share policy, before a filesystem can enforce ownership, and before an auditor can answer "who ran what, when" — the cluster needs one consistent, cluster-wide answer to the question "who is this user, and what are they allowed to touch?" That answer comes from a directory service, and in HPC the directory protocol of choice is LDAP.

This section explains LDAP itself — what it is, why clusters depend on it, where it physically sits in your architecture, when to stand it up in your build sequence, and how to actually deploy and wire it in. Section 10 picks up where this one ends: caching LDAP identity at scale with SSSD on every compute node.

WHAT — What LDAP Actually Is

LDAP (Lightweight Directory Access Protocol) is not a piece of software — it is a protocol, standardized in RFC 4511, for reading and writing entries in a hierarchical directory. Think of it as the read-heavy, hierarchical cousin of a relational database: instead of tables and rows optimized for transactional writes, you get a tree of named entries optimized for fast, structured lookups — "give me the UID and shell for user jsmith" thousands of times a second, from thousands of nodes.

The Directory Information Tree (DIT)

Every LDAP directory is organized as a tree, called the DIT. Each node in the tree is an entry, uniquely identified by a Distinguished Name (DN) — the LDAP equivalent of a full file path. A typical HPC DIT looks like this:

dc=cluster,dc=example,dc=org
├── ou=People
│   ├── uid=jsmith,ou=People,dc=cluster,dc=example,dc=org
│   └── uid=agupta,ou=People,dc=cluster,dc=example,dc=org
└── ou=Groups
    ├── cn=researchers,ou=Groups,dc=cluster,dc=example,dc=org
    └── cn=admins,ou=Groups,dc=cluster,dc=example,dc=org

Each entry is built from one or more objectClasses, which define which attributes it must and may carry. For POSIX-style Linux accounts (the kind your cluster needs), the two workhorse objectClasses are:

objectClassPurposeKey attributes
posixAccountRepresents a Unix user accountuid, uidNumber, gidNumber, homeDirectory, loginShell
posixGroupRepresents a Unix groupcn, gidNumber, memberUid
inetOrgPersonHuman-readable identity attributes layered on top of an accountcn, sn, mail

An example entry, in LDIF (LDAP Data Interchange Format) — the plain-text format used to define and import directory entries:

dn: uid=jsmith,ou=People,dc=cluster,dc=example,dc=org
objectClass: inetOrgPerson
objectClass: posixAccount
objectClass: top
uid: jsmith
cn: Jane Smith
sn: Smith
mail: jsmith@example.org
uidNumber: 100234
gidNumber: 50000
homeDirectory: /home/jsmith
loginShell: /bin/bash

LDAP the protocol vs. the directory that speaks it. "LDAP" itself does not store anything — it's the wire protocol. The actual server holding the data is a specific directory implementation. In HPC you'll most often meet:

  • OpenLDAP — the lightweight, open-source slapd daemon; the traditional choice for a standalone Linux-only cluster identity store.
  • 389 Directory Server — Red Hat's enterprise-grade LDAP server, the engine underneath FreeIPA.
  • FreeIPA — a full identity management suite (389-DS + MIT Kerberos + a CA + DNS + a web UI) that speaks LDAP but gives you Kerberos SSO and centralized policy for free.
  • Active Directory — Microsoft's directory; also speaks LDAP (plus Kerberos), common when a cluster has to share identity with a Windows-heavy corporate environment.

WHY — Why Clusters Cannot Run on Local /etc/passwd

A single workstation happily keeps its user list in /etc/passwd and /etc/group. An HPC cluster with hundreds or thousands of compute nodes cannot, for reasons that compound quickly at scale:

  • UID/GID consistency. If jsmith is UID 100234 on the login node but UID 100987 on compute node c0421 (because the accounts were created locally, in a different order, on each node), then file ownership becomes meaningless the moment a job writes to a shared parallel filesystem. Job A's output looks like it's owned by a completely different person on a different node.
  • Onboarding/offboarding at scale. Editing /etc/passwd by hand — or even via a config-management push — on 2,000 nodes every time a researcher joins or leaves is slow and error-prone. A directory update is a single write, propagated everywhere in seconds.
  • Single source of truth. The scheduler (Slurm), the filesystem (Lustre/GPFS/NFS), the login nodes, and any web portals all need to agree on who a user is and which groups grant them budget/allocation access. One directory, one truth, no drift.
  • Auditability and offboarding compliance. Security reviews routinely need to answer "list every account with access to this cluster" and "prove this ex-employee's access was revoked on day X." A central directory with logging gives you that in one query; grepping 2,000 /etc/passwd files does not.
  • Group-based authorization. Slurm QOS/partition access, filesystem ACLs, and sudo policy are almost always expressed as "members of group X" — which only works if group membership is centrally and consistently defined.

WHERE — LDAP's Place in the Cluster Architecture

Identity flows outward from one authoritative source to every node that needs to authenticate a user or resolve a UID:

  • Login/head nodes authenticate interactive SSH sessions against the directory — this is where users actually type a password or present a key that needs a UID/GID lookup behind it.
  • Compute nodes almost never talk to LDAP directly for every lookup. Instead they run SSSD (System Security Services Daemon), which caches identity and authentication results locally so that a flaky network blip or an LDAP server restart doesn't stall ten thousand simultaneous job-launch UID lookups. Full setup is in Section 10 — SSSD Integration.
  • The LDAP server itself should not live on a head node in any production cluster. Put it on dedicated, replicated servers (at minimum a primary + one syncrepl consumer) outside the failure domain of your login/scheduler nodes — if LDAP goes down, nobody can log in or launch jobs anywhere, so it needs its own uptime story, backups, and monitoring independent of the rest of the stack. Many sites run it as a small VM pair or a pair of dedicated identity nodes.

WHEN — Where This Fits in the Build Sequence

Identity is a foundation layer, not an afterthought bolted on after users start complaining. Sequence it like this:

  1. After base OS provisioning and networking are stable (nodes can resolve DNS and reach each other) — LDAP needs working name resolution and, ideally, NTP-synced clocks (critical if you layer Kerberos on top later).
  2. Before you open the cluster to any real users. Local accounts created "just to get started" become technical debt the moment a second person needs an account, and reconciling ad-hoc local UIDs against a newly-introduced directory is a painful, error-prone migration.
  3. Before or alongside scheduler (Slurm) setup — not after. Slurm accounting, fair-share, and job ownership all key off UID/GID. If Slurm is configured and jobs have already run under locally-assigned UIDs, backfilling consistent UID/GIDs later means re-chowning accounting records and, in the worst case, files already written to the shared filesystem under the "wrong" (soon to be reassigned) UID.
  4. Before the parallel filesystem is populated with real user data, for the same UID-consistency reason.

HOW — Deploying and Wiring In LDAP

Step 1 — Choose and deploy a directory

For a Linux-only HPC cluster with modest identity needs, OpenLDAP is lightweight and well understood. If you also want Kerberos SSO, a certificate authority, and a web UI out of the box, FreeIPA bundles all of that around 389-DS and is often the better long-term choice for a cluster that will grow.

OpenLDAP (Debian/Ubuntu):

sudo apt-get install slapd ldap-utils
sudo dpkg-reconfigure slapd
# Prompts you for: base DN (e.g. dc=cluster,dc=example,dc=org),
# admin password, database backend (mdb is the current default)

OpenLDAP (RHEL/Rocky):

sudo dnf install openldap-servers openldap-clients
sudo systemctl enable --now slapd
# RHEL ships slapd already using cn=config (OLC); seed it via
# /etc/openldap/slapd.d or the provided .ldif bootstrap files

FreeIPA server:

sudo dnf install freeipa-server
sudo ipa-server-install \
  --realm=CLUSTER.EXAMPLE.ORG \
  --domain=cluster.example.org \
  --ds-password= \
  --admin-password= \
  --setup-dns --no-forwarders

ipa-server-install stands up 389 Directory Server, an MIT Kerberos KDC, a Dogtag CA, and (optionally) DNS in one guided run — see the official FreeIPA Quick Start Guide.

Step 2 — Design the DIT/OU structure

Keep it flat and predictable. For most HPC sites, two top-level organizational units cover everything:

dc=cluster,dc=example,dc=org
├── ou=People    <- one posixAccount entry per user
└── ou=Groups    <- one posixGroup entry per project/team/role

Resist the urge to nest deeply by department early on — it complicates ACLs and search filters for little benefit at cluster scale (a few hundred to low tens of thousands of accounts). If you need project-based access control, model it as group membership (cn=proj-fusion, cn=proj-genomics), not as DIT structure.

Step 3 — Configure TLS/LDAPS

Never run plaintext LDAP (port 389 without StartTLS) for authentication traffic in production — credentials and directory contents traverse the network in the clear otherwise. Enable LDAPS (port 636) or mandate StartTLS on port 389.

# cn=config (OLC) example: point slapd at your cert material
dn: cn=config
changetype: modify
replace: olcTLSCertificateFile
olcTLSCertificateFile: /etc/openldap/certs/ldap-server.crt
-
replace: olcTLSCertificateKeyFile
olcTLSCertificateKeyFile: /etc/openldap/certs/ldap-server.key
-
replace: olcTLSCACertificateFile
olcTLSCACertificateFile: /etc/openldap/certs/ca.crt
# Apply it with ldapmodify
ldapmodify -Y EXTERNAL -H ldapi:/// -f enable-tls.ldif

# In /etc/sysconfig/slapd or the systemd unit, listen on LDAPS too:
SLAPD_URLS="ldapi:/// ldap:/// ldaps:///"

Step 4 — Verify with ldapsearch

# Anonymous search over LDAPS, verifying TLS + returning a user entry
ldapsearch -H ldaps://ldap01.cluster.example.org \
  -x -b "ou=People,dc=cluster,dc=example,dc=org" \
  "(uid=jsmith)" uidNumber gidNumber homeDirectory loginShell

# Authenticated bind test (prompts for password)
ldapsearch -H ldaps://ldap01.cluster.example.org \
  -D "uid=jsmith,ou=People,dc=cluster,dc=example,dc=org" -W \
  -b "dc=cluster,dc=example,dc=org" "(objectClass=posixAccount)"

Step 5 — Configure client nodes

Historically this meant editing /etc/nsswitch.conf to add ldap as a source and configuring pam_ldap / nss-pam-ldapd directly:

# /etc/nsswitch.conf (legacy direct-LDAP approach)
passwd:     files ldap
group:      files ldap
shadow:     files ldap

In practice, almost nobody points compute nodes at LDAP directly anymore — direct pam_ldap/nss_ldap has no local caching, so an LDAP hiccup or network partition means every login and every UID lookup on every node fails simultaneously. The modern, recommended path is to route through SSSD instead, which layers caching, offline auth, and connection failover on top of the same LDAP backend. That configuration — sssd.conf, id_provider = ldap, cache tuning, and integration with Slurm's UID lookups at job-launch scale — is covered in full in Section 10 — SSSD Integration.

Step 6 — Sync UID/GID ranges across the cluster

Reserve a UID/GID range for LDAP-managed accounts that never overlaps system/local accounts on any node image:

# /etc/login.defs on every node image — keep local accounts out of the LDAP range
UID_MIN   1000
UID_MAX  60000
# LDAP-managed human accounts start at 100000+
# Service accounts (e.g. svc-slurm) sit in a separate reserved band, e.g. 400-999

Bake this into your golden node image / configuration management (Ansible, Warewulf, xCAT postscripts) so every node — provisioned today or reimaged next year — agrees on the same reserved bands from day one.

Step 7 — Integration with cluster management tools

If you're running a commercial or semi-commercial cluster manager, don't hand-wire LDAP against its grain:

  • Bright Cluster Manager (BCM) has built-in LDAP integration (cmauth/CMDaemon-managed OpenLDAP by default, or bind-to-external-LDAP mode) exposed through cmsh — use its native user-management module rather than editing slapd.conf by hand on a BCM head node.
  • xCAT expects identity to be handled by whatever OS-level mechanism you configure (typically SSSD) on the management and compute images; it doesn't ship its own directory but has documented patterns for syncing /etc/passwd-equivalent data during node deployment for sites that don't want a live LDAP dependency at node boot.

Check your CM tool's own docs before improvising — most drama here comes from fighting the tool's assumptions about where identity "lives" rather than from LDAP itself.

Common pitfalls
  • UID/GID collisions. A node image with pre-existing local accounts (or a previous ad-hoc cluster) can collide with LDAP-assigned UIDs. Always audit /etc/passwd on your golden image before go-live and keep local/system UIDs strictly below your LDAP range.
  • Nested groups. Plain posixGroup has no native nesting — memberUid lists are flat. If you need "group of groups" semantics, you need groupOfNames/groupOfUniqueNames with recursive resolution, which not every consumer (including some old NSS/PAM stacks) understands. Test group-of-groups resolution explicitly before relying on it for Slurm QOS mapping.
  • Referral loops. Misconfigured olcReferral or chained referrals between replicas can cause clients to bounce between servers indefinitely, especially after a topology change. Disable unnecessary referrals on read replicas and test failover paths, not just the happy path.
  • LDAPS cert trust issues. A self-signed or internal-CA cert that isn't distributed to every node's trust store causes silent auth failures that look like "LDAP is down" when it's actually a TLS handshake rejection. Push your CA cert via configuration management to every node image, not just the ones you remembered to test on.
  • Clock skew. If you layer Kerberos on top later (FreeIPA does this by default), clocks more than ~5 minutes out of sync between a node and the KDC will silently break authentication. Get NTP/chrony solid before LDAP/Kerberos go live.
