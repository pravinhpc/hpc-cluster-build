19 — CSP Comparison: AWS vs. GCP vs. Azure vs. OCI for GPU Clusters

The previous four sections walked through building a GPU HPC/AI cluster on each hyperscaler individually. This page puts them side by side. The short version: all four offer credible paths to a multi-thousand-GPU cluster with a modern NVIDIA generation and a purpose-built cluster-networking fabric, but they differ meaningfully in which GPU generations ship first, what the interconnect is actually called and how it's implemented, which tool sits at the center of the build, and how storage and pricing are structured. None of the four is a wrong choice in the abstract — the right one depends on your workload shape, your existing cloud footprint, and how much you value a single opinionated toolchain versus low-level control.

How to read this page
This is a comparison, not a ranking. Each CSP's own build-out section (linked below) covers the mechanics in depth — this page exists to help you decide which one to start with, or how to reason about running more than one.

Compute: GPU Generations and Representative Shapes

All four CSPs now offer Hopper (H100/H200) generally, and all four have Blackwell (B200/GB200/GB300) shipping or in fast rollout as of mid-2026. The differences are in exact instance/shape naming and in how the GPUs are packaged — individual 8-GPU nodes vs. rack-scale NVLink domains (GB200/GB300 NVL72, spanning up to 72 GPUs in one NVLink domain).

CPU Pairing

Host CPUs are overwhelmingly x86 (Intel Xeon or AMD EPYC, generation tied to the GPU platform generation) across all four clouds for GPU-attached nodes — the GPU is the bottleneck resource, so host CPU choice is mostly fixed by the reference design rather than customer-selectable. The one structural exception is the GB200/GB300 NVL72 rack-scale platform (offered by all four CSPs in some form), which pairs each Blackwell GPU pair with an NVIDIA Grace ARM CPU rather than x86 — this is a platform-level choice (Grace-Blackwell superchip), not a per-CSP option. Outside of GB200/GB300, ARM host options exist on all four clouds (Graviton on AWS, Axion on GCP, Cobalt on Azure, Ampere A1 on OCI) but are used for general-purpose/CPU-only fleets, not paired with H100/H200/B200 GPU nodes.

Primary Cluster-Build Tooling

CSPPrimary toolModel
AWSAWS ParallelClusterOpen-source, CLI/config-driven; wraps CloudFormation to stand up head node, Slurm, fabric, and storage together; now supports P6e-GB200/P6-B200
GCPCluster Toolkit (formerly Cluster Toolkit for Slurm / "cloud-hpc-toolkit")Terraform-based blueprints; composes VPC, GPUDirect config, filesystem, and Slurm/GKE into a single deployable spec
AzureCycleCloud (plus CycleCloud Workspace for Slurm)GUI + API-driven cluster lifecycle manager; provisions Slurm/PBS/Grid Engine clusters with autoscaling on top of ND-series VMs
OCIOCI HPC / Cluster Networking stack via Terraform (OCI Resource Manager + community Terraform modules)More do-it-yourself than the other three: Terraform stands up bare metal instances, RDMA cluster network, and block/file storage; Slurm bring-up is typically layered on separately

All four tools ultimately do the same job — turn a declarative spec into a running Slurm (or Kubernetes) cluster with fabric and storage wired up — but they sit at different points on the "opinionated product" to "composable infrastructure-as-code" spectrum. ParallelCluster and CycleCloud lean toward turnkey; Cluster Toolkit and OCI's Terraform-first approach lean toward composable.

Storage

CSPHigh-performance parallel FSGeneral-purpose managed storage
AWSAmazon FSx for LustreS3 (object), EBS (block), FSx for OpenZFS
GCPParallelstore (Lustre-based, DAOS-derived)Cloud Storage (object), Filestore (NFS), Persistent Disk (block)
AzureAzure Managed LustreAzure NetApp Files (NFS/SMB), Blob Storage (object), Managed Disks (block)
OCIOCI File Storage (NFS) at scale, plus third-party parallel FS (Lustre, WEKA) deployable on bare metalObject Storage, Block Volumes

All four support mounting a parallel filesystem across the compute fleet for checkpoint and dataset I/O; the practical difference is how "native" the offering is. FSx for Lustre and Parallelstore are the most turnkey, purpose-built managed parallel filesystems; Azure Managed Lustre is newer to general availability; OCI leans more on customer-deployed parallel filesystems atop its high-throughput File Storage and block storage primitives.

Pricing Model

The commercial models look superficially similar (on-demand, reserved/committed-use, spot/preemptible) but the discount depth and capacity guarantees differ:

CSPOn-demandCommitted/reservedSpot equivalent
AWSStandard hourlySavings Plans, Reserved Instances, Capacity Blocks for ML (short-term capacity reservation for GPU instances)EC2 Spot — steep discount, can be reclaimed
GCPStandard hourlyCommitted Use Discounts (CUDs), Dynamic Workload Scheduler / Flex-start & Calendar mode for GPU capacitySpot VMs
AzureStandard hourly (pay-as-you-go)Reserved Instances, Savings PlansSpot VMs
OCIStandard hourly (and notably, OCI dropped all outbound data-transfer/egress charges across its full footprint in early 2026)Annual/multi-year Universal Credits and capacity reservationsPreemptible capacity (more limited than the other three)

Egress cost is the sleeper issue in this table: moving trained checkpoints or datasets between clouds, or serving inference traffic out to the internet, is billed per-GB on AWS, GCP, and Azure and can dominate a multi-cloud bill; OCI's zero-egress policy is a genuine differentiator for teams that expect to move a lot of data out.
