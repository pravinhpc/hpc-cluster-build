05 — Cluster Provisioning with xCAT

xCAT (Extreme Cloud Administration Toolkit) is the grandparent of open-source cluster provisioning. Before Warewulf, before Bright Cluster Manager, xCAT was already turning racks of bare metal into working clusters — and it's still doing that job today, on everything from small university clusters to some of the largest supercomputers on the planet.

What is xCAT, really?

xCAT started life inside IBM in the early 2000s as an internal tool for deploying large Linux clusters, and IBM later open-sourced it. It's now community-maintained on GitHub (xcat2/xcat-core) and is free to use — no license fee, no vendor lock-in. Think of it as a toolbox of Perl-based commands, a database of "what every node should look like," and a set of network services (DHCP, TFTP, DNS) glued together so that powering on a bare-metal server results in a fully configured, cluster-ready node with zero manual OS installs.

Where BCM (covered in the previous section) is a polished, commercially-supported product with a GUI and a single vendor behind it, xCAT is the opposite philosophy: command-line first, fully scriptable, free, and community-driven. It's popular in HPC shops — including several IBM Power/GPU systems and many university and national-lab clusters — precisely because it doesn't hide anything behind a UI. Everything xCAT does, you can also do by hand by reading its database tables and scripts.

Why this matters
Once you understand xCAT, you understand the mechanics that every other provisioning tool (BCM, Warewulf, Foreman, MAAS) is really automating under the hood: DHCP hands out an IP, PXE loads a boot image over TFTP, and an installer or a diskless image turns that bare machine into a named, configured cluster node. xCAT just makes those mechanics explicit.

Core concepts

The management node

Every xCAT cluster has one (or a hierarchy of) management node(s) — the server that runs the xCAT daemon (xcatd), hosts the database, and provides DHCP/TFTP/HTTP/DNS services to the rest of the cluster. On larger clusters, xCAT supports a hierarchical setup with service nodes that offload provisioning traffic for a rack or a pod, so the single management node doesn't become a bottleneck when 500 nodes PXE-boot at once.

Node objects and database tables

xCAT stores cluster state in a relational database (SQLite by default, or PostgreSQL/MySQL for larger sites) organized into tables. You rarely edit these tables directly — you use commands like mkdef, chdef, and lsdef — but it helps to know the key ones:

TablePurpose
nodelistMaster list of node names, groups, and status — the root of "does this node exist."
nodetypeWhat OS/architecture/provisioning method (os, arch, profile, provmethod) each node uses.
nodehmHardware management settings — power control method, console method (mgt, cons).
macMAC address to node name mapping, used by DHCP.
chainThe post-boot "chain of custody" — what happens right after install (run a postscript, boot to disk, run another script, etc).
postscriptsWhich postscripts run on which nodes/groups after OS deployment.

A node in xCAT is a formal object — you can inspect it in full with lsdef, exactly like kubectl describe for a Kubernetes pod. This object model is what makes xCAT scriptable: everything is text in, text out.

Stateful vs. stateless (diskless) provisioning

xCAT supports both major provisioning models, and picking between them is one of the first design decisions on any build:

  • Stateful (diskful): a normal OS install to local disk, done via a scripted installer — Anaconda kickstart for RHEL/Rocky/CentOS, or AutoYaST for SUSE. The node reboots into a persistent local OS, just like installing Linux on a laptop. Changes persist across reboots.
  • Stateless (diskless): the entire root filesystem is built once on the management node into an image, compressed, and shipped to compute nodes at every boot. The node loads it into RAM (via tmpfs/ramdisk, optionally with a small persistent "statelite" overlay for a handful of directories) and runs from memory. Nothing is written to local disk, so every reboot returns the node to an identical, known-good state — extremely useful for large HPC fleets where node drift is the enemy.
Rule of thumb
Stateless is popular on large GPU/HPC compute fleets because it eliminates configuration drift and makes node replacement trivial — just PXE boot a spare node with the same image. Stateful is often kept for management nodes, login nodes, or storage nodes that need real persistent local state.

osimage — the deployment blueprint

An osimage is an xCAT object that ties together everything needed to deploy a node: the OS distribution, architecture, provisioning method (install, netboot, statelite), the kickstart/autoyast template, the package list, and (for diskless) the path to the built root image. You typically start from a sample osimage created by copycds when you import an ISO, then clone and customize it.

The PXE/DHCP/TFTP flow

This is the plumbing that makes "power on and it installs itself" possible:

  1. Compute node powers on, NIC issues a DHCP request on the network xCAT manages.
  2. xCAT's DHCP service (configured via makedhcp) recognizes the node's MAC address (from the mac table) and hands back an IP plus the location of a PXE/TFTP bootloader.
  3. The node's NIC firmware fetches that bootloader over TFTP and loads a boot kernel + initrd — for stateful installs this launches the OS installer; for stateless it mounts and boots the packed root image over HTTP/NFS.
  4. xCAT's DNS service (via makedns) and hosts table keep hostname resolution consistent across the cluster as nodes come online.
  5. Once installed (or netbooted), postscripts run to apply final configuration — join Slurm, set up SSH keys, configure NTP, etc.

Step-by-step: building a cluster with xCAT

Step 1 — Install xCAT on the management node

xCAT ships as RPM/deb repositories for RHEL/Rocky, SLES, and Ubuntu. On a RHEL-family management node:

wget https://xcat.org/files/xcat/repos/yum/latest/xcat-core/xcat-core.repo -P /etc/yum.repos.d/
wget https://xcat.org/files/xcat/repos/yum/xcat-dep/rh8/x86_64/xcat-dep.repo -P /etc/yum.repos.d/
yum install xCAT

source /etc/profile.d/xcat.sh   # loads xCAT commands into PATH
xcatconfig -c                    # initial configuration

This installs the xCAT daemon, the default SQLite database, and the full command suite (nodels, lsdef, mkdef, nodeset, rpower, and friends).

Step 2 — Define your nodes

Nodes can be defined individually with mkdef, or bulk-added from a CSV/range with nodeadd. A typical single-node definition, giving xCAT everything it needs for hardware management, network boot, and provisioning:

# Define one compute node
mkdef -t node cn01 groups=compute,all \
  arch=x86_64 \
  mgt=ipmi bmc=10.4.14.51 bmcusername=ADMIN bmcpassword=admin \
  mac=6C:AE:8B:1B:E8:52 \
  netboot=xnba \
  ip=10.1.1.51 interface=eth0 \
  provmethod=rocky9.3-x86_64-install-compute

# Or bulk-add a range of nodes from a stanza/definition file
nodeadd cn[01-64] groups=compute,all

# Inspect what you just created
lsdef cn01
nodels compute
Tip
groups=compute,all matters — most later commands (nodeset, rpower, xdsh) can target a whole group at once instead of naming every node.

Step 3 — Create and customize an osimage

Import an OS ISO to auto-generate baseline osimage definitions, then clone and tailor one for your compute nodes:

# Import ISO media, generates sample osimage defs automatically
copycds /path/to/Rocky-9.3-x86_64-dvd.iso

# List what got created
lsdef -t osimage

# Inspect and customize the install-based (stateful) image
lsdef -t osimage rocky9.3-x86_64-install-compute
chdef -t osimage rocky9.3-x86_64-install-compute \
  pkglist=/opt/xcat/share/xcat/install/rh/compute.rocky9.pkglist

# For a stateless (diskless) image instead:
lsdef -t osimage rocky9.3-x86_64-netboot-compute
genimage rocky9.3-x86_64-netboot-compute       # builds the root image
packimage rocky9.3-x86_64-netboot-compute      # compresses it for netboot

Step 4 — Set up DHCP, TFTP, and DNS

# Generate DHCP config for the management network and restart the service
makedhcp -n
makedhcp -a

# Generate /etc/hosts and DNS zone files for all defined nodes
makedns -n

makedhcp -n writes the DHCP config based on your network definitions (networks table); makedhcp -a adds all node MAC/IP reservations. makedns keeps hostname resolution in sync so every service — Slurm, monitoring, SSH — agrees on node names.

Step 5 — Provision the nodes

# Tell xCAT what should happen on next boot for this group
nodeset compute osimage=rocky9.3-x86_64-install-compute

# Power the nodes on (or reboot) to kick off PXE boot + install
rpower compute boot

# Watch console output live while it installs
rcons cn01

# Poll progress across the group
nodestat compute

For stateless nodes, the equivalent is nodeset compute osimage=rocky9.3-x86_64-netboot-compute followed by the same rpower compute boot — the node now nets-boots straight into RAM every time instead of installing to disk.

Step 6 — Post-install configuration and Slurm integration

Postscripts are shell/Perl scripts stored on the management node and run on the node right after deployment (and optionally on every boot for stateless nodes). Associate them via the postscripts table or chdef:

# Attach postscripts to the compute group
chdef -t group compute -p postscripts=configureslurm,syncntp,confignfs

# Push out an ad-hoc command/script to a live group right now (no reboot needed)
xdsh compute "systemctl restart slurmd"
xdcp compute /etc/munge/munge.key /etc/munge/munge.key

A typical configureslurm postscript installs the Slurm compute daemon, writes slurm.conf/gres.conf (for GPU nodes), copies the Munge auth key from the management node, and enables/starts slurmd — completing the hand-off from "bare metal" to "member of the job scheduler," which is the topic of a later section in this guide.

xCAT vs. BCM vs. Warewulf — a quick gut check

ToolModelStrengthsTrade-offs
xCATFree, open-source, CLI/DB-drivenExtremely flexible, mature (20+ yrs), scales to huge/hierarchical clusters, no license costSteeper learning curve, no polished GUI, community support only (unless via IBM/vendor contract)
BCM (Bright)Commercial, GUI + CLITurnkey experience, vendor support, integrated monitoringLicense cost, more opinionated/less transparent internals
WarewulfFree, open-source, lightweight, container-image basedSimple mental model, fast for stateless-first clusters, modern OCI-image workflowSmaller ecosystem than xCAT for complex hardware management (power/console) at very large scale
Watch out
xCAT's flexibility is also its biggest trap for newcomers: because almost everything is configurable at the table level, it's easy to end up with an undocumented, hand-tuned management node that only one person understands. Keep your node definitions, osimages, and postscripts in version control from day one.
