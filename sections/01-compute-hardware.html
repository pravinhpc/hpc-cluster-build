01 — Compute & Hardware Layer

Before a single job scheduler or network switch enters the picture, an HPC cluster is a room full of physical machines. This section covers what those machines actually are: the difference between CPUs and GPUs, what's inside a modern GPU compute node, how GPUs talk to each other inside and outside a box, the "other" nodes a cluster needs besides the flashy GPU ones, and the power and cooling realities that shape every design decision.

CPU vs. GPU: two different jobs

A CPU (Central Processing Unit) is built for general-purpose, low-latency, sequential-heavy work: a handful of very fast, very smart cores (typically 32–128 per socket in modern server chips) that excel at branching logic, orchestration, I/O, and running an operating system. A GPU (Graphics Processing Unit) is built for massive parallelism: thousands of simpler cores that all execute the same kind of math at once — ideal for the matrix multiplications that dominate both traditional scientific simulation (climate models, computational fluid dynamics, molecular dynamics) and modern AI training/inference.

In a real cluster these roles are complementary, not competing. The CPU (often called the "host") handles the operating system, data staging, job scheduling hooks, and feeding data to the GPUs. The GPUs (the "device") do the heavy numerical lifting. This is why almost every GPU compute node is really a CPU+GPU hybrid — for example, the NVIDIA GB200 Grace Blackwell Superchip pairs a 72-core Grace CPU with two B200 GPUs on the same module, connected by a high-bandwidth NVLink-C2C chip-to-chip link so the CPU can feed the GPUs without a slow PCIe hop.

Rule of thumb
CPU-only nodes are the right choice for workloads that are memory-latency-bound, branchy, or don't parallelize well (traditional CFD solvers, some genomics pipelines, pre/post-processing). GPU nodes win when the workload is dense linear algebra at scale — nearly all AI training/inference, and an increasing share of simulation codes that have been rewritten to use GPU-accelerated libraries.

Anatomy of a modern GPU compute node

The reference point most cluster builders use is NVIDIA's DGX/HGX class 8-GPU node. A DGX H100, for example, packs:

Newer generations (B200, GB200 NVL72) push these numbers further — see the NVLink comparison table below — but the shape of the box is the same: a handful of CPU sockets acting as traffic controller, a bank of GPUs doing the math, fast local NVMe for staging data, and multiple network interfaces separating GPU-to-GPU traffic, storage traffic, and management traffic onto different physical paths.

Field note
Local NVMe on a compute node is not your parallel filesystem. It's ephemeral scratch — great for checkpoint staging or dataset caching close to the GPU, but it disappears (or gets wiped) when the node is reimaged or reassigned. Section 06 (Storage) covers where the durable data actually lives.

NVLink/NVSwitch (intra-node) vs. inter-node fabric

It's easy to conflate "the network" as one thing, but a GPU cluster actually has (at least) two distinct interconnects with very different jobs:

NVLink + NVSwitch (intra-node / intra-rack)

A proprietary, very high-bandwidth, low-latency mesh that lets every GPU in a node (or in a GB200 NVL72 rack) talk to every other GPU as if they shared memory. This is what makes an 8-GPU server — or a 72-GPU rack — behave like one giant accelerator for model-parallel workloads.

Inter-node fabric (InfiniBand / RoCE Ethernet)

Standard networking (covered in depth in Section 02) that connects one node's NICs to the next node's NICs across the cluster. Bandwidth per link is far lower than NVLink, and latency is higher — so cluster software tries hard to keep tightly-coupled communication inside the NVLink domain and only cross the network fabric when it has to.

Why this matters
A single NVLink connection moves roughly 10–25x more data per second than a PCIe 5.0 link, and the NVSwitch fabric lets that happen non-blocking, any GPU to any GPU. That's the entire reason NVLink domains (a single node, or a full NVL72 rack) are treated as one scheduling unit for large model training — splitting a tightly-coupled job across an NVLink boundary onto plain network fabric is usually a major performance cliff.

Node roles in a real cluster

A production HPC/AI cluster is not just racks of identical GPU boxes. It's a mix of node types, each doing a distinct job:

Node typePurposeTypical hardware
Head / login nodeUser entry point — SSH access, job submission, compilers, module environmentModest CPU-only server, sometimes redundant pair
Management node(s)Runs the cluster manager, scheduler controller (Slurm/PBS), provisioning services, monitoringCPU-only, often virtualized/HA pair
Compute — CPU-onlyTraditional simulation, pre/post-processing, workloads that don't benefit from GPUsDual-socket high-core-count server
Compute — GPUAI training/inference, GPU-accelerated simulationDGX/HGX-class 4-8-GPU nodes, or GB200/GB300 NVL72 rack-scale units
High-memory nodeIn-memory analytics, genomics assembly, some pre-processing jobs needing huge RAMCPU node with 4-8+ TB RAM
Storage nodeServes the parallel filesystem (Lustre/GPFS/WEKA) to the rest of the clusterHigh core count + large NVMe/HDD arrays + fast NICs, minimal/no GPU

The single biggest sizing mistake in a first-time cluster design is treating everything as "GPU node." Login, management, and storage nodes are cheap relative to GPU nodes but are load-bearing — a badly under-resourced login or storage node throttles every user on the cluster regardless of how many GPUs sit idle.

BMC, IPMI, and Redfish: managing hardware when the OS is down

Every server in the cluster — compute, storage, login, management — has a small, independent computer bolted onto the motherboard called a BMC (Baseboard Management Controller). It has its own firmware, its own network port, and often runs on standby power even when the main server is fully powered off. This is what lets an operator power-cycle a frozen node, watch boot output, mount a virtual ISO, or pull sensor data (temperature, fan speed, power draw) without ever touching the primary OS or network.

IPMI

The older, widely-supported standard (IPMI 2.0) for platform management: power control, sensor data, System Event Log, Serial-over-LAN. Simple, ubiquitous, but limited in data format and security model.

Redfish

A modern DMTF standard (DSP0266) — a RESTful, HTTPS-based API returning JSON, purpose-built to be scriptable, multivendor, and secure at scale. Most current-generation servers (including NVIDIA DGX and OEM GPU nodes) expose Redfish alongside or instead of legacy IPMI.

Tip
Out-of-band (BMC/Redfish) networking should be a physically or at least VLAN-isolated network, separate from both the compute fabric and the storage fabric. This is what lets you reboot or reimage a node — or diagnose why it went unresponsive — even when its primary network path is completely broken.

Power and cooling: the constraint everything else lives inside

Modern GPU nodes are power-dense in a way traditional CPU-only servers never were. A single DGX H100 draws roughly 10.2 kW; a GB200 NVL72 rack draws well over 100 kW. That changes the physical building requirements, not just the IT design.

Air cooling

Standard for CPU-only and lower-density GPU racks. Works fine up to roughly 15-20 kW per rack with good hot-aisle/cold-aisle containment. Beyond that, air alone can't move heat fast enough.

Liquid cooling

Direct-to-chip liquid cooling (cold plates on CPUs/GPUs, connected to a facility water loop via CDUs — Cooling Distribution Units) is now standard for high-density GPU racks like GB200 NVL72, which are liquid-cooled by design and cannot be reasonably air-cooled at their power density.

At a high level: the denser the compute (more GPUs, more NVLink bandwidth, tighter integration), the higher the power draw per rack, and the more the facility has to shift from air handlers to chilled-water loops. This is a datacenter facilities decision as much as an IT one, and it needs to be made before racks are ordered, not after.

The practical takeaway: don't buy one node type and force every workload onto it. A well-designed cluster mixes GPU nodes (often the majority of the budget), CPU-only nodes, high-memory nodes, and storage nodes — each sized for the job it actually does, tied together by the networking and software layers covered in the next sections.
