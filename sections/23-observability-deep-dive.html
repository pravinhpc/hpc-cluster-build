23 — Observability Deep-Dive: Metrics, Logs, Traces at Fleet Scale

Section 12 covered the basics — DCGM, Prometheus, Grafana on a single cluster. This section goes further: how observability holds together once you're running many clusters, many thousands of GPUs, and a metrics/logs pipeline that has itself become infrastructure you have to capacity-plan and operate.

The three pillars, applied to HPC

Observability is usually described as three pillars — metrics, logs, and traces — and each maps onto HPC slightly differently than it does in a typical web-service stack.

Metrics

Numeric time series: GPU utilization, temperature, power, XID counts, fabric error counters, job queue depth. This is the pillar HPC leans on hardest — it's cheap to store, cheap to alert on, and DCGM already emits it natively.

Logs

Unstructured or semi-structured text: dmesg/XID lines, slurmctld/slurmd daemon logs, syslog, driver messages. This is where the "why" behind a metric threshold crossing usually lives.

Traces

The least common pillar in HPC. Distributed tracing was built for request-scoped microservices, and most HPC jobs aren't shaped like that — but it has a real, narrower role, covered below.

The practical shift at fleet scale isn't adding a new pillar — it's that each existing pillar stops being something one machine can hold. A single Prometheus server, a single Loki instance, and a single Grafana dashboard set all hit structural ceilings once you're running more than a handful of clusters.

Scaling Prometheus beyond one cluster

Prometheus was designed as a single-node, pull-based system, and that design holds up well within one cluster. Across clusters, two approaches exist, and they solve different problems.

Federation — one Prometheus server scrapes an aggregated /federate endpoint on other Prometheus servers — was the original answer, but it doesn't scale past a handful of clusters. It only pulls pre-aggregated series (not raw data), it adds its own scrape latency, and it was never designed as a global query layer. Most teams today treat federation as fine for small setups and a liability once you want raw multi-cluster queries, long retention, or a single pane of glass over dozens of clusters.

The better-scaling pattern is remote_write: each cluster's Prometheus keeps doing what it's good at — scraping and short-term local storage — and continuously ships every sample to a horizontally scalable, object-storage-backed backend. The two dominant choices:

Grafana Mimir

A "metrics warehouse" — Prometheus, Grafana Alloy, or an OpenTelemetry Collector remote-writes into it, and Mimir owns the write path, tenant limits, replication, long-term storage blocks, and query serving. Good fit for a new multi-team, multi-cluster platform built from scratch.

Thanos

Extends Prometheus from the outside rather than replacing it — a sidecar uploads each Prometheus's TSDB blocks to object storage, and a Querier component federates queries across all of them plus a global store. Good fit when you already have a working per-cluster Prometheus fleet and want global query + long retention layered on top without ripping anything out.

Both give you a single PromQL endpoint across every cluster, which is what lets one Grafana dashboard show fabric-level utilization across five geographically separate clusters simultaneously. Sharding matters once ingestion volume grows: Mimir and Thanos Receive both support horizontally sharding the write path across multiple ingester replicas, keyed by tenant or by series hash, so no single ingestion node becomes the bottleneck as node count grows into the thousands.

DCGM deep dive: field IDs and diagnostic levels

Every metric DCGM exposes is addressed by a numeric field ID (for example, DCGM_FI_DEV_GPU_UTIL is field 203, DCGM_FI_DEV_GPU_TEMP is field 150). dcgm-exporter's default and custom metric-list files simply enumerate which field IDs to scrape and expose — this is the mechanism that lets an operator add NVLink or NVSwitch topology counters to Prometheus without touching DCGM itself, just the exporter's config map.

DCGM's active diagnostic (dcgmi diag -r <level>) runs at four increasing levels of intrusiveness:

LevelApprox. durationWhen to run it
1< 2.5 secondsQuick readiness check — safe to run before every job dispatch
2~2.5–10 minutes (4 vs 8 GPU systems)Post-failure epilogue — run automatically after a job fails or a node throws an XID
3~5 minutes (includes End User Diagnostics)Administrator-run post-mortem, typically during node draining
4~20 minutesDeepest stress test — used to clear a node for RMA or confirm a suspected marginal GPU

NVLink and NVSwitch topology metrics (link bandwidth, CRC error counts, replay counters) are exposed through their own field IDs as well, and are what let a fabric-health dashboard distinguish "this node's aggregate NVLink bandwidth dropped" from "one specific link on one specific NVSwitch is degraded" — a distinction that matters enormously for multi-node NVLink-domain training jobs where a single bad link can silently bottleneck an entire job.

Where distributed tracing fits in HPC

Classic distributed tracing (Jaeger, Zipkin, OpenTelemetry traces) exists to follow a single request as it hops across dozens of microservices. Most HPC workloads — a multi-day training job holding a fixed GPU allocation — don't have that request-scoped shape, which is why tracing is the least-adopted pillar here. But it does have a real niche: profiling collective communication inside a distributed training job. Tools like NVIDIA Nsight Systems and NCCL's own profiling hooks can produce trace-like timelines showing exactly how long each rank spent in an all-reduce, where stragglers appear, and whether a specific node's NVLink or IB path is the one holding up the whole collective. It's a narrower, HPC-flavored form of tracing — span-per-collective-op rather than span-per-microservice-hop — but the underlying idea (causally-ordered timing data instead of aggregated metrics) is the same.

Log aggregation and correlating a single job

The hard part of log aggregation at fleet scale isn't ingestion — it's correlation. A single degraded-node incident can be scattered across slurmctld's log (job was scheduled here), slurmd's log on the node (job started, then the node was drained), dmesg/syslog (the actual XID event), and DCGM's own event stream — four sources, one incident, and no shared identifier unless the pipeline is built to carry one through. Structured logging — every log line emitted as JSON with consistent fields like job_id, node, cluster, and timestamp — is what makes that correlation a single query instead of four manual greps across four machines.

Grafana Loki and the ELK/OpenSearch stack solve this the same way conceptually but at different cost points: Loki indexes only labels (not full text), which keeps storage cheap and pairs naturally with a Prometheus/Grafana stack already using the same label model; ELK/OpenSearch indexes full text, which costs more to store and run but supports richer ad-hoc search — a better fit when logs also need to serve security or audit investigations.

SLOs and SLIs for a GPU fleet

Borrowing from the SRE discipline: an SLI is a measured indicator (a ratio of good outcomes to total valid outcomes), an SLO is the target value for that indicator, and an error budget is simply 1 minus the SLO — the amount of "badness" you're allowed before you're out of compliance. A few SLIs that map cleanly onto a GPU fleet:

SLIExample SLOWhat it protects against
GPU availability %99.5% of allocated GPU-hours are on healthy, non-drained GPUsSilent capacity loss from drained/failed nodes
Job success rate99% of jobs complete without an infrastructure-caused failureDistinguishes user code bugs from platform reliability
Mean time to detect (MTTD) a degraded node< 5 minutes from first anomalous signal to alert firedTime a bad node sits in the scheduling pool silently wasting GPU-hours

Reference architecture

Each cluster keeps its own short-term Prometheus and Loki for local resilience — a network partition to the central backend shouldn't blind local operators to a local fire — while a central Mimir/Thanos and Loki pair provides the long-term, cross-cluster query surface that a single Grafana instance and a single Alertmanager sit on top of.

Capacity planning the observability stack itself

The observability stack is infrastructure too, and it needs its own capacity plan. As a rough planning heuristic: a GPU node emitting ~200 active DCGM series plus ~50 node-level series, scraped every 15 seconds, generates roughly 15-20 samples/second per node. At 2,000 nodes that's on the order of 30,000-40,000 samples/second flowing into remote_write — well within a modestly-sized Mimir or Thanos ingester tier, but the number to watch isn't raw throughput, it's cardinality: every additional label value (per-GPU, per-job, per-NVLink-port) multiplies the series count, and storage/memory cost scales with active series far more than with sample rate. Log volume is harder to estimate generically — it depends heavily on log verbosity settings — but a fleet-wide Loki deployment sized for a few hundred MB/day per 100 nodes of structured logs is a reasonable starting point to validate against actual ingestion once agents are deployed.
