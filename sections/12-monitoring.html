12 — Monitoring & Observability: DCGM, Prometheus, Grafana

A cluster you can't see is a cluster you can't trust. This section covers how operators watch thousands of GPUs, fabrics, and nodes in real time — and how they find out about a failure before an angry researcher does.

Why observability matters at HPC scale

A single DGX or workstation is easy to babysit — you can just glance at nvidia-smi. A cluster with hundreds or thousands of GPU nodes is a different animal entirely. At that scale, failures aren't rare edge cases — they're a daily occurrence, and the job of a monitoring stack is to make them visible, attributable, and actionable before they silently waste GPU-hours.

Here's what operators specifically need to see, continuously, across the whole fleet:

Health signals

  • GPU utilization — are GPUs actually doing work, or idling while a job "runs"?
  • XID errors — the NVIDIA driver's error-code channel for GPU-level faults (ECC errors, Xid 79 "GPU fallen off the bus", Xid 63/64 row-remap events, etc.)
  • Thermal throttling — GPUs silently downclock when they overheat, tanking throughput without crashing anything
  • Fabric health — InfiniBand/RoCE link flaps, NVLink errors, NVSwitch faults
  • Node failures at scale — with 1,000+ nodes, something is always down; the question is whether you know about it in minutes or in a support ticket three days later

Accounting signals

  • Job-level GPU efficiency — is a Slurm job actually saturating its allocated GPUs, or paying for idle silicon?
  • Queue and scheduler health — pending job backlog, drained nodes, reservation conflicts
  • Capacity trends — utilization over weeks/months to justify (or defer) the next cluster expansion
  • Cost attribution — which team/project consumed which GPU-hours

The pattern that has become the de facto standard for all of this — in HPC shops, hyperscalers, and NVIDIA's own MARS/DGX Cloud fleets alike — is: DCGM for GPU-native telemetry and health, Prometheus (plus a scalable remote-write backend) for metrics collection and storage, Grafana for dashboards, and Loki/ELK + Alertmanager for logs and paging. The rest of this section walks through each layer.

NVIDIA DCGM — Data Center GPU Manager

DCGM is NVIDIA's purpose-built toolset for managing and monitoring NVIDIA GPUs in server and cluster environments. It runs as a background daemon (nv-hostengine) on every GPU node and exposes telemetry, diagnostics, and health monitoring through a CLI (dcgmi) and client libraries. Think of it as the layer that turns raw GPU hardware counters into something a monitoring system can consume.

dcgmi — the command-line interface

The dcgmi tool is what operators reach for when SSH'd onto a node to triage a problem interactively. A few of the commands you'll use constantly:

# See a snapshot of all GPUs on this node
dcgmi discovery -l

# Set up a group of GPUs to watch, then check health
dcgmi group -c gpu_group --default
dcgmi health --set gpu_group -g pcie,mem,inforom,thermal,power,driver,nvlink
dcgmi health --check -g gpu_group

# Run the built-in active diagnostic suite (levels 1-4, level 3/4 stress the GPU)
dcgmi diag -r 3 -g gpu_group

# Dump live utilization / temperature / power metrics
dcgmi dmon -e 203,204,150,155 -c 5

DCGM's health monitoring module can passively watch for problems across PCIe, GPU memory, InfoROM, the driver, thermal/power behavior, NVLink, NVSwitch, and even attached ConnectX NICs — flagging warning or critical severity per-component without interrupting running jobs. The active diagnostic (dcgmi diag) is the tool you run between jobs, during node draining, or as part of a pre-flight health gate before a node re-enters the scheduler pool — levels 3 and 4 actually load the GPU and can catch marginal hardware that passive monitoring misses.

Common XID errors you will actually see
XIDMeaningTypical response
13Graphics engine exception (often a bad kernel/driver interaction)Usually benign in isolation; watch for repeats
31GPU memory page faultOften a user application bug; check the job's memory access pattern
48Double-bit ECC error (uncorrectable)Flag GPU for row-remapping / RMA if recurring
63 / 64Row-remapping event pending / failureNode needs a reset to apply the remap; recurring 64s mean the GPU is failing
74NVLink errorCheck fabric/NVLink topology and cabling/seating
79GPU has fallen off the busHardware failure — drain the node immediately, do not just reboot and hope
94 / 95Contained / uncontained ECC errorUncontained (95) can crash other processes sharing the GPU — drain and investigate

XID codes are logged to dmesg/syslog by the NVIDIA kernel driver. In a fleet monitoring stack, XID counts should always be scraped as a Prometheus metric and alerted on — a rising XID 79/95 rate is one of the highest-signal indicators of failing GPU hardware at scale.

DCGM Exporter — bridging DCGM to Prometheus

dcgm-exporter is NVIDIA's official Prometheus exporter built on top of DCGM's Go bindings. It runs as a lightweight daemon (typically one per GPU node, deployed as a Kubernetes DaemonSet via the GPU Operator, or as a systemd service on bare-metal Slurm nodes) and exposes an HTTP /metrics endpoint that Prometheus scrapes on a regular interval. It reports GPU utilization, memory utilization, temperature, power draw, SM clock, PCIe throughput, NVLink bandwidth/errors, XID error counts, ECC error counts, and — critically for job accounting — can label each metric with the Slurm/Kubernetes job ID that owns the GPU at scrape time, letting you build "GPU efficiency per job" dashboards directly from raw exporter data.

Prometheus architecture for cluster monitoring

Prometheus is a pull-based metrics system: it doesn't wait for nodes to push data at it, it goes and scrapes each node's /metrics HTTP endpoint on a schedule (typically every 15-30 seconds for GPU metrics). Every node runs one or more small "exporter" processes whose only job is to translate local state into Prometheus's text metrics format.

node_exporter

General Linux host metrics: CPU, memory, disk, filesystem, network interface counters. The baseline exporter on every node in the fleet, GPU or not.

dcgm-exporter

GPU-specific telemetry from DCGM, as described above. Runs only on GPU nodes.

Fabric / IB exporters

InfiniBand port counters (via ibstat/perfquery-based exporters) or switch-side SNMP exporters for RoCE fabrics — surfaces link flaps, CRC errors, and symbol errors before they become job failures.

The scale problem — and why remote_write exists

A single Prometheus server works fine for a small cluster, but it has two structural limits at HPC scale: it's a single point of failure, and its local TSDB (time-series database) is not built to retain years of high-cardinality GPU metrics from thousands of nodes efficiently. The standard fix is to keep Prometheus doing what it's good at — scraping and short-term local storage (hours to a couple of weeks) — and configure remote_write to continuously ship samples to a horizontally scalable, multi-tenant backend for long-term storage and global querying. The three common choices are Grafana Mimir (the actively developed successor to Cortex, object-storage-backed), Thanos (sidecar/receiver architecture also backed by S3/GCS-style object storage), and Cortex (largely superseded by Mimir today — most teams migrating off Cortex land on Mimir). All three speak the same remote-write protocol and give you a single global PromQL endpoint across every cluster in your fleet, which is what lets a Grafana dashboard show utilization across five geographically separate clusters at once.

Example scrape config and dcgm-exporter deployment

# prometheus.yml — scrape both node and GPU exporters, remote_write to Mimir
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: 'node_exporter'
    static_configs:
      - targets: ['gpu-node-001:9100', 'gpu-node-002:9100']
        labels:
          cluster: 'oci-nrt-cs-001'

  - job_name: 'dcgm_exporter'
    scrape_interval: 15s
    static_configs:
      - targets: ['gpu-node-001:9400', 'gpu-node-002:9400']
        labels:
          cluster: 'oci-nrt-cs-001'
    metric_relabel_configs:
      # keep GPU UUID + Slurm job id labels, drop noisy internal DCGM fields
      - source_labels: [__name__]
        regex: 'DCGM_FI_DEV_(GPU_UTIL|MEM_COPY_UTIL|GPU_TEMP|POWER_USAGE|XID_ERRORS|ECC_SBE_VOL_TOTAL|ECC_DBE_VOL_TOTAL|NVLINK_CRC_DATA_ERROR_COUNT_TOTAL)'
        action: keep

remote_write:
  - url: "https://mimir.internal.example.com/api/v1/push"
    queue_config:
      max_samples_per_send: 5000
      max_shards: 30
    tls_config:
      ca_file: /etc/prometheus/certs/ca.pem

# dcgm-exporter — quickest path: standalone container on a GPU node
docker run -d --restart=always --gpus all \
  --cap-add SYS_ADMIN \
  -p 9400:9400 \
  nvcr.io/nvidia/k8s/dcgm-exporter:3.3.9-3.6.1-ubuntu22.04

# curl its metrics endpoint directly to sanity-check before wiring Prometheus
curl -s localhost:9400/metrics | grep DCGM_FI_DEV_GPU_UTIL

Monitoring pipeline, end to end

Every node runs small exporter agents; Prometheus pulls their metrics on a schedule and forwards them to a long-term backend via remote_write; Grafana queries that backend for dashboards; Alertmanager evaluates rules against the same data and routes pages to PagerDuty; and a separate log pipeline (Promtail/Filebeat → Loki/ELK) handles unstructured text logs that never fit Prometheus's numeric time-series model.

Grafana dashboards

Grafana is the visualization layer that operators and end users actually look at. A production HPC monitoring stack typically ships several purpose-built dashboards rather than one giant one:

Fleet health dashboard

GPU utilization heatmap across every node/GPU in the cluster (see mockup below), aggregate XID error counts over the last 24h, count of nodes currently drained vs. healthy, thermal throttling events, and NVLink/fabric error rates. This is the "is anything on fire right now" view.

Job efficiency dashboard

Per-job GPU utilization and memory-bandwidth utilization over the job's lifetime, joined against Slurm job ID labels from dcgm-exporter. Lets a user (or their manager) see instantly whether a multi-day training job is actually using the GPUs it reserved, or leaving them idle waiting on I/O.

Typical panels: a heatmap panel for per-GPU utilization across the fleet, a time-series panel for XID error rate (alert threshold overlaid), a stat panel for "nodes currently unhealthy," a bar gauge for fabric link error counts per switch, and a table panel joining job ID → owning team → GPU-hours consumed for cost attribution.

Log aggregation basics

Prometheus metrics tell you that something is wrong (a number crossed a threshold); logs tell you why. Every node produces unstructured text — kernel messages (dmesg, which is where XID errors actually get written by the NVIDIA driver), syslog, and scheduler daemon logs like slurmctld.log/slurmd.log — and at fleet scale you need those centralized and searchable, not scattered across thousands of individual node filesystems.

Two common approaches:

Grafana Loki

Indexes only metadata labels (node, cluster, service) rather than full text, keeping storage costs low. Pairs naturally with Grafana and Prometheus since it uses the same label model and query ergonomics (LogQL mirrors PromQL). Promtail or the newer Grafana Alloy agent tails log files on each node and ships them to Loki. This is the lighter-weight, more Prometheus-native option and the common default in NVIDIA-style GPU cluster stacks.

ELK / OpenSearch

Elasticsearch (or OpenSearch) + Logstash/Filebeat + Kibana — full-text indexing of every log line, more powerful ad-hoc search and richer query DSL, but heavier on storage and compute. A better fit when logs need to support security/audit investigations or complex text search beyond label filtering.

Either way, the goal is the same: when Alertmanager fires "node-011 GPU 2 XID 79," the very next click should take an operator straight to that node's correlated dmesg output around the same timestamp — without SSH'ing in.

Alerting basics

Alertmanager is Prometheus's companion component for turning firing alert rules into notifications. Prometheus itself evaluates alerting rules (PromQL expressions with thresholds) on a schedule; when a rule's condition is true, it hands the alert to Alertmanager, which handles deduplication, grouping, silencing, and routing to the right notification channel — commonly PagerDuty for anything that needs a human paged at 3 a.m., and Slack for lower-severity/informational alerts.

# alertmanager rule examples (Prometheus rules.yml)
groups:
  - name: gpu-health
    rules:
      - alert: NodeDown
        expr: up{job="node_exporter"} == 0
        for: 2m
        labels: {severity: critical}
        annotations:
          summary: "{{ $labels.instance }} is unreachable"

      - alert: GPUFallenOffBus
        expr: increase(DCGM_FI_DEV_XID_ERRORS{xid="79"}[5m]) > 0
        labels: {severity: critical}
        annotations:
          summary: "XID 79 on {{ $labels.gpu }} at {{ $labels.instance }} — drain node"

      - alert: GPUThermalThrottle
        expr: DCGM_FI_DEV_GPU_TEMP > 85
        for: 10m
        labels: {severity: warning}
        annotations:
          summary: "{{ $labels.instance }} GPU {{ $labels.gpu }} sustained > 85C"

Routing these into PagerDuty is typically a matter of configuring an Alertmanager receiver with a PagerDuty integration key per severity tier — critical alerts (node down, XID 79/95, fabric fully down) page the on-call engineer immediately, while warnings (thermal creep, minor XID counts, single-link fabric degradation) route to a Slack channel for daytime triage instead of an interrupt at 2 a.m.
