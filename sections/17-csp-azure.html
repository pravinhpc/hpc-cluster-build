17 — CSP Build: Microsoft Azure

Everything earlier in this guide assumed you own the racks. On Azure, the physical layer — servers, InfiniBand fabric, power, cooling — is Microsoft's problem, and yours becomes VM sizing, fabric-aware placement, and orchestration software that turns a pool of virtual machines into a working Slurm or PBS cluster. This section covers the GPU VM families relevant to HPC/AI, Azure's InfiniBand story, and Azure CycleCloud — the tool most Azure-native GPU clusters are actually built with.

The GPU VM families that matter

Azure's HPC/AI compute lives in the ND-series (network-optimized, GPU-heavy, InfiniBand-attached). Three generations show up most often in current builds:

VM sizeGPUPer-GPU fabricNotes
ND H100 v58× NVIDIA H100 80GB400 Gbps NVIDIA Quantum-2 CX7 InfiniBand (dedicated NIC per GPU)Current flagship training SKU; NVLink 4.0 intra-node
NDm A100 v48× NVIDIA A100 80GB200 Gbps HDR InfiniBand (dedicated NIC per GPU)Previous-generation, still widely deployed; NVLink 3.0 intra-node
ND MI300X v58× AMD Instinct MI300XInfiniBand-attached, AMD Infinity Fabric intra-nodeAMD alternative for teams standardizing on ROCm

The pattern across all three: every GPU gets its own dedicated, topology-agnostic RDMA NIC rather than the GPUs sharing a handful of NICs, which is what lets multi-node NCCL/RCCL collectives scale close to linearly as node count grows.

InfiniBand on Azure

These VM sizes are deployed on an NDR/HDR InfiniBand fabric built and operated by Microsoft — you don't touch switches or cabling. What you're responsible for as the cluster builder is placement and drivers:

  • Placement groups / proximity — CycleCloud and the underlying scale set logic place nodes so their IB NICs land on the same non-blocking fabric segment; requesting nodes outside a single scale-set deployment can silently degrade to worse topology.
  • Driver stack — the InfiniBand NIC needs a matching OFED/driver version inside the VM image; Azure's HPC-flavored marketplace images (AlmaLinux-HPC, Ubuntu-HPC) ship this pre-tuned, which is why most CycleCloud templates start from one of them rather than a stock OS image.
  • SR-IOV passthrough — the IB NIC is exposed to the guest via SR-IOV, so MPI/NCCL inside the VM talk to it almost as directly as on bare metal.

Azure CycleCloud — the primary build tool

Azure CycleCloud is Microsoft's cluster orchestration product for HPC/AI on Azure. It's the rough equivalent of what BCM does on-prem (guide 04), but built around dynamic autoscale of cloud VMs rather than a fixed fleet of physical nodes:

  • Cluster templates define one or more nodearrays (e.g. a GPU compute array, a login/scheduler array), each mapped to a VM size, image, and network configuration.
  • Autoscale — nodearrays scale from zero; CycleCloud watches the scheduler's queue (Slurm, PBS, LSF, Grid Engine, HTCondor are all supported) and spins up or tears down VMs to match demand.
  • Scheduler integration is built in — the default Slurm template ships with three partitions (hpc, htc, dynamic) and pre-wires PMIx, Pyxis, and enroot so containerized AI jobs work out of the box.

Step-by-step: building a Slurm cluster with CycleCloud

Step 1 — Deploy the CycleCloud server

CycleCloud itself runs as a management VM (deployable from the Azure Marketplace or the CycleCloud Workspace for Slurm solution template) inside a VNet. It needs an Azure AD / Entra application registration and a managed identity with permission to create and delete VMs, disks, and NICs in the target subscription — this is what lets it actually scale the cluster.

Step 2 — Define the cluster template

A cluster template describes the nodearrays, VM sizes, image, and network placement. A minimal GPU Slurm template looks like this:

[cluster azure-gpu-slurm]
FormLayout = selectionpanel
Category = Schedulers

[[node defaults]]
Credentials = azure-subscription
SubnetId = $SubnetId
Region = $Region

[[nodearray hpc]]
MachineType = Standard_ND96isr_H100_v5
ImageName = microsoft-dsvm:ubuntu-hpc:2204:latest
MaxCoreCount = 768
Interruptible = false

  [[[configuration]]]
  slurm.autoscale = true
  slurm.partition = hpc

  [[[network-interface eth0]]]
  AssociatePublicIpAddress = false

  [[[cluster-init cyclecloud/slurm:execute]]]

[[nodearray login]]
MachineType = Standard_D8s_v5
MaxCoreCount = 8

  [[[cluster-init cyclecloud/slurm:scheduler]]]

Step 3 — Wire up the VNet and storage

Nodearrays reference a subnet inside a VNet you (or the Workspace solution template) provision ahead of time, typically with a dedicated subnet for compute so NSG rules and IB placement can be scoped tightly. Shared storage — Azure NetApp Files or Azure Managed Lustre — is mounted at boot time via the same cluster-init scripts that set up Slurm.

Step 4 — Import and start the cluster

The template is imported into CycleCloud (via the web UI or the cyclecloud CLI), started, and the scheduler nodearray boots first, followed by GPU nodes as jobs are submitted — CycleCloud provisions VMs on demand rather than holding them all warm.

Alternative paths: Azure Batch and AKS

CycleCloud isn't the only way to run GPU workloads on Azure:

  • Azure Batch — a managed job-scheduling service for embarrassingly parallel or batch workloads; good fit if you don't need a persistent Slurm-style cluster and just want to submit jobs against an autoscaling pool.
  • AKS (Azure Kubernetes Service) — GPU node pools on ND-series VMs, useful when the workload is already containerized and orchestrated as Kubernetes jobs rather than HPC scheduler jobs; InfiniBand support requires the same SR-IOV-aware images and device plugins as a VM-based cluster.

Most training-focused HPC/AI clusters still land on CycleCloud + Slurm because that's the path with the most mature InfiniBand-aware autoscale and topology placement; Batch and AKS are better fits when the workload model is already batch-job or Kubernetes-native.
