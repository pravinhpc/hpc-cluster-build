22 — Configuration Management with Puppet

Long before Ansible playbooks were the default answer to "how do I configure a fleet of Linux boxes," Puppet was the tool that popularized declarative, desired-state configuration management — and it's still running in production at a meaningful number of HPC centers today, particularly university and national-lab clusters with decades of institutional investment in it. Understanding Puppet's model matters even if you end up choosing Ansible, because the two tools represent genuinely different philosophies for the same problem: keeping a fleet of machines in a known-good state.

The core contrast: pull vs. push

Ansible, covered earlier in this guide, is agentless and push-based: a control node connects out over SSH and pushes configuration to targets on demand, when you run ansible-playbook. Nothing runs on the managed node between runs — there's no daemon, no periodic check-in, no local state.

Puppet is the opposite model: agent-based and pull-based. Every managed node runs a persistent puppet-agent service. On an interval (30 minutes by default), the agent wakes up, gathers facts about itself (via Facter), sends those facts to a central Puppet server, and asks for a catalog — a compiled, node-specific description of the desired end state. The agent then applies that catalog locally, converging the node toward the declared state, and reports back what it changed. Nobody has to remember to run anything; every node in the fleet is continuously and independently correcting its own drift on its own schedule.

That single architectural choice cascades into most of the practical differences between the two tools: Puppet needs a running server component and agent software installed everywhere, in exchange for continuous, unattended drift correction. Ansible needs nothing installed on targets, in exchange for configuration only happening exactly when you trigger it.

Core Puppet concepts

Manifests, modules, classes

Puppet configuration is written in its own declarative DSL, in .pp files called manifests. A manifest declares resources — packages, files, services, users — and their desired state ("this package should be installed," "this service should be running and enabled"), not the imperative steps to get there. Manifests are organized into modules, a standard directory layout (manifests/, files/, templates/, data/) that bundles related configuration into a reusable, shareable unit. Within a module, a class is a named, reusable block of Puppet code — the equivalent of an Ansible role — that gets declared by name wherever it's needed.

The catalog and compile process

When an agent checks in, the Puppet server doesn't just hand back raw manifest text — it compiles all the classes assigned to that specific node, resolves Hiera data lookups, evaluates any conditional logic, and produces a catalog: a static, fully-resolved, node-specific document listing every resource and its dependency order. The agent applies only that catalog. This compile step is where Puppet does the heavy lifting of turning generic, parameterized code into "what exactly should node X look like right now."

Hiera — separating data from code

Hiera is Puppet's built-in hierarchical key-value data lookup system. Instead of hardcoding values (package versions, NTP servers, Slurm cluster names) inside manifests, you look them up from external YAML files organized into a hierarchy — typically something like "per-node overrides → per-role → per-datacenter → global defaults" — configured in a hiera.yaml file. Puppet facts (hostname, OS, custom facts like a node's cluster role) drive which hierarchy level a given lookup checks first, following a "first match wins, with fallthrough to defaults" pattern. This is the same underlying idea as Ansible's group_vars/host_vars, just built into the language itself.

PuppetDB

PuppetDB is Puppet's storage and query layer: every agent run's facts, catalog, and report get stored there, queryable via its API or the puppet query command. It's what lets you answer fleet-wide questions like "which nodes are running an out-of-date kernel package" or "which nodes failed their last run" without SSHing anywhere.

r10k / Code Manager — deploying modules

r10k (and Puppet Enterprise's managed equivalent, Code Manager) is the tool that gets your Puppet code from a Git "control repository" onto the Puppet server. A control repo's branches map directly to Puppet environments (e.g. a production branch becomes the production environment), and a Puppetfile at its root pins exactly which module versions get pulled in from the Forge or other Git repos. Running r10k deploy environment syncs the server's on-disk environments to match what's declared in Git — the Puppet-world equivalent of a CI/CD deploy step.

Why HPC sites historically chose Puppet

Puppet predates Ansible by several years and had a multi-year head start building a mature module ecosystem (the Puppet Forge) and strong desired-state enforcement guarantees. Several traits made it attractive specifically for research-computing and university HPC centers: continuous drift correction meant a manually-patched node would self-heal back to policy within 30 minutes without anyone noticing the drift happened; the agent/master model scales well to large, heterogeneous fleets with long-lived infrastructure teams who could invest in learning the DSL; and because many national labs and universities adopted it early, there's a real body of public, reusable HPC-specific Puppet code — for example EDF's puppet-hpc generic HPC cluster stack, and the University of Luxembourg's puppet-slurm module for managing Slurm.

A realistic HPC module structure: roles and profiles

Almost every mature Puppet codebase — HPC or otherwise — converges on the same pattern, known as roles and profiles. A profile is technology-specific glue (how to configure Slurm, how to configure Munge, how to configure GPU drivers), while a role is business-specific: it composes one or more profiles into "what this class of machine actually is." Nodes are only ever assigned a role, never individual profiles directly, which keeps the node classification layer thin and stable while the implementation detail lives in profiles.

site/
├── roles/
│   └── manifests/
│       ├── compute_node.pp    # class roles::compute_node
│       └── login_node.pp      # class roles::login_node
└── profiles/
    └── manifests/
        ├── slurm.pp           # class profiles::slurm
        ├── munge.pp           # class profiles::munge
        └── gpu_drivers.pp     # class profiles::gpu_drivers

Example manifest + Hiera data

A role simply composes profiles; the profiles reference Hiera-supplied data rather than hardcoding it:

# site/roles/manifests/compute_node.pp
class roles::compute_node {
  include profiles::munge
  include profiles::slurm
  include profiles::gpu_drivers
}

# site/profiles/manifests/slurm.pp
class profiles::slurm (
  String $cluster_name    = lookup('profiles::slurm::cluster_name'),
  String $controller_host = lookup('profiles::slurm::controller_host'),
  Integer $slurmd_port     = lookup('profiles::slurm::slurmd_port', Integer, 'first', 6818),
) {
  package { 'slurm-slurmd': ensure => installed }

  file { '/etc/slurm/slurm.conf':
    ensure  => file,
    content => template('profiles/slurm.conf.epp'),
    require => Package['slurm-slurmd'],
  }

  service { 'slurmd':
    ensure  => running,
    enable  => true,
    require => File['/etc/slurm/slurm.conf'],
  }
}

# hiera.yaml
version: 5
hierarchy:
  - name: "Per-node overrides"
    path: "nodes/%{trusted.certname}.yaml"
  - name: "Per-role data"
    path: "roles/%{facts.role}.yaml"
  - name: "Common defaults"
    path: "common.yaml"

# data/roles/compute_node.yaml
profiles::slurm::cluster_name: "research-cluster-01"
profiles::slurm::controller_host: "slurm-ctrl-01.cluster.local"
profiles::slurm::slurmd_port: 6818
profiles::gpu_drivers::driver_version: "550.90.07"

Puppet vs. Ansible for HPC — tradeoffs

DimensionPuppetAnsible
Execution modelPull — agents check in on an interval and request a catalogPush — control node connects out and runs on demand
Node footprintPersistent puppet-agent daemon on every nodeNone — only SSH + Python required on targets
Drift handlingContinuous, automatic — drift self-corrects within one agent intervalOnly when you explicitly re-run a playbook
Data separationHiera, built into the languagegroup_vars/host_vars, inventory variables
Learning curveCustom declarative DSL, catalog/compile model to internalizeYAML + Jinja2 — generally faster to onboard new admins
Infrastructure neededPuppet server (or PE), PuppetDB, r10k/Code Manager pipelineNone beyond the control node itself
Best fitLong-lived fleets that benefit from unattended, continuous enforcementEnvironments that want zero agent footprint and full control over exactly when changes land
Why this matters
Neither model is strictly "better" — they optimize for different failure modes. Puppet trades agent overhead for hands-off drift correction; Ansible trades continuous enforcement for zero footprint and precise control over when changes are applied. Many sites that started on Puppet in the 2010s still run it today simply because the switching cost of re-platforming a mature, working control repo rarely clears the bar — while newer HPC builds increasingly default to Ansible for its lower operational surface area.
