11 — User Onboarding & Distribution Lists (DLs)

A cluster with perfect hardware and a flawless scheduler is still useless to a new hire who can't log in. Onboarding is the unglamorous plumbing that turns "I was told I have access" into an actual working shell prompt — and getting it wrong is one of the most common sources of week-one frustration on any HPC system.

Why cluster onboarding is harder than a normal web app

Signing up for a SaaS tool usually means: create an account, verify an email, done. Granting someone working access to an HPC cluster is a small stack of distinct systems that all have to agree with each other before a single srun command will succeed:

  • A Unix identity — a UID and GID that is consistent across every login node, compute node, and storage server, normally sourced from LDAP or Active Directory rather than created locally on each machine (see Section 10).
  • Authentication material — an SSH public key registered against that identity, or a Kerberos principal, so the user can actually prove who they are.
  • A project / allocation assignment — which grant, budget code, or research group's compute time the user's jobs should be billed against.
  • Storage quota — a home directory, and usually a project/scratch directory, with quota limits set correctly on day one instead of "unlimited until someone notices."
  • A Slurm association — the tuple of (cluster, account, user, partition) that the scheduler checks before it will even queue a job, plus a QOS that determines priority and resource caps.
  • Group membership for access control — Unix/LDAP groups that gate which partitions, licensed software, or fairshare accounts the user is allowed to touch.

Miss any one of these and the failure mode is usually a cryptic error days later — "Invalid account or account/partition combination" from Slurm, or a home directory owned by the wrong UID after a re-image — rather than a clean "access denied" at the front door. That's why HPC teams try hard to make onboarding a single, repeatable pipeline instead of a checklist a human re-types from memory each time.

Distribution Lists (DLs) as the access-control lever

A Distribution List (or mail-enabled security group, or Entra ID/AD security group — the corporate-IT terms overlap heavily) is the object your organization already uses for things like "everyone on the AI Research team gets this email" or "everyone in this group can book this shared calendar." HPC teams reuse the same object as the single source of truth for cluster access tiers.

The pattern: create (or reuse) a group like team-ai-research in the corporate directory, and treat membership in that group as the trigger for "this person should have cluster access at tier X." A PI or team lead manages membership through the normal corporate group-management UI — no cluster admin ticket required for routine adds. A scheduled sync job then mirrors that membership into the cluster's own LDAP/POSIX group, and everything downstream (home directory creation, Slurm association, partition access) keys off that POSIX group.

Why this matters
Without a DL-to-cluster-group mapping, every new hire becomes a manual cluster-admin ticket: create Unix account, add to Slurm, set quota, done — repeated by hand, every time, for every cluster. With the mapping in place, the cluster admin's job shrinks to "make sure the sync job ran," and access changes flow at the speed of a corporate group edit. This is also why offboarding tends to actually happen on time when it's DL-driven — removing someone from a DL is a five-second action a manager already knows how to do, versus filing a ticket that might sit for weeks.

End-to-end onboarding pipeline

The diagram below shows the full path from "a new team member needs cluster access" to "they've run their first job." Each stage is intentionally decoupled so that a failure or delay in one stage (say, a slow approval) doesn't corrupt the state of the others.

Walking through each stage

1. Request — the user (or their manager) files a ticket or fills out an access-request form naming the project/allocation they need access to.

2. Approval — the PI, team lead, or allocation owner approves. This is the only gate that should require human judgment; everything after it should be mechanical.

3. Added to DL/AD group — once approved, the requester (or an automated workflow acting on the approval) adds the user to the corporate DL/security group that maps to the target cluster access tier, e.g. team-ai-research → hpc-ai-research-users.

4. Sync job — a scheduled job (cron, systemd timer, or an identity-governance connector) reads DL membership from Active Directory/Entra ID and reconciles it against the cluster's LDAP directory or local /etc/group state. This can be a vendor tool (Entra Cloud Sync group provisioning, SSSD's AD provider with dynamic group mapping) or a small custom script — see the code examples below.

5. Provisioning — the sync (or a hook it triggers) creates the POSIX group if it doesn't exist, creates the user's home directory with correct ownership and mode, and sets an initial storage quota.

6. Slurm association — sacctmgr creates the (cluster, account, user) association and assigns a default QOS, so the scheduler will accept jobs from this user under the right billing account.

7. Welcome email — an automated email (ideally templated, not hand-typed) with links to getting-started docs, the SSH onboarding steps, and who to contact for help.

8. First login validation — the user completes the Day-1 checklist below; a lightweight validation script can confirm home directory ownership, quota, and Slurm association are all correctly in place before declaring onboarding "done."

Automating provisioning: sacctmgr, home directories, and group sync

None of the steps above need to be manual toil. Below are the building blocks a cluster team typically scripts around.

Slurm accounting: creating the user association

Slurm tracks accounting and enforces access at the level of an association — the (cluster, account, user, partition) tuple, managed entirely through sacctmgr against the slurmdbd database. Per the SchedMD accounting docs, you must define clusters before accounts, and accounts before users — the hierarchy has to exist top-down.

# 1. Create the billing/allocation account (once, per project)
sacctmgr add account ai_research \
    Description="AI Research team allocation" \
    Organization="team-ai-research"

# 2. Add the new user to that account on this cluster,
#    with a default QOS and a fairshare weight
sacctmgr add user name=jsmith \
    account=ai_research \
    cluster=oci-nrt-cs-001 \
    partition=gpu-a100 \
    qos=normal \
    fairshare=100

# 3. Verify the association landed correctly
sacctmgr show assoc user=jsmith format=Account,Cluster,User,Partition,QOS

# 4. (Offboarding mirror, see below) — revoke without deleting history
sacctmgr modify user jsmith set MaxSubmitJobs=0

Note the last line: for offboarding, most sites prefer to set limits to zero rather than immediately deleting the association — deleting an association can orphan historical accounting records for jobs the user already ran, which breaks usage reporting.

Home directory creation with correct ownership and quota

This is typically a small idempotent script run by the provisioning step, either directly or as an LDAP/SSSD post-sync hook:

#!/usr/bin/env bash
# provision_home.sh    
set -euo pipefail
USER="$1"; UID_N="$2"; GID_N="$3"; QUOTA_GB="$4"
HOME_DIR="/home/${USER}"

if [ ! -d "$HOME_DIR" ]; then
  mkdir -p "$HOME_DIR"
  cp -r /etc/skel/. "$HOME_DIR"
fi

chown -R "${UID_N}:${GID_N}" "$HOME_DIR"
chmod 750 "$HOME_DIR"

# Example: GPFS/NFS quota via a filer-side quota tool
# (swap for your storage backend's actual CLI, e.g. `zfs set quota=`,
#  `mmsetquota` for GPFS, or NetApp `qtree`/`quota` commands)
set_fs_quota --path "$HOME_DIR" --hard "${QUOTA_GB}G" --soft "$((QUOTA_GB * 9 / 10))G"

echo "Provisioned home for ${USER} (uid=${UID_N}) quota=${QUOTA_GB}G"

Syncing a DL/AD group into a POSIX group

There are three common approaches, in increasing order of "buy vs. build":

ApproachHow it worksBest for
SSSD AD provider auto-mappingSSSD reads AD group membership directly at auth time via ldap_group_* / ad_gpo_* settings; no separate sync job needed since SSSD is already the identity provider (see Section 10)Sites already using SSSD against AD as the primary identity source
Managed identity-governance syncEntra Cloud Sync / SCIM connector provisions group membership into an on-prem AD or LDAP target on a scheduleLarger orgs with existing Entra ID/Entra Governance investment
Custom scheduled sync scriptA cron job queries the DL via Graph API/LDAP, diffs against the cluster's POSIX group, and applies adds/removesSmall teams, or bridging a DL type the managed connectors don't support
#!/usr/bin/env python3
# sync_dl_to_posix_group.py — run every 15 min via cron/systemd timer
import subprocess
from graph_client import get_group_members  # thin wrapper over MS Graph API

DL_NAME = "team-ai-research"
POSIX_GROUP = "hpc-ai-research-users"

def current_posix_members(group):
    out = subprocess.run(["getent", "group", group], capture_output=True, text=True)
    return set(out.stdout.strip().split(":")[-1].split(","))

def main():
    desired = set(get_group_members(DL_NAME))       # usernames from the DL
    current = current_posix_members(POSIX_GROUP)

    to_add = desired - current
    to_remove = current - desired

    for user in to_add:
        subprocess.run(["usermod", "-aG", POSIX_GROUP, user], check=True)
        print(f"[sync] added {user} to {POSIX_GROUP}")

    for user in to_remove:
        subprocess.run(["gpasswd", "-d", user, POSIX_GROUP], check=True)
        print(f"[sync] removed {user} from {POSIX_GROUP} (no longer in DL)")

if __name__ == "__main__":
    main()
Watch out
A naive sync script that only adds and never removes quietly turns your access model into a ratchet — people accumulate access and it never comes back off. Always diff both directions, and log every removal so an audit can explain "who lost access, and when."

Offboarding: the mirror process that's easy to neglect

Offboarding gets far less engineering attention than onboarding, mostly because nobody demos it in a sprint review — but a stale association is a real security and cost-control problem: idle allocations still count against fairshare history, and an ex-employee's still-valid SSH key is exactly the kind of gap an audit will flag.

Offboarding step detail

  • Remove from DL — ideally triggered automatically from an HR termination event, not a manual step someone has to remember.
  • Sync detects removal — the exact same scheduled sync job from onboarding picks up the membership diff and runs the "remove" branch.
  • Disable the account — lock the Unix account (usermod -L / disable in AD) and revoke or expire the SSH key so no new sessions can start, without deleting the account outright (in-flight jobs may still need to finish or be cleanly killed).
  • Revoke the Slurm association — set submit limits to zero (sacctmgr modify user … set MaxSubmitJobs=0) rather than deleting the association immediately, to preserve accounting history.
  • Quota-lock the home directory — flip to read-only and freeze the quota rather than deleting data instantly; give the PI/manager a window to retrieve anything needed.
  • Retention window — typically 30–90 days depending on site policy, after which the data is archived or purged.
  • Purge — final deletion, ideally requiring explicit PI/manager sign-off so nobody's unpublished results vanish by accident.

Day-1 checklist

Hand this to every new user as part of the welcome email — it's the human-facing counterpart to the automated pipeline above.

  • ☐ Confirm you received the welcome email with your cluster hostname and account name
  • ☐ Generate an SSH key pair if you don't already have one (ssh-keygen -t ed25519) and submit the public key through the access portal
  • ☐ Log in to a login/head node and confirm your shell prompt shows the expected username and UID (id)
  • ☐ Check your home directory ownership and quota (quota -s or the site's storage-quota command)
  • ☐ Run sacctmgr show assoc user=$USER to confirm your account, partition, and QOS are correct
  • ☐ List available software with module avail and load a module (module load) to confirm the module system works
  • ☐ Submit a trivial first Slurm job (e.g. sbatch --wrap="hostname" -A ai_research -p gpu-a100) and confirm it completes with sacct -j <jobid>
  • ☐ Bookmark the getting-started docs and the support/ticket channel for your site
  • ☐ If you expect to need more storage than the default quota, submit a quota-increase request through the same access-portal workflow used for the original request — don't wait until you hit the limit mid-job
Tip
Bake the first four checklist items into an automated post-provisioning validation script that runs right after step 6 of the onboarding pipeline. If any of them fail — wrong UID on the home directory, missing Slurm association — you find out from a monitoring alert before the new hire ever files a "I can't log in" ticket.
